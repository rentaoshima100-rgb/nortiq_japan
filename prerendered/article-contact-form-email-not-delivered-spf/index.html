問い合わせフォームの通知メールが届かない原因と設定

Web制作問い合わせフォームの通知メールが届かない原因と設定NORTIQ LABS · COLUMN

通知メールが届かないとき、最初に確認することは？

送信元ドメインにSPFまたはDKIMが設定されているかを、DNSのTXTレコードで確認することから始めます。フォームの不具合を疑ってプログラムを調べる前に、メールの認証設定を見るほうが早く原因に届きます。

Googleは「メール送信者のガイドライン」で、2024年2月1日からすべての送信者に対し、送信ドメインへのSPFまたはDKIMの設定、正引きと逆引きのDNSの設定、TLS接続の使用を求めています (出典: Google「メール送信者のガイドライン」2024年2月1日適用)。この要件を満たしていないメールは、届かないか迷惑メールとして扱われる可能性があります。つまり御社の設定が数年前のままであれば、フォーム側に手を入れても状況は変わりません。

あなたのホームページは、いま何点ですか？

URLを入れるだけで、SEO・セキュリティ設定・表示速度・AI対応をその場で採点します。登録は不要、無料です。

ホームページを無料診断する →

確認の順番は「設定の有無」「送信元の一致」「迷惑メール判定」の3段

次の順番で切り分けます。上から順に見ることで、無駄な調査を省けます。

  1. 設定の有無を見る (所要10分)。送信元ドメインのTXTレコードに v=spf1 で始まる記述があるかを確認します。無ければここが原因です。
  2. 送信元が一致しているかを見る (所要15分)。フォームの通知メールが、どのサーバから送られているかを特定します。つまずきやすい点は、サイトと通知メールの送信元が別々のサービスになっている場合です。レンタルサーバのフォーム機能と、外部のメール配信サービスを併用しているときに起こります。
  3. 迷惑メール判定を見る (所要15分)。届いてはいるが迷惑メールフォルダに入っているのか、そもそも届いていないのかを分けます。受信側のメールヘッダで認証結果を読む方法は後述します。

1の段階で設定が無いと分かれば、作業はSPFの追記から始まります。手順は「設定の手順は？フォーム通知メールの直し方」で具体的に示します。

自社で確認できる範囲と、サーバ会社に依頼する範囲の線引き

どこまで自社で確認できるかを整理しておくと、問い合わせの手間が減ります。

作業 自社で可能か 依頼先
TXTレコードの有無の確認 可能 (公開情報のため) 不要
メールヘッダの認証結果の確認 可能 不要
SPFレコードの追記・修正 管理画面があれば可能 DNSを管理するサーバ会社または制作会社
DKIMの鍵の発行と公開 原則として不可 メールを送るサービスの提供元
DMARCの宣言と運用方針の決定 方針の決定は自社 設定はDNSの管理先

DKIMの鍵はメールを送る側のサービスが発行するため、御社だけでは完結しません。どのサービスから送っているかを先に特定しておくと、問い合わせが一度で済みます。

なぜ急に届かなくなったのか？要件が変わっています

Gmailは2024年2月1日から、すべての送信者に送信ドメイン認証の設定を求めています。フォームも社内の設定も変えていないのに届かなくなったのであれば、受信側の基準が変わったと考えるほうが筋が通ります。

すべての送信者に求められる要件

Googleの「メール送信者のガイドライン」は、2024年2月1日以降、送信件数の多少にかかわらず次を求めています (出典: Google「メール送信者のガイドライン」)。

  • 送信ドメインにSPFまたはDKIMのいずれかを設定する
  • 送信ドメインまたはIPに有効な正引きと逆引きのDNS (PTRレコード) を設定する
  • メール送信にTLS接続を使用する
  • Postmaster Toolsで報告される迷惑メール率を0.3%未満に保つ
  • メッセージをRFC 5322の形式に従って作成する

同ガイドラインでは、認証されていないメッセージは迷惑メールとされるか、5.7.26のエラーで拒否される可能性があるとされています。問い合わせの通知メールは1日数件かもしれませんが、この要件は件数で免除されません。

1日5,000件を超える送信者に追加される要件

同じドメインから1日5,000件を超えてGmail宛に送る場合は、要件が増えます (出典: Google「メール送信者のガイドライン」)。

項目 すべての送信者 1日5,000件超
SPFまたはDKIM いずれか必須 両方必須
DMARC 要件なし 必須 (ポリシーは none でもよい)
From:ヘッダのドメインの一致 要件なし SPFまたはDKIMのドメインと一致
ワンクリック登録解除 要件なし マーケティングメールと購読メールで必須

この5,000件は1回の送信数ではなく、同じドメインから送信されたすべてのメールが合算されます。フォームの通知は少なくても、メールマガジンや請求書の自動送信を同じドメインから出していれば、合算で基準を超えることがあります。御社が送っているメールを棚卸ししておくと、どちらの要件に当てはまるかが判断できます。

なお迷惑メール率については、0.3%未満が要件で、0.10%未満に保ち0.30%以上にならないようにすることが推奨されています (出典: Google「メール送信者のガイドライン」)。確認の手順は後述します。

SPF・DKIM・DMARCは何が違う？

SPFは送信元のサーバを、DKIMは本文の改変の有無を、DMARCはその結果をどう扱うかを示す仕組みです。3つは置き換えの関係ではなく、積み上げの関係にあります。

SPFとは、そのドメインのメールを送ってよいサーバのIPをDNSで宣言する仕組みです。DKIMとは、送信時に電子署名を付け、受信側が公開鍵で検証できるようにする仕組みです。DMARCとは、SPFとDKIMの検証に失敗したメールを受信側にどう扱ってほしいかを、ドメインの持ち主が宣言する仕組みです。

3つの役割を1枚の表で整理する

項目 SPF DKIM DMARC
検証するもの 送信元のサーバ 署名と本文の同一性 SPFとDKIMの結果とFrom:の一致
設定する場所 DNSのTXTレコード 送信サービスと DNS DNSのTXTレコード
転送に弱いか 弱い (経路が変わると失敗) 比較的強い 両者の結果を見る
単独で届くか 条件により届く 条件により届く 単独では成立しない

DMARCのポリシー (none / quarantine / reject) の違い

DMARCは3つのポリシーから選びます。none は監視のみで扱いを変えず、quarantine は迷惑メールフォルダへ、reject は受信を拒否します。

まず none で宣言してレポートを受け取り、自社のメールが正しく認証されているかを確かめてから強める運用が一般的です。順序を逆にすると、自社の正規のメールまで止まります。

国内では、宣言したまま none に留まっている例が多く報告されています。日本プルーフポイントの調査では、日経225企業のDMARC導入率は92%である一方、reject または quarantine を適用している割合は43%でした。業種別では金融・保険業が60%、製造業が47%です (出典: 日本プルーフポイント DMARC導入状況の調査)。官公庁ドメインでは reject が18%、none が61%、未導入が12%と報じられています (出典: ScanNetSecurity 日本プルーフポイント調査の報道)。いずれも民間企業による調査で、政府統計ではありません。

御社の目的がフォームの通知メールを届かせることであれば、まずSPFとDKIMを確実に通すことが先です。DMARCは none から始めて差し支えありません。なお総務省は2018年から、JPドメイン名における送信ドメイン認証技術の設定状況を調査し公表しています (出典: 総務省 報道資料「JPドメイン名における送信ドメイン認証技術の設定状況の調査」)。

設定の手順は？フォーム通知メールの直し方

送信経路の特定、SPFの追記、DKIMの有効化、DMARCの宣言、動作確認の5手順で進めます。DNSの変更を含むため、作業前に現在のレコードを控えておきます。

手順1から3: 送信経路の特定とSPF・DKIMの設定

  1. 送信経路を特定する (所要30分)。フォームの通知がどのサーバやサービスから送られているかを確認します。つまずきやすい点は、CMSのプラグインが自前でメールを送っている場合です。サーバのメール機能を使っているつもりで、実際は別経路という例があります。
  2. SPFを追記する (所要30分とDNSの反映待ち)。送信に使うサービスが公開している指定文字列を、既存のSPFレコードに追記します。つまずきやすい点は、サービスごとに指定が異なるため、提供元の公式ドキュメントの記載をそのまま使う必要がある点です。
  3. DKIMを有効にする (所要1時間程度)。送信サービス側で鍵を発行し、指示されたTXTレコードまたはCNAMEをDNSへ登録します。鍵の発行は送信側のサービスでしか行えないため、依頼が必要です。

手順4から5: DMARCの宣言と送信テスト

  1. DMARCを宣言する (所要30分)。_dmarc のTXTレコードで、まず p=none とレポートの送付先を指定します。Googleのガイドラインでも、1日5,000件超の送信者の要件としてDMARCの設定が挙げられ、ポリシーは none でもよいとされています (出典: Google「メール送信者のガイドライン」)。
  2. 送信テストを行う (所要30分)。自社のフォームから実際に送信し、Gmailなど外部のアドレスで受信してヘッダの認証結果を確認します。確認の読み方は次のセクションで扱います。

つまずきやすい点: SPFレコードを2つ書いてしまう

実装の現場で最も多い失敗は、SPFレコードを2行に分けて登録してしまうことです。SPFは1つのドメインに1つという前提のため、2つあると評価が不正になり、設定したつもりで認証に失敗します。サービスを追加するときは、新しい行を作らず既存の1行に追記します。

もう1つ多いのが、DNSの反映待ちを考えずに判断してしまうことです。変更直後は古い情報が参照されることがあるため、テストは時間を置いて行います。

直ったかどうかは、どこで確認する？

受信側のヘッダでSPFとDKIMの判定を見て、あわせてPostmaster Toolsの迷惑メール率を確認します。送信できたかではなく、受信側がどう判定したかが基準になります。

メールヘッダで認証結果を読む

テスト送信したメールを外部のアドレスで受け取り、メッセージのソースを表示します。Authentication-Results の行に、次のような判定が並びます。

表示 意味 対応
spf=pass 送信元サーバが許可されている 問題なし
spf=fail または softfail 許可されていないサーバから送信 SPFの指定文字列を見直す
dkim=pass 署名の検証に成功 問題なし
dkim=none 署名が付いていない 送信サービス側でDKIMを有効化する
dmarc=pass From:のドメインが認証と一致 問題なし

spf=pass でも dmarc=fail になる場合があります。これはFrom:に表示されるドメインと、実際に認証されたドメインがずれているためです。Googleのガイドラインでも、1日5,000件超の送信者の要件として、From:ヘッダのドメインがSPFまたはDKIMのドメインと一致していることが挙げられています (出典: Google「メール送信者のガイドライン」)。

拒否されたときに返るエラーコードの意味

届かない場合は、送信側に戻るエラーの文面を確認します。Googleのガイドラインには、認証されていないメッセージは迷惑メールとされるか、5.7.26のエラーで拒否される可能性があると記載されています (出典: Google「メール送信者のガイドライン」)。このコードが返っていれば、原因は認証設定にあると特定できます。

継続的な指標としては、Postmaster Toolsの迷惑メール率を見ます。同ガイドラインでは0.3%未満に保つことが要件とされ、0.10%未満に保ち0.30%以上にならないようにすることが推奨されています (出典: Google「メール送信者のガイドライン」)。問い合わせの通知メールのような件数の少ない送信では率が安定しないため、メールマガジンなど他の送信とあわせて見る必要があります。

ここまで確認して pass が並んでいるのに届かない場合は、原因が別にあります。次のセクションで切り分けます。

設定しても届かないときに疑う箇所は？

フォームの送信元アドレスの付け方と、フォーム自体が不正送信に使われていないかを確認します。認証が pass しているのに届かない場合、原因はフォームの実装側に残っています。

送信者アドレスを入力値にしている場合の問題

よくある実装が、通知メールのFrom:に問い合わせ者が入力したメールアドレスをそのまま入れる方式です。この場合、送信しているのは御社のサーバなのに、From:は他社のドメインになります。SPFもDKIMも御社のドメインで設定しているため、認証は一致しません。

直し方は、From:を御社のドメインの固定アドレスにし、問い合わせ者のアドレスはReply-To:に入れることです。返信のしやすさは保たれ、認証も通ります。実装の変更が必要なため、制作会社への依頼事項になります。

フォームが第三者中継に悪用されていないかの確認

入力値をそのままメールの項目に渡している実装は、メールヘッダ・インジェクションの対象になります。IPAは、この問題によってメールの第三者中継が可能になり、迷惑メールの送信に悪用されるおそれがあると説明しています (出典: IPA「安全なウェブサイトの作り方」1.8 メールヘッダ・インジェクション)。御社のサーバから迷惑メールが送られていれば、正規の通知メールも届きにくくなります。

IPAは根本的解決として3項目を挙げ、保険的対策として外部からの入力の全てについて改行コードを削除することを示しています (出典: IPA「安全なウェブサイトの作り方」1.8)。古いフォームを使い続けている場合は、この観点での点検を依頼する価値があります。

自動投稿が多い場合の対策としては、reCAPTCHAの導入があります。reCAPTCHA v3はスコアを0.0から1.0の範囲で返し、既定のしきい値は0.5です (出典: Google for Developers「reCAPTCHA v3」)。しきい値は自社サイトの状況に合わせて調整します。なお受信する迷惑投稿そのものの対策は別の論点です。

国の報告書でも、送信ドメイン認証技術としてDMARC、SPF、DKIMが挙げられています (出典: 国家公安委員会・総務大臣・経済産業大臣「不正アクセス行為の発生状況及びアクセス制御機能に関する技術の研究開発の状況」令和8年3月12日)。設定は迷惑メール対策の一部でもあります。

制作会社に依頼するとき、何を伝えればよい？

送信経路と希望するDMARCのポリシー、確認方法の3点を伝えると作業範囲が決まります。「メールが届きません」だけでは、調査から始まるため時間と費用がかかります。

発注時に伝える3点

  1. 送信経路。どのサービスやサーバからフォームの通知メールを送っているか。分からない場合は「特定も含めて依頼する」と伝えます。
  2. DMARCのポリシーの希望。まず p=none で始めたいのか、将来 quarantine まで進めたいのか。方針は御社の判断事項です。
  3. 確認方法。作業完了の判定を、ヘッダの spf=pass と dkim=pass の確認まで含めるかどうか。ここを決めておくと、設定したが届かないという手戻りを防げます。

あわせて、DNSの管理をどこが行っているかを先に調べておきます。ドメインの登録事業者とサーバ会社が別の場合、レコードを編集できる側に依頼する必要があります。

運用を引き継ぐときの確認事項

設定は一度で終わりではありません。送信に使うサービスを追加したときは、SPFへの追記が必要になります。引き継ぎでは次を確認しておきます。

確認事項 なぜ必要か
現在のSPFレコードの全文 サービス追加時に1行へ追記するため
DKIMの鍵を発行したサービス名 鍵の更新や再発行の窓口が変わるため
DMARCレポートの送付先アドレス 受け取っていないと運用が止まるため
DNSの管理先 変更作業の依頼先を間違えないため

御社のフォームが届かない状態は、問い合わせの機会がそのまま失われている状態です。原因が認証設定なのか実装側なのかは、ヘッダの判定を見れば切り分けられます。それでも判断がつかない場合や、設定と実装の両方を見直したい場合は、無料診断で現状の確認からご相談いただけます。当社では自社でメールの送信経路と認証設定を運用しており、実装の側から調べられます。

よくあるご質問

この記事に関して多い質問と回答をまとめます。

SPFとDKIMは両方設定する必要がありますか

Googleの「メール送信者のガイドライン」では、すべての送信者に対してはSPFまたはDKIMのいずれかを求めています。ただし同じドメインから1日5,000件を超えてGmail宛に送る場合は、SPFとDKIMの両方とDMARCが必須です (出典: Google「メール送信者のガイドライン」)。件数が少なくても、転送された場合に強いのはDKIMのため、両方を設定しておくほうが安定します。

DMARCのポリシーは none のままでも問題ありませんか

通知メールを届かせるという目的に限れば、none でも支障はありません。Googleのガイドラインも、1日5,000件超の送信者の要件としてDMARCの設定を挙げつつ、ポリシーは none でもよいとしています (出典: Google「メール送信者のガイドライン」)。なりすまし対策まで含めて考える場合は、レポートで自社のメールの状況を確認した後に quarantine へ進めます。

レンタルサーバのフォームを使っている場合、SPFには何を書けばよいですか

サーバ会社が公開している指定文字列をそのまま使います。会社ごとに記述が異なるため、推測で書かず公式のドキュメントを確認してください。すでにSPFレコードがある場合は、新しい行を作らず既存の1行に追記します。

通知メールの送信者アドレスを問い合わせ者のメールアドレスにしてはいけないのですか

From:に他社のドメインを入れると、御社のドメインで設定した認証と一致しなくなります。From:は自社ドメインの固定アドレスにし、問い合わせ者のアドレスはReply-To:に入れる実装が安全です。返信の操作は変わりません。

設定を変えてから、届くようになるまでどのくらいかかりますか

DNSの変更が参照されるまでに時間差があるため、変更直後の判定はあてになりません。しばらく時間を置いてからテスト送信し、ヘッダの spf=pass と dkim=pass を確認してください。認証が通っているのに届かない場合は、フォームの実装側を確認します。
