# PHP 8.2サポート終了2026年12月の対応5手順

## まず何をするか: 自社サイトのPHPの版を確認して制作会社へ連絡する

最初にやることは、自社サイトが動いているPHPの版を確認し、8.2以下であれば保守先へ「いつ上げるか」を日付で尋ねる連絡を入れることです。PHP公式のSupported Versionsによると、PHP 8.2のセキュリティサポートの終了日は2026年12月31日です。期限が決まっている作業ですので、調べるより先に連絡を入れてしまってもかまいません。

### PHPの版を自分で確認する3つの場所

技術の知識がなくても、次の順番で見れば確認できます。

1. WordPressの管理画面を開き、「ツール」から「サイトヘルス」を選び、「情報」タブの「サーバ」の欄にある「PHPバージョン」を見ます。所要時間は3分ほどです。
2. 管理画面に入れない場合は、レンタルサーバの管理画面にログインし、「PHP設定」や「PHPバージョン切替」の画面で、対象のドメインに設定されている版を確認します。所要時間は5分ほどです。
3. どちらも分からない場合は、契約している制作会社または保守会社に「このサイトのPHPの版を教えてください」と尋ねます。回答までの時間は相手次第ですので、この経路を選ぶ場合は早めに送ります。

### 連絡時に書くと話が早い3項目

保守先への連絡では、次の3点を本文に入れておくと、折り返しの質問を1往復減らせます。

- 対象のサイトのURL (複数ある場合はすべて)
- 確認できたPHPの版、または確認できなかったという事実
- 「2026年12月31日までに上げられますか。難しい場合は、いつなら可能ですか」という日付を尋ねる一文

上げる先の版をこちらから指定する必要はありません。WordPress公式の動作環境では推奨されるPHPのバージョンが8.3以上とされており、選び方には次の期限という観点も関わりますので、この点は後述します。

### 所要時間の目安と、つまずきやすい点

確認そのものは10分程度で終わりますが、実際に版を上げる作業には、検証環境での動作確認を含めて数日から数週間かかることがあります。年末は制作会社の作業枠が埋まりやすく、期限に近づくほど日程の選択肢が減ります。

つまずきやすいのは、「サーバの管理画面でPHPの版を切り替えられるので自分でやってしまおう」と考えてしまう場面です。切り替えは数クリックで終わりますが、古いプラグインやテーマがその場で動かなくなり、サイトが表示されない状態になることがあります。切り替えは検証環境での確認の後に行うものですので、本番のサイトで試さないようにしてください。

## PHP 8.2のサポートは2026年12月31日に終わります

PHP公式のSupported Versionsによると、PHP 8.2のセキュリティサポートの終了日は2026年12月31日で、Active Supportは2024年12月31日に終了しています。つまりPHP 8.2は、すでに2年近く「不具合の修正は行われず、セキュリティの修正だけが提供される」状態にあり、その最後の保護も2026年の年末で切れます。

### Active SupportとSecurity Supportの違い

PHP公式のSupported Versionsは、各版の支援期間を2段階で示しています。

| 段階 | 提供されるもの | PHP 8.2の終了日 |
|---|---|---|
| Active Support | 不具合の修正とセキュリティの修正 | 2024年12月31日 |
| Security Support (end of life) | 深刻なセキュリティ問題の修正のみ | 2026年12月31日 |

Active Supportが終わった時点では、動作に支障があっても修正の対象になりません。Security Supportまで終わると、深刻なセキュリティ問題が見つかっても修正そのものが提供されなくなります。この2段目が終わる日が、PHP 8.2では2026年12月31日です。

### 終了後に何が止まるのか、何が止まらないのか

誤解されやすい点ですので、分けて書きます。

- **止まらないもの**: サイトの表示です。2027年1月1日になった瞬間にサイトが落ちるわけではありません。PHP 8.2は同じように動き続けます。
- **止まるもの**: 新しく見つかった問題への修正の供給です。問題が見つかっても、直す手段が提供されません。
- **時間差で影響が出るもの**: WordPress本体とプラグインの対応です。WordPress公式の動作環境では推奨されるPHPのバージョンが8.3以上とされており、古いPHPのままでは、更新を続けるうちに動作が保証されない組み合わせになっていきます。
- **外部から見える部分**: レンタルサーバ側が古いPHPの提供を打ち切る場合です。契約しているサーバの告知によっては、こちらの都合に関係なく切り替えの期日が決まります。

### サポートが切れた状態を使い続けた場合にIPAが指摘していること

IPAはサポート終了に関する注意喚起で、サポートが終了した製品を使い続けた場合、危険度の高い脆弱性が新たに見つかっても製品ベンダによる修正等の対応が期待できず、情報漏えいや意図しないサービス停止につながるおそれがあると説明しています。根本的な対策としては、サポートが継続している後継または代替へ移行し、移行先で動作検証を行うことが推奨されています。

なお、このIPAの注意喚起はOSを対象とした文書で、PHPを名指しした記述ではありません。ここではサポート終了という状態の一般的な考え方として参照しています。ただし「移行したうえで動作検証を行う」という組み立ては、PHPの版を上げる作業でもそのまま当てはまります。検証環境での確認を省いて本番だけを切り替える進め方は、この推奨から外れることになります。

## 上げる先は8.3か8.4か: 次の期限から逆算して選ぶ

WordPressの推奨環境を満たす最低ラインはPHP 8.3以上で、同じ作業を数年先に回したい場合はセキュリティサポートが2028年12月31日まであるPHP 8.4が候補になります。どちらを選んでも作業そのものの手順は変わりませんので、判断の軸は「次に同じ依頼をするのはいつか」に置くと決めやすくなります。

### 各版のセキュリティサポートの終了日を並べて比べる

PHP公式のSupported Versionsによると、各版の期限は次のとおりです。

| 版 | Active Supportの終了日 | Security Supportの終了日 |
|---|---|---|
| PHP 8.2 | 2024年12月31日 | 2026年12月31日 |
| PHP 8.3 | (終了済み) | 2027年12月31日 |
| PHP 8.4 | 2026年12月31日 | 2028年12月31日 |
| PHP 8.5 | 2027年12月31日 | 2029年12月31日 |

8.3に上げた場合、次の期限は2027年12月31日で、1年後にまた同じ作業が必要になります。8.4なら2028年12月31日、8.5なら2029年12月31日まで猶予があります。作業を1回で済ませたい場合、8.3は選びにくい版だということが表から読み取れます。

### WordPress公式が求める動作環境 (PHP・データベース・HTTPS)

WordPress公式の動作環境のページには、次のとおり記載されています。

- PHP: 「バージョン 8.3 以上。」
- データベース: 「MariaDB 10.11 以上、または MySQL 8.4 以上。」
- HTTPS: 「すべてのインストールに必須。」

ここで見落としやすいのが、データベースの版です。PHPだけを上げても、データベースが古いままでは推奨環境を満たしません。保守先に連絡するときは、PHPの版と合わせてデータベースの版も確認してもらうと、二度手間になりません。

WordPress本体も確認の対象です。WordPress公式のリリース一覧によると、最新の安定版は2026年11月18日に公開されたWordPress 7.1.5で、同ページには7.1シリーズの中で最新のもののみが安全に使用でき、積極的にメンテナンスされていると記載されています。PHPの版を上げる作業は、本体とプラグインの更新と並行して発生すると考えてください。

### プラグインとテーマの対応状況という制約

実際にどの版まで上げられるかは、使っているプラグインとテーマで決まることがあります。制約になりやすいのは次の3つです。

1. **更新が止まっているプラグイン**: 作者の更新が数年単位で止まっているものは、新しいPHPで動く保証がありません。代替への差し替えか、機能そのものをやめる判断が必要になります。
2. **制作時に作り込んだテーマや独自機能**: 既製のテーマと違って作者による更新がありませんので、修正は制作会社の作業になります。ここが見積もりの差になりやすい部分です。
3. **決済や外部サービスとの連携**: 連携先が指定する動作環境に合わせる必要があり、PHPの版を自由に選べない場合があります。

したがって、版の希望は「8.4を希望しますが、プラグインの対応状況によっては8.3でもかまいません」という形で伝えるのが現実的です。確定させるのは、検証環境での確認の後になります。

## 依頼の手順: 見積もりを取ってから切り替えるまでの5ステップ

確認、見積もり、検証環境での動作確認、本番の切り替え、切り替え後の点検の5段階に分け、各段階で何を受け取るかを先に決めておくと手戻りが出ません。社内で技術的な判断ができなくても、「次に何が返ってくるか」が分かっていれば進行は管理できます。

### 手順1 現状の確認と対象の洗い出し

保守先に、現在のPHPの版、データベースの版、WordPress本体の版、使用中のプラグインとテーマの一覧を出してもらいます。対象のサイトが複数ある場合は、サイトごとに分けて出してもらってください。

- 所要時間の目安: 依頼から2日から5日程度
- つまずきやすい点: サイトが複数ある場合、サブドメインのサイトや過去のキャンペーン用サイトが抜け落ちます。ドメインの一覧を自社側から渡すほうが確実です

### 手順2 見積もりの取得と作業範囲の確定

洗い出しの結果をもとに、見積もりを依頼します。この段階で「上げる先の版」「検証環境を用意するか」「プラグインが動かない場合の対応」を文面で確定させます。

- 所要時間の目安: 依頼から1週間程度
- つまずきやすい点: 「PHPバージョンアップ作業」の1行だけで見積もりが出てくることがあります。その場合は内訳を分けてもらいます。詳しくは次のセクションで扱います

### 手順3 検証環境での動作確認

本番のサイトを複製した検証環境を作り、そこで新しいPHPの版に切り替えて動作を確認します。IPAもサポート終了への対応として、移行先での動作検証を推奨しています。

- 所要時間の目安: 1週間から2週間
- つまずきやすい点: 確認を制作会社だけに任せると、業務上の使い方が抜けます。自社でも問い合わせフォームの送信や記事の投稿を実際に試してください

### 手順4 本番の切り替えと切り戻しの用意

検証環境で問題がないことを確認したら、本番を切り替えます。切り替え前のバックアップと、問題が出た場合に元の版へ戻す手順を、作業前に文面で確認しておきます。

- 所要時間の目安: 作業自体は当日のうちに完了します
- つまずきやすい点: アクセスの多い時間帯や、キャンペーンの期間中は避けます。切り戻しの判断を誰がするのかも、作業前に決めておきます

### 手順5 切り替え後の点検と記録

切り替え後に、サイトの表示と主要な機能を点検します。あわせて、切り替えた日付と上げた先の版を自社の記録に残します。

- 所要時間の目安: 当日30分程度の点検と、1週間程度の経過観察
- つまずきやすい点: 記録を残さないと、次の期限が来たときに現状を再び調べ直すことになります。点検の具体的な箇所は後述します

## 見積書で確認する項目と、追加費用になりやすい作業

PHPの版を上げる作業は、WordPress本体とプラグインの更新、テーマの修正、検証環境の用意が別項目になりやすいため、どこまでが見積もりに含まれるかを項目ごとに確認します。「PHPバージョンアップ対応」の1行で金額だけが書かれた見積もりは、後から追加費用が発生しやすい形です。

### 作業範囲として書き分けてもらう項目

次の項目が、それぞれ含まれるのか、別見積もりなのかを文面で確認します。金額を比べる前に、同じ範囲で比べられる状態にすることが先です。

| 項目 | 確認したいこと |
|---|---|
| 検証環境の用意 | 本番の複製を作るか、本番で直接作業するか |
| バックアップの取得 | 取得するデータの範囲と、保管する期間 |
| PHPの切り替え作業 | サーバ側の設定変更そのもの |
| WordPress本体の更新 | 同時に最新の安定版へ上げるか |
| プラグインの更新 | 全件を対象にするか、必要なものだけか |
| テーマや独自機能の修正 | 修正が必要になった場合の扱い |
| 切り替え後の動作確認 | 誰がどこまで確認するか |
| 切り戻しの対応 | 問題が出た場合の作業が含まれるか |

### 古いプラグインやテーマが動かない場合の扱い

見積もりの段階では、どのプラグインが動かないかはまだ分かりません。検証環境で確認して初めて判明しますので、ここをどう扱うかを先に決めておく必要があります。取り決め方は3通りあります。

1. **上限を決めた追加作業として扱う**: 「修正が必要な場合は、着手前に見積もりを出し、承認後に作業する」と書いてもらう形です。想定外の請求を避けられます。
2. **一定の範囲までを含める**: 「軽微な修正はn時間まで作業範囲に含む」という形です。小さな修正のたびに承認を取るやり取りが省けます。
3. **機能をやめる判断も選択肢に入れる**: 使っていない機能のために修正費を払う必要はありません。洗い出しの段階で、現在使っていないプラグインを自社側で洗い出しておくと費用が下がります。

### 保守契約に含まれるか、別見積もりかの線引き

月額の保守契約を結んでいる場合、PHPの版を上げる作業が含まれるかどうかは契約によって異なります。契約書で次の2点を確認してください。

- 保守の対象が「サイトの維持」までか、「動作環境の更新」まで含むか
- 更新に伴う不具合の修正が、保守の範囲か別作業か

含まれていない場合でも、それは不当な請求ではありません。版の切り替えは定期的に発生する作業ですので、今回の見積もりを取る際に、次回以降を保守契約に含める形へ見直せるかも一緒に相談すると、同じやり取りを繰り返さずに済みます。

## 実装側でつまずきやすい点と、担当者が見るべき確認箇所

切り替え後に問題が出やすいのは、問い合わせフォームの送信、決済や外部連携、管理画面の拡張機能で、画面の表示が正常でも機能だけが止まることがあります。トップページを開いて問題なく見えたからといって、確認を終えてはいけません。

### 非推奨の警告が画面に出てしまうケース

新しいPHPでは、古い書き方が非推奨として扱われます。この警告が画面に表示される設定になっていると、サイトの上部や記事の途中に英語の文字列が出ることがあります。訪問者から見える形で出てしまうため、発見が遅れると印象に直接影響します。

実装側の注意点として、警告の表示を画面から消す設定だけで対応を終えると、原因はそのまま残ります。警告はログに記録して、原因となっている箇所を直すのが本来の対応です。見積もりを取る際に「非推奨の警告が出た場合、表示を止めるだけか、原因の修正まで行うか」を確認しておくと、この取り違えを防げます。

もう1つハマりやすいのが、キャッシュです。切り替え直後は、キャッシュのプラグインやサーバ側のキャッシュが古い状態を保持しているため、問題があっても見えないことがあります。確認の前にキャッシュを消してもらうよう依頼してください。

### フォーム送信と外部連携の確認

表示に出ない不具合が集まるのが、この部分です。次の箇所は、実際に動かして確認する必要があります。

- 問い合わせフォームからの送信と、通知メールの受信
- 予約や資料請求など、送信後に自動返信が届く仕組み
- 決済や外部サービスとの連携 (カート、予約システム、地図、SNSの表示など)
- 管理画面の拡張機能 (記事の入力画面、画像の一括処理、バックアップの自動実行など)
- サイト内検索と、絞り込みの機能

通知メールは、届かなくても画面上は送信完了と表示されることがあります。実際に受信箱を開いて確認してください。

### 切り替え後に自社で踏む確認手順のチェック表

制作会社の確認とは別に、自社でも次の順で確認します。所要時間は30分程度です。

1. トップページと主要な下層ページを表示する (スマートフォンでも確認します)
2. 問い合わせフォームからテスト送信し、通知メールの受信を確認する
3. 管理画面にログインし、記事を1件下書き保存して、画像を1枚アップロードする
4. 決済や予約の仕組みがある場合は、テスト用の手順で1件通す
5. サイト内検索で、結果が返ることを確認する

問題が見つかった場合は、切り戻すべき状態なのか、修正で対応できるのかを保守先に判断してもらいます。自社側で切り替えを戻そうとしないでください。

## 間に合わない場合の考え方と、次の期限への備え

年内に間に合わない場合も、作業の予定日を決めて記録し、暫定で何を止めるかを保守先と合意しておくことが、放置との差になります。期限を過ぎた瞬間にサイトが落ちるわけではありませんので、慌てて準備不足のまま切り替えるより、日程を決めて進めるほうが結果は安全です。

### 予定日を決めて記録に残す

間に合わないと分かった時点で、次の3つを文面で残します。

1. 作業を行う予定の月 (日付まで決まらなくても、月単位で決めます)
2. その日まで暫定で何をするか (プラグインの更新を止める、新しい機能の追加を見送る等)
3. 誰が進行を見るか (自社の担当者と、保守先の担当者の双方)

記録の形式は、メールのやり取りを残しておく程度でも十分です。重要なのは、次に誰かが見たときに「いつ対応する予定だったか」が分かる状態にしておくことです。

### 次の期限を保守契約の確認項目に入れる

PHPの版の期限は、PHP公式のSupported Versionsで公表されています。PHP 8.3のセキュリティサポートの終了日は2027年12月31日、8.4は2028年12月31日、8.5は2029年12月31日です。今回どの版に上げたかによって、次に同じ作業が必要になる時期が決まります。

| 今回上げた先 | 次の期限 |
|---|---|
| PHP 8.3 | 2027年12月31日 |
| PHP 8.4 | 2028年12月31日 |
| PHP 8.5 | 2029年12月31日 |

この日付を自社の年間予定に入れておくと、次は期限の半年前から動けます。保守契約を更新する際に、動作環境の更新を保守の範囲に含めるか、含めない場合は期限の半年前に見積もりを出してもらう取り決めを入れておくと、担当者が代わっても引き継がれます。

### リニューアルとまとめて実施する判断の目安

サイトの作り直しを検討している場合、PHPの版を上げる作業とまとめたほうが費用の無駄が少ないことがあります。目安は次のとおりです。

- **まとめたほうがよい場合**: リニューアルの実施が1年以内に決まっており、現在のサイトに大きな不具合が出ていない場合です。古いテーマの修正費が、作り直しで不要になります。
- **先にPHPだけ上げたほうがよい場合**: リニューアルの時期が未定か、1年より先になる場合です。期限の切れた状態を長く続けることになるため、切り離して進めます。
- **判断を保留してよい場合はありません**: どちらにしても、いつ何をするかを決めた記録だけは残してください。

サイトの作り直しそのものの進め方は本記事の範囲を超えますので、リニューアルの進め方を扱った記事をあわせてご覧ください。

## よくあるご質問

この記事に関して多い質問と回答をまとめます。

### PHP 8.2のサポートはいつ終わりますか

PHP公式のSupported Versionsによると、PHP 8.2のセキュリティサポートの終了日は2026年12月31日です。不具合の修正まで含むActive Supportは、2024年12月31日に終了しています。

### サポートが終わったPHPを使い続けると、サイトはすぐに止まりますか

期限を過ぎた時点でサイトの表示が止まるわけではありません。止まるのは、新たに見つかった問題に対する修正の供給です。IPAはサポート終了に関する注意喚起で、サポートが終了した製品では危険度の高い脆弱性が新たに見つかっても製品ベンダによる修正等の対応が期待できず、情報漏えいや意図しないサービス停止につながるおそれがあると説明しています。あわせて、レンタルサーバ側が古い版の提供を終了する場合は、その告知の期日にも従う必要があります。

### PHPの版を上げる作業は、保守契約の範囲に含まれますか

契約によって異なります。保守の対象が「サイトの維持」までなのか、「動作環境の更新」まで含むのかを契約書で確認してください。含まれていない場合は別見積もりになりますが、次回以降を保守の範囲に含める形へ見直せるかを、今回の依頼とあわせて相談すると、同じやり取りを繰り返さずに済みます。

### PHP 8.3と8.4のどちらに上げるべきですか

次の期限から逆算して選びます。PHP公式のSupported Versionsによると、8.3のセキュリティサポートの終了日は2027年12月31日、8.4は2028年12月31日です。WordPress公式の動作環境では推奨されるPHPのバージョンが8.3以上とされていますので、8.3でも要件は満たしますが、1年後にまた同じ作業が必要になります。プラグインの対応状況が許すなら、8.4以上を希望として伝えるほうが作業の回数が減ります。

### 古いプラグインが新しいPHPで動かない場合はどうなりますか

対応は3通りです。同じ機能を持つ別のプラグインへ差し替える、制作会社に修正してもらう、その機能そのものをやめる、のいずれかになります。どれを選ぶかは検証環境で確認して初めて判断できますので、見積もりの段階で「修正が必要になった場合は着手前に見積もりを出す」という取り決めを入れておくと、想定外の請求を避けられます。現在使っていないプラグインを自社側で洗い出しておくと、そもそも対応の対象が減ります。
