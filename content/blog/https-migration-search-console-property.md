# 常時SSL化後のSearch Console｜追加の要否

## 何から始めるか：自分のプロパティがどちらの種類か確認する

最初にやることは、Search Consoleで自社のプロパティがドメインプロパティかURLプレフィックスプロパティかを確認することです。これで追加が必要かどうかが決まります。

アドレス変更ツールを探す前に、ここを見てください。Google公式ドキュメントは、HTTPからHTTPSへの移行についてアドレス変更ツールは不要だと明記しています（出典: Google検索セントラル「URLの変更を伴うサイト移転」。2026年11月時点）。詳しくは次のセクションで扱います。

やるべきことは、プロパティの種類によって変わります。

| プロパティの種類 | HTTPS化のときにやること |
| --- | --- |
| ドメインプロパティ | 追加は不要。プロトコルがまとまるため、そのまま使えます |
| URLプレフィックスプロパティ | HTTPS用のプロパティを別に追加します |

### 画面での見分け方

Search Consoleの左上にあるプロパティの切り替えメニューを開いてください。表示されている名前で判別できます。

1. `example.com` のようにスキームが付いていない表示: ドメインプロパティです（所要時間の目安: 1分）
2. `https://example.com/` のように `http://` または `https://` から始まる表示: URLプレフィックスプロパティです（目安: 1分）

つまずきやすい点は、両方の種類を登録している御社があることです。過去の担当者がURLプレフィックスで登録し、後にドメインプロパティを追加した状態が残っていることがあります。この場合は、どちらでデータを見るかを先に決めてください。

### ドメインプロパティなら追加は不要です

Search Consoleヘルプは、ドメインプロパティを "A domain-level property that Includes all subdomains (m, www, and so on) and multiple protocols (http, https, ftp)." (すべてのサブドメインと複数のプロトコルを含むドメインレベルのプロパティ) と説明しています。さらに "A Domain property aggregates data for all subdomains, protocols, and subpaths of the property." (ドメインプロパティは、すべてのサブドメイン、プロトコル、サブパスのデータを集約します) とされています（出典: Search Consoleヘルプ「プロパティを追加する」。2026年11月時点）。

プロトコルが集約されるため、HTTPS化の前後でデータが途切れません。前後の比較を1つの画面で行いたい場合も、ドメインプロパティのほうが扱いやすくなります。

一方、URLプレフィックスプロパティだけで運用している場合は、HTTPS用のプロパティを追加しない限り、切り替え後のデータが入ってきません。この仕組みは次のセクションで扱います。

## アドレス変更ツールはHTTPS化では使いません

Google公式ドキュメントは、アドレス変更ツールが必要なのはドメインまたはサブドメインを別のものに移す場合だけで、HTTPからHTTPSへの移行では必要ないと明記しています。探して見つからないのではなく、使う場面ではありません。

### Google公式の記述

Google検索セントラルの「URLの変更を伴うサイト移転」は、アドレス変更ツールについて "You only need this tool when moving from one domain or subdomain to another" (ドメインまたはサブドメインを別のものに移す場合にのみ、このツールが必要です) とし、続けて "You don't need it for HTTP to HTTPS moves" (HTTPからHTTPSへの移行では必要ありません) と記しています（出典: Google検索セントラル「URLの変更を伴うサイト移転」。2026年11月時点）。

Search Consoleヘルプのアドレス変更ツールのページも、ツールを使用できないケースの一覧に "Changing address from http to https." (httpからhttpsへのアドレス変更) を挙げています。この場合については "Google will figure out your changes for you." (Googleが変更を自動的に検出します) とされています（出典: Search Consoleヘルプ「アドレス変更ツール」。2026年11月時点）。

申告しなくてよい理由は、リダイレクトで伝わるためです。恒久的なリダイレクトを設定しておけば、Googleが自力で新しいURLを認識します。

### ツールを使えないケースの一覧

同じ公式ドキュメントが、ツールが不要または使えないケースとして挙げているのは次の3つです。

1. HTTPからHTTPSへの移行
2. 同じドメイン内でのwwwありとwwwなしの切り替え。公式ヘルプは "use canonical tagging and/or redirects without using the change of address tool." (アドレス変更ツールを使わず、canonicalの指定かリダイレクトを使う) としています
3. 同じドメイン内でのパスの移動。"just add redirects, and update your sitemaps as appropriate." (リダイレクトを追加し、必要に応じてサイトマップを更新する) とされています

つまずきやすい点は、2のwwwありとwwwなしの切り替えをHTTPS化と同時に行う場合です。この組み合わせでもツールは使いませんが、プロパティの扱いは別で、wwwありとwwwなしは別のプロパティになります。詳しくは後述します。

### ツール自体の使用条件

HTTPS化では使わないツールですが、将来ドメインを変えるときに備えて条件を知っておくと判断が早くなります。公式ヘルプは次の3点を示しています。

1. "You must use the same Google account to manage both properties." (両方のプロパティを同じGoogleアカウントで管理する必要があります)
2. "The Change of Address tool can be used only on properties at the domain level" (アドレス変更ツールはドメインレベルのプロパティでのみ使用できます)
3. "The tool does not move any subdomains below the specified domain (including www)." (指定したドメインの下のサブドメインは、wwwを含めて移動しません)

2つ目の条件は、URLプレフィックスプロパティでは使えないという意味です。ドメインを変える予定がある御社は、この時点でドメインプロパティを登録しておくと手戻りがありません。

## URLプレフィックスプロパティはプロトコルごとに別になります

URLプレフィックスプロパティはプロトコルを含むため、httpとhttpsの両方を使う場合はプロトコルごとに別のプロパティを追加する必要があります。アドレス変更ツールが不要なことと、プロパティの追加が必要なことは両立します。

この2つを混同すると、「何もしなくてよい」と受け取って計測が止まります。申告は不要、器の追加は必要と覚えてください。

### 公式ヘルプの記述

Search Consoleヘルプの「プロパティを追加する」は、URLプレフィックスプロパティについて "Includes only URLs with the specified prefix, including the protocol (http/https)." (プロトコルを含む、指定した接頭辞を持つURLのみを含みます) と説明しています。

そのうえで "If your site supports multiple protocols (http and https), you must add a separate property for each protocol." (サイトが複数のプロトコルに対応している場合は、プロトコルごとに別のプロパティを追加する必要があります) と明記されています（出典: Search Consoleヘルプ「プロパティを追加する」。2026年11月時点）。

### 追加しないと起きること

HTTPS化した後、旧プロパティのデータは次のように変わります。

| 見ている画面 | 切り替え後に表示されるもの |
| --- | --- |
| `http://example.com/` のプロパティ | 新しいデータが入らず、表示回数とクリック数が減っていきます |
| `https://example.com/` のプロパティ（未登録） | そもそも画面がないため、データを見られません |

つまずきやすい点は、この状態を検索順位の下落と誤認することです。旧プロパティのグラフが落ちるのは、HTTPS側のデータが別の器に入っているためで、サイトの評価が落ちたわけではありません。

追加の手順は次のとおりです。

1. Search Consoleでプロパティを追加し、URLプレフィックスに `https://` から始まるURLを入力する（所要時間の目安: 5分）
2. 所有権を確認する（目安: 10分。旧プロパティと同じ方法が使えることが多いですが、HTMLファイルを置く方法の場合はファイルがHTTPS側にも存在するかを確かめてください）
3. サイトマップを新しいプロパティに送信する（目安: 5分）

### サブドメインも含まれません

同じヘルプは "Subdomains, such as m.example.com, are not included in this URL prefix." と記しており、URLプレフィックスプロパティにはサブドメインが含まれません。

これは、wwwありとwwwなしも別のプロパティになるという意味です。HTTPS化と同時にwwwの有無を変える場合、必要なプロパティは最大で4通り（httpのwwwあり、httpのwwwなし、httpsのwwwあり、httpsのwwwなし）になります。4つを管理したくない場合は、次のセクションで扱うドメインプロパティに切り替えるほうが実務的です。

## ドメインプロパティならプロトコルがまとまります

ドメインプロパティはすべてのサブドメインと複数のプロトコルのデータを集約するため、HTTPS化によるプロパティの追加自体が不要になります。前のセクションで挙げた4通りの管理も必要ありません。

### 公式ヘルプの記述

Search Consoleヘルプは、ドメインプロパティを "A domain-level property that Includes all subdomains (m, www, and so on) and multiple protocols (http, https, ftp)." (すべてのサブドメインと複数のプロトコルを含むドメインレベルのプロパティ) と説明しています。

データの扱いについては "A Domain property aggregates data for all subdomains, protocols, and subpaths of the property." (ドメインプロパティは、すべてのサブドメイン、プロトコル、サブパスのデータを集約します) とされています（出典: Search Consoleヘルプ「プロパティを追加する」。2026年11月時点）。

集約されるという点が、HTTPS化のときに効きます。切り替えの前後でグラフが途切れず、同じ画面で比較できます。

### これから登録する場合の選び方

これからSearch Consoleに登録する、またはプロパティを整理するなら、ドメインプロパティを選ぶほうが後の手間が減ります。理由は3つです。

1. HTTPS化でプロパティを足す必要がない（目安: 判断に1分）
2. wwwありとwwwなしが1つにまとまる
3. 将来ドメインを変えるとき、アドレス変更ツールがドメインレベルのプロパティでのみ使えるため、条件を満たした状態になる

ただし、すでにURLプレフィックスプロパティで数年分のデータが溜まっている場合は、過去のデータがドメインプロパティに移るわけではありません。ドメインプロパティは追加した時点から集約を始めます。古いデータを見たい間は、両方を残しておいてください。

### 所有権の確認方法が変わる点

実務でつまずくのはここです。ドメインプロパティの所有権確認は、DNSレコードの追加でのみ行います。HTMLファイルを置く方法やmetaタグを入れる方法は使えません。

DNSの設定は、ドメインを管理している事業者の画面で行います。制作会社にドメインを預けている御社では、自社だけで完結しません。手順は次のとおりです。

1. Search Consoleでドメインプロパティを追加し、表示されるTXTレコードの値をコピーする（所要時間の目安: 5分）
2. ドメインの管理者にTXTレコードの追加を依頼する（目安: 依頼から反映まで1営業日から数日。つまずきやすい点は、誰がドメインを管理しているか社内で分からない場合です。レコードを追加できる人を先に特定してください）
3. 反映後にSearch Consoleで確認を実行する（目安: 5分。DNSの反映には時間がかかるため、すぐに通らなくても数時間待ってから再試行します）

TXTレコードは、確認が通った後も消さないでください。消すと所有権の確認が外れます。

## HTTPS化の前後でやることを番号順に並べると

証明書の設定、恒久的なリダイレクトの設定、プロパティの追加、データの確認の順です。アドレス変更ツールはこの流れに入りません。

Google検索セントラルは、HTTPSへの移行について "For a move to HTTPS, get and configure the required TLS certificates on your server." (HTTPSへの移行では、サーバで必要なTLS証明書を取得して設定します) としています（出典: Google検索セントラル「URLの変更を伴うサイト移転」。2026年11月時点）。

### 番号付きの手順とつまずきやすい点

1. TLS証明書を取得してサーバに設定する（所要時間の目安: 設定は数十分。証明書の発行自体は利用するサービスによって即時から数日）
2. サイト内のリンクと画像の参照先をHTTPSに揃える（目安: 半日。つまずきやすい点は、本文中に直接書かれた `http://` から始まる画像のURLです。残っていると鍵のアイコンが出ません）
3. HTTPからHTTPSへの恒久的なリダイレクトを設定する（目安: 1時間）
4. Search Consoleでプロパティを確認し、URLプレフィックスプロパティの場合はHTTPS用を追加する（目安: 15分）
5. サイトマップを新しいプロパティに送信する（目安: 5分）
6. 数日間、インデックスの状況とクロールの様子を見る（目安: 1日1回5分）

6で急がないことが大切です。Google検索セントラルは、URLの変更を伴わないサイト移転について、公開直後はGooglebotのクロール率が一時的に下がることがあり、問題がなければ数日でまた上がるとしています（出典: Google検索セントラル「URLの変更を伴わないサイト移転」。2026年11月時点）。切り替えた当日の数字で判断しないでください。

サーバの移転を同時に行う場合は、DNSの準備も加わります。同ドキュメントは、移転の少なくとも1週間以上前にDNSのTTLを下げ始めることと、下げる値として数時間を例示しています。

### リダイレクトは301または308を使います

Google検索セントラルは、HTTPSへの移行で301や308などの恒久的なサーバ側リダイレクトを推奨しています。302などの一時的なリダイレクトは使いません。

リダイレクトをいつまで残すかも示されています。同ドキュメントは、URLの変更を伴う移転について、リダイレクトを1年以上維持するよう推奨しています。HTTPS化はURLが変わる移転に当たるため、HTTPからHTTPSへのリダイレクトも1年以上は外さないでください。

反映までの期間についても目安があります。同ドキュメントは、小中規模のサイトではほとんどのページが移転するまでに数週間かかるとし、Googlebotが移転を完了とみなすには旧URLと新URLを少なくとも1回ずつ訪問する必要があるとしています。

実装者としての注意点を1つ挙げます。リダイレクトをWordPressのプラグインで設定している御社は、プラグインを止めた瞬間にリダイレクトが消えます。サーバの設定ファイル側に書くか、プラグインを止めない運用ルールを決めてください。1年以上維持するという推奨は、プラグインの管理期間としては長い方です。

## 切り替えた後、どのプロパティでデータを見ますか

URLプレフィックスプロパティで運用している場合、切り替え前のデータは旧プロパティ、切り替え後のデータは新プロパティに入るため、前後の比較は2つの画面を並べて行います。1つの画面で続けて見ることはできません。

### プロパティごとに個別に確認します

Google検索セントラルは、サイト移転にあたってのプロパティの登録について "include both the HTTPS and HTTP site variants if you use HTTPS URLs." (HTTPS URLを使う場合は、HTTPS版とHTTP版の両方のバリエーションを含めてください) とし、"Verify data for each property separately in Search Console." (Search Consoleではプロパティごとに個別にデータを確認してください) としています（出典: Google検索セントラル「URLの変更を伴うサイト移転」。2026年11月時点）。

実務での見方は次のとおりです。

| 見たいもの | 開くプロパティ |
| --- | --- |
| 切り替え前の表示回数とクリック数 | `http://` のプロパティ |
| 切り替え後の表示回数とクリック数 | `https://` のプロパティ |
| 切り替え前後を続けて見る | ドメインプロパティ（登録している場合） |

つまずきやすい点は、旧プロパティにデータが残るため、消えたと思って削除してしまうことです。削除すると過去のデータが見られなくなります。

### 前後を1つの画面で見たい場合

ドメインプロパティを追加してください。ただし、追加した時点から集約が始まるため、過去にさかのぼって1つの画面にまとまるわけではありません。

当社の実装経験では、HTTPS化の作業そのものより、この「データが2つに分かれる」点の説明に時間がかかります。切り替えの前にドメインプロパティを登録しておけば、切り替えの前後が同じ画面に並びます。順番を逆にすると取り返せないため、HTTPS化を決めた時点で登録しておくことをお勧めします。

期間を指定して前後を比べる操作そのものは、Search Consoleの比較機能で行います。どの期間をどう取るかは、プロパティが分かれているかどうかとは別の話です。

### 制作会社に依頼するときの伝え方

HTTPS化を外注する場合、依頼の文面に次の3点を入れてください。計測が止まる事故は、ここが曖昧なまま進んだときに起きます。

1. HTTPからHTTPSへの恒久的なリダイレクト（301または308）を設定し、1年以上維持すること
2. Search ConsoleにHTTPS用のプロパティを追加し、サイトマップを送信すること（ドメインプロパティを使う場合はその旨を明記）
3. 作業後、旧プロパティを削除しないこと

3を書いていないと、整理のつもりで消されることがあります。過去のデータは戻りません。

## よくあるご質問

常時SSL化後のSearch Consoleについて多い質問をまとめます。

### 旧プロパティは削除してよいですか

削除しないでください。過去のデータが見られなくなります。

HTTPS化の後、`http://` のプロパティには新しいデータが入らなくなりますが、それまでに蓄積した表示回数、クリック数、検索クエリは残ります。Google検索セントラルも、HTTPS URLを使う場合はHTTPS版とHTTP版の両方のバリエーションを登録するよう求めています。整理したい気持ちは分かりますが、保存容量の問題ではないため、残しておく不利益はありません。

### HTTPS化で検索順位は上がりますか

順位への効き方について、今回参照したGoogle公式ドキュメントでは具体的な影響の大きさを確認できませんでした。確認できたのは、HTTPS化は移行の手順と計測の扱いが定められているという事実までです。

順位の変化を期待するよりも、HTTPSでないと表示される警告をなくすこと、そしてフォームの送信などで利用者に不安を与えないことを目的に置くほうが、判断がぶれません。

### wwwありとwwwなしも別のプロパティが必要ですか

URLプレフィックスプロパティでは必要です。Search Consoleヘルプは "Subdomains, such as m.example.com, are not included in this URL prefix." として、サブドメインが含まれないことを明記しています。

一方、ドメインプロパティはすべてのサブドメインを含むため、wwwありとwwwなしが1つにまとまります。両方を使い分けている御社は、ドメインプロパティのほうが管理が軽くなります。

なお、wwwありとwwwなしの統一にアドレス変更ツールは使いません。公式ヘルプは "use canonical tagging and/or redirects without using the change of address tool." としています。

### サイトマップは再送信が必要ですか

新しくプロパティを追加した場合は、そのプロパティにサイトマップを送信してください。プロパティごとに送信の状態が管理されるためです。

サイトマップの中身も確認してください。記載されているURLが `http://` のままだと、リダイレクトを経由することになります。HTTPS化のときに、サイトマップ内のURLもHTTPSに書き換えます。

### 切り替え後に表示回数が落ちたのは障害ですか

落ちた画面がどのプロパティかを先に確認してください。`http://` のプロパティであれば、データがHTTPS側に移っただけで、障害ではありません。

HTTPS側のプロパティでも落ちている場合は、様子を見る期間があります。Google検索セントラルは、公開直後はGooglebotのクロール率が一時的に下がることがあり、問題がなければ数日でまた上がるとしています。また、小中規模のサイトではほとんどのページが移転するまでに数週間かかるとされています。

数週間を過ぎても戻らない場合は、リダイレクトの設定、サイトマップのURL、`http://` から始まる内部リンクの残存を順に確認してください。
