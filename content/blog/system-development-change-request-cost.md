# システム開発の仕様変更｜追加費用の判断と手続

## 仕様変更で追加費用が出るのは、どんな場合？

当初の契約で定めた仕事の内容を超えるかどうかで分かれます。請負は完成を約する契約であるため、何を完成とするかが基準になります。

民法第632条は、請負を「当事者の一方がある仕事を完成することを約し、相手方がその仕事の結果に対してその報酬を支払うことを約することによって、その効力を生ずる。」と定めています。出典: e-Gov法令検索 民法（2026年10月時点）。

つまり、完成の内容は契約で決まります。その内容を動かせば、報酬の前提も動きます。追加費用の議論は、相場の話ではなく契約の範囲の話です。

### 契約の範囲の内か外か

判断の出発点は、変更後の内容が見積もりと要件定義書に書かれていたかどうかです。書かれていれば範囲の内、書かれていなければ範囲の外になります。

実務で境目になりやすい例を並べます。

| 変更の内容 | 追加費用が出やすいか |
|---|---|
| 要件定義書に無い機能を追加する | 出ます |
| 画面の項目を1つ増やす（帳票や連携にも波及する） | 出やすくなります |
| ボタンの文字や配色を変える | 出にくい（調整の範囲） |
| 要件定義書の記述が曖昧で、解釈が分かれた | 協議になります |
| 発注側が渡す原稿やデータの提出が遅れた | 作業の手戻り分で出ることがあります |

波及の範囲が見落としやすい点です。画面に項目を1つ足すだけでも、データベース、帳票、他システムとの連携まで直す必要があれば、作業量は見た目より増えます。

### 見積もりの前提条件が判断を分ける

曖昧さが残る場合に効いてくるのは、見積書に書かれた前提条件です。ここに数量や範囲が書かれていれば、範囲の内外を機械的に判断できます。

見積書で確認しておく前提を挙げます。

1. 画面数、帳票数、連携先の数
2. 対象とするデータの件数と、移行の対象期間
3. 対応する端末とブラウザ、対応する環境の範囲
4. 修正の回数の上限（デザインや文言の修正を何回まで含むか）
5. 発注側が用意するもの（原稿、画像、データ、テストの担当範囲）

当社の実装経験では、1番と4番が書かれていない見積書で、後から認識の違いが出ます。契約前に前提条件の記載を求めてください。

前提条件が書かれていない状態で変更の話になった場合は、どちらの責任かを争うよりも、増える作業の内訳を確かめる方が早く進みます。その見方は次に説明します。

## 提示された追加費用が妥当かは、どう確かめる？

金額の相場ではなく、変更によって増える作業の内訳で確かめます。工程ごとの工数と単価に分けた説明を求めてください。

仕様変更の追加費用に相場はありません。同じ変更でも、作りの構造によって増える作業量が変わります。比較の対象になるのは他社の金額ではなく、当初の見積もりの内訳です。

### 内訳の求め方

求めるものは3点です。増える作業、その工数、工数に掛ける単価です。合計額だけの提示を受けた場合は、この3点に分けた資料を依頼してください。

システム開発の見積書は一般に、開発費用、PM費、インフラ費、ライセンス費、保守費の5要素で構成されるとされています。追加費用も同じ区分で示してもらうと、当初の見積もりと並べて読めます。

| 確認する項目 | 見るポイント |
|---|---|
| 増える作業の範囲 | 画面、帳票、連携、テストのどこに波及するか |
| 工数 | 工程ごとの人日。設計とテストが含まれているか |
| 単価 | 当初の見積もりと同じ単価が使われているか |
| 影響する納期 | 延びる期間と、その理由 |
| 減る作業 | 入れ替えの変更なら、やめる機能の分が差し引かれているか |

最後の項目を忘れないでください。機能を入れ替える変更であれば、作らなくなった分の工数は減ります。加算だけが提示されている場合は、差し引きを求めてください。

### 見積もりの前提との差分の見方

当初の見積書の備考欄に書かれた前提条件が、確認の基準になります。見積書の備考欄に記載された前提条件、たとえば対応OSやブラウザのバージョン、開発体制、役割分担などを確認しておくことが、契約後の想定外の追加費用を防ぐうえで重要とされています。

差分を読む手順です。

1. 当初の見積書と要件定義書から、該当する箇所を抜き出す
2. 変更後の内容と並べ、何が増え、何が減るかを一覧にする
3. 増える作業が、当初の工数の何割に当たるかを計算する
4. 提示された金額を、その割合と突き合わせる
5. 説明がつかない差がある場合は、その工程の内訳を個別に確認する

3番の割合が役に立ちます。当初の実装工程が20人日で、変更で3人日増えるという説明であれば、金額も同じ比率に近いはずです。比率が大きくずれている場合は、単価か工程の数え方が変わっています。

契約方式の違いにも注意が必要です。IPAが2020年3月31日に公開した「情報システム・モデル取引・契約書（アジャイル開発版）」が前提とする準委任のアジャイル開発では、成果物の完成ではなくチームの稼働コストと期間で費用を見積もる方式が採られます。出典: 情報システム・モデル取引・契約書（アジャイル開発版）（IPA）。この方式では、変更は追加費用ではなく、期間内の優先順位の入れ替えとして扱われます。

御社の契約がどちらの方式かによって、確かめる対象が変わります。請負なら増える作業の内訳、準委任なら期間と体制が論点です。

## 受注側に費用を負担させる形は問題になる？

なります。中小受託取引適正化法は、責めに帰すべき理由がないのに給付の内容を変更させ、やり直させて利益を不当に害することを禁じています。

この法律は、従来の下請法が改正されたものです。改正法（令和7年5月23日法律第41号）の附則第一条は「この法律は、令和八年一月一日から施行する。」としており、法律名は「製造委託等に係る中小受託事業者に対する代金の支払の遅延等の防止に関する法律」になりました。出典: e-Gov法令検索 同法（2026年10月時点）。

適用されるかどうかは、発注側と受注側の資本金等の区分によります。適用の有無は同法の定義規定で確認してください。適用されない取引でも、考え方は交渉の目安になります。

### 禁止されている行為

同法第5条第2項第3号は、次の行為を挙げています。

> 中小受託事業者の責めに帰すべき理由がないのに、中小受託事業者の給付の内容を変更させ、又は中小受託事業者の給付を受領した後（役務提供委託又は特定運送委託の場合にあつては、中小受託事業者からその委託に係る役務の提供を受けた後）に給付をやり直させること。

同項の柱書は、これらの行為によって中小受託事業者の利益を不当に害してはならないと定めています。変更そのものが禁じられているのではなく、費用の手当てをしないまま変更ややり直しを求め、相手の利益を不当に害する形が対象です。

発注側が気をつけたい場面を挙げます。

1. 要件定義書に書いていなかった内容を、当然含まれるものとして無償で求める
2. 検収後に、仕様の解釈を変えてやり直しを求める
3. 納期を動かさないまま、作業量が増える変更を求める
4. 追加費用の請求を受けた後、金額を示さずに値引きだけを求める

3番は見落としやすい点です。期間を変えずに作業を増やせば、実質的に単価を下げたことになります。

### 協議に応じないことも禁止の対象

同法第5条第2項第4号は、協議そのものを求めています。

> 中小受託事業者の給付に関する費用の変動その他の事情が生じた場合において、中小受託事業者が製造委託等代金の額に関する協議を求めたにもかかわらず、当該協議に応じず、又は当該協議において中小受託事業者の求めた事項について必要な説明若しくは情報の提供をせず、一方的に製造委託等代金の額を決定すること。

つまり、費用が動いたときに協議の場を持ち、説明と情報の提供を行うことが条文上の求めになっています。追加費用の請求に納得できない場合も、無回答で済ませる形は取れません。

実務上は、次の対応が求めに沿う形になります。

| 相手方の求め | 発注側の対応 |
|---|---|
| 追加費用の協議の申し入れ | 日程を設けて応じる |
| 金額の根拠の説明の求め | 当初の見積もりとの差分の認識を示す |
| 判断の材料の提供の求め | 変更の背景と、優先度の判断を伝える |
| 金額の提示 | 認める部分と認めない部分を分けて回答する |

認めない場合も、理由を書面で残してください。協議の記録が、後の判断の根拠になります。

## 発注の時点で何を書面にしておく？

給付の内容と代金の額等は、発注時に書面または電磁的方法で明示する義務があります。内容が定まらない事項は、定まった後に直ちに明示します。

この義務は、中小受託取引適正化法第4条第1項に定められています。発注側に課される義務であり、後からの認識の違いを防ぐ仕組みでもあります。

### 明示する事項

条文は次のとおりです。出典: e-Gov法令検索 製造委託等に係る中小受託事業者に対する代金の支払の遅延等の防止に関する法律（2026年10月時点）。

> 委託事業者は、中小受託事業者に対し製造委託等をした場合は、直ちに、公正取引委員会規則で定めるところにより、中小受託事業者の給付の内容、製造委託等代金の額、支払期日及び支払方法その他の事項を、書面又は電磁的方法により中小受託事業者に対し明示しなければならない。

条文が挙げている事項を整理します。

| 明示する事項 | 仕様変更との関係 |
|---|---|
| 給付の内容 | 変更の前後で何が変わったかを示す基準になります |
| 代金の額 | 追加費用の差分を計算する起点になります |
| 支払期日 | 追加分の支払いの時期を決める前提になります |
| 支払方法 | 追加分を別の請求にするかの判断に関わります |

給付の内容が最も重要です。ここが「システム開発一式」と書かれているだけでは、変更の前後を比べる基準になりません。画面の数、機能の一覧、対象とするデータの範囲まで書いてください。

明示は書面でも電磁的方法でも構いません。同条第2項は、電磁的方法で明示した場合に相手方から書面の交付を求められたときは、遅滞なくこれを交付しなければならないとしています。

### 仕様が固まっていない場合の扱い

着手の時点で仕様が固まらないことはあります。条文もその場合を想定しています。

同法第4条第1項のただし書は、これらの事項のうちその内容が定められないことにつき正当な理由があるものについては明示を要しないものとし、この場合には、内容が定められた後直ちに、当該事項を書面または電磁的方法により明示しなければならないとしています。

実務に落とすと、次の進め方になります。

1. 発注時点で決まっている事項を明示する（決まっていない事項は保留と書く）
2. 保留とした事項について、いつ決めるかの期限を定める
3. 決まった時点で、直ちに追記した書面を交わす
4. 代金の額が変わる場合は、その時点で金額も明示する

2番の期限を置かないと、保留のまま実装が進みます。後から決めた内容が実装済みの部分と合わず、やり直しの費用が発生します。

当社の実装経験では、保留の項目を一覧にして期限を入れた表を作るだけで、変更の回数が目に見えて減ります。決まっていないことを決まっていないと書き、いつ決めるかを約束するのが、変更管理の出発点です。

変更が起きた後の手続は、次に説明します。

## 変更管理の手続は、契約書にどう書く？

変更の申し出から合意までの流れを、書面の様式と期限つきで定めます。協議するという一文だけでは、判断の根拠になりません。

変更管理とは、仕様を変えるときに、誰がどの様式で申し出て、何を確認し、いつまでに合意するかを決めた手続のことです。これが決まっていれば、変更のたびに交渉の形から考え直す必要がなくなります。

### 契約書に入れる条項

契約書に入れておく内容を、優先度の高い順に挙げます。

1. 変更を申し出られる当事者と、申し出の様式（変更要求書の提出）
2. 申し出を受けた側が、影響の調査結果を回答する期限（例: 5営業日）
3. 回答に含める事項（増減する作業、工数、金額、納期への影響）
4. 合意の方法（書面または電子メールでの相互の承諾をもって確定する）
5. 合意するまでの間、作業をどう進めるか（着手しない、または現行仕様で続ける）
6. 合意に至らない場合の扱い（当初の仕様で継続する、または協議を続ける）
7. 軽微な変更の扱い（金額と工数の影響が一定未満なら申し出を省略できる基準）

5番を書いていないと、合意前に作業が進みます。後から合意できなかった場合、その作業の費用の負担が争いになります。

7番の基準は、運用の負担を決める箇所です。文言の修正まで変更要求書を要求すると、手続が回らなくなります。影響の大きさで線を引いてください。

### 変更要求書の項目

様式は簡単なもので構いません。1枚に収める形で、次の項目を置きます。

| 項目 | 記載する内容 |
|---|---|
| 管理番号と日付 | 連番と、申し出た日 |
| 申し出た当事者 | 発注側か受注側か、担当者名 |
| 変更の内容 | 変更前と変更後を並べて書く |
| 変更の理由 | 業務上の必要、法令対応、解釈の相違など |
| 影響の調査結果 | 増減する作業、工数、金額、納期（受注側が記入） |
| 合意の有無と日付 | 双方の承諾の記録 |
| 当初契約との関係 | 契約金額を変更するか、別契約にするか |

変更前と変更後を並べて書く欄が要点です。変更後だけを書くと、何が変わったのかを後から追えません。

当社の実装経験では、この1枚を運用するだけで、追加費用の協議が短くなります。管理番号で過去の合意を参照できるため、同じ論点を繰り返さなくなるためです。

公的なひな型を参照する方法もあります。IPAは「情報システム・モデル取引・契約書 第二版」を2020年12月22日に公開しており、見直しの論点として請負契約・準委任契約における報酬請求権を挙げています。出典: 情報システム・モデル取引・契約書 第二版（IPA）。提示された契約書の変更に関する条項を、この標準例と比べて読む使い方ができます。

## 変更が多い案件は、契約の形を変えるべき？

仕様が固まらない工程は、完成を約さない形や工程を区切る形が向いています。IPAはアジャイル開発版のモデル契約も公開しています。

変更のたびに追加費用の協議が必要になるのは、1本の請負契約で最後まで縛っているからです。契約の形を変えると、変更が手続の対象から外れます。

### 工程で分ける考え方

工程ごとに契約を分けると、次の工程の見積もりを、前の工程の成果を見てから作れます。仕様が固まっていない段階で全体の金額を約束しないため、変更が追加費用にならずに済みます。

一般的な対応を整理します。

| 工程 | 向いている形態 | 変更の扱い |
|---|---|---|
| 要件定義 | 準委任 | 変更が前提の工程。追加費用になりません |
| 外部設計 | 準委任または請負 | 成果物の範囲を定義できるかで分かれます |
| 実装、内部設計 | 請負 | 仕様が確定しているため、変更は手続の対象になります |
| テスト、移行 | 請負または準委任 | 体制の提供が中心なら準委任になります |

要件定義を準委任で切り出すのが、最も効果の大きい分け方です。この工程での仕様の変更は、作業の方向を決める行為そのものであり、追加費用の対象になりません。

準委任を選ぶ場合は、民法上の報酬の考え方が請負と異なる点を押さえてください。準委任では既にした履行の割合に応じた報酬が基準になります。出典: e-Gov法令検索 民法（2026年10月時点）。期間と体制に対して支払う形になるため、成果物の完成を条件に支払いを止めることはできません。

### 変更を前提にした進め方の注意点

アジャイル開発を選ぶ方法もあります。IPAは2020年3月31日に「情報システム・モデル取引・契約書（アジャイル開発版）」を公開しており、準委任契約を前提としたアジャイル開発の外部委託を対象としています。出典: 情報システム・モデル取引・契約書（アジャイル開発版）（IPA）。

このモデル契約が前提とするアジャイル開発の準委任契約では、成果物の完成そのものではなく、チームの稼働コストと期間で費用を見積もる方式が採られます。変更は追加費用ではなく、期間内の優先順位の入れ替えとして扱われます。

ただし、発注側の負担は軽くなりません。注意点を挙げます。

1. 優先順位を決める役割を、発注側が担う必要があります
2. 期間内に全部が入るとは限りません。入らなかった分は次の期間に回ります
3. 総額が先に確定しないため、予算の管理は期間単位になります
4. 社内の稟議が総額を求める場合は、期間と体制の上限で説明する形になります

当社の実装経験では、1番が実質的な分かれ目です。週に1回、優先順位を判断できる担当者を置けるかどうかで、この形が機能するかが決まります。判断を任せきりにすると、作るものが発注側の意図から離れていきます。

請負と準委任のどちらが有利かという問いには、一般的な答えがありません。変更の頻度と、発注側が判断に関われる体制の2つで決めてください。

## 当社に相談できることは？

提示された追加費用の内訳の読み方から、変更管理を含む契約の形の設計までご相談いただけます。進行中の案件でも、発注前の段階でも承ります。

追加費用でつまずく案件に共通しているのは、金額の高さではありません。増える作業の内訳が示されず、妥当かどうかを発注側が判断できない状態です。

原因は、当初の見積書に前提条件が書かれていないことにあります。前提が無ければ差分を測れず、交渉は印象の応酬になります。

当社では、見積書と要件定義書を読んで差分を整理するところから始めます。ご相談いただける範囲は次のとおりです。

| 段階 | 当社の対応 |
|---|---|

なお、他社との金額の交渉を当社が代理することはありません。法的な代理も行いません。当社が担うのは、増える作業の内容を技術的に読み解き、妥当性の判断材料をお渡しする部分です。

進行中の案件でお困りの場合は、当初の見積書と変更の依頼内容をお手元に用意して[無料診断](/diagnostic)からお知らせください。どこまでが当初の範囲に含まれるかについて、技術的な見方をお伝えできます。

発注前の段階であれば、工程の区切り方から一緒に決められます。[料金ページ](/pricing)に基本の進め方を載せていますので、見積もりの依頼前にご確認ください。

## よくあるご質問

仕様変更と追加費用についてよく寄せられるご質問をまとめます。いずれも一般的な説明で、実際の扱いは御社の契約書と見積書の記載によります。

### 軽微な仕様変更でも追加費用を請求されますか。

契約書に軽微な変更の基準が書かれているかによります。基準が無ければ、金額の大小にかかわらず範囲外の変更として扱われ得ます。

文言や配色の修正であれば、修正の回数の範囲に収まることが多くあります。見積書に修正の回数の上限が書かれているかを確認してください。

### 見積もりに含まれていたはずの機能を追加費用と言われた場合はどうしますか。

見積書と要件定義書の該当箇所を示して、認識を突き合わせてください。記載があれば範囲の内です。

記載が曖昧で解釈が分かれる場合は、どちらの責任かを争う前に、増える作業の内訳の提示を求める方が早く進みます。中小受託取引適正化法第5条第2項第4号は、代金の額に関する協議の求めに応じ、必要な説明と情報の提供を行うことを求めています。出典: e-Gov法令検索 製造委託等に係る中小受託事業者に対する代金の支払の遅延等の防止に関する法律（2026年10月時点）。

### 仕様変更の合意はメールでも有効ですか。

契約書が書面を求めていなければ、メールでも合意の記録になります。中小受託取引適正化法第4条第1項も、明示の方法として書面または電磁的方法を認めています。

ただし、変更前と変更後の内容、金額、納期への影響の3点が本文に書かれている必要があります。了解しましたという返信だけでは、何に合意したのかを後から特定できません。

### 追加費用の金額に相場はありますか。

ありません。同じ変更でも、作りの構造によって増える作業量が変わるためです。

確かめる対象は、増える作業の範囲、工数、単価の3点です。当初の見積もりで使われた単価と同じ単価が適用されているか、設計とテストの工数が含まれているかを見てください。

### 仕様変更で納期が延びた場合、どちらが費用を負担しますか。

変更を求めた側と、変更の必要が生じた原因によって分かれます。発注側の都合による変更であれば、延びた期間に伴う費用は発注側の負担になるのが原則です。

注意したいのは、納期を動かさずに作業量が増える変更を求める形です。中小受託取引適正化法第5条第2項第3号は、責めに帰すべき理由がないのに給付の内容を変更させ、相手方の利益を不当に害することを禁じています。納期の据え置きは、実質的に単価を下げる形になり得ます。
