# システム開発の契約不適合責任｜通知期間の決め方

## 何から始めるか。契約書で期間がどう書かれているかを確認します

最初にやることは2つです。契約書に契約不適合責任の条項があるかを確認します。そのうえで、通知の期間が何か月または何年と書かれているかを見ます。書かれていない場合は、法律の原則で判断されます。

### 確認する条項名と見る箇所

条項の名前は契約書によって異なります。次の見出しがあれば、そこに書かれています。

| 条項名の例 | 見る内容 |
| --- | --- |
| 契約不適合責任 | 通知の期間、起算日、対応の範囲 |
| 瑕疵担保責任 | 古い契約書で使われている名称。内容は同趣旨のことが多い |
| 保証 | 保証期間と保証の対象 |
| 検査および検収 | 検収の合格条件と、合格後の扱い |

複数の条項に分かれて書かれていることもあります。4つすべてを読んでから判断してください。

あわせて、納品物の範囲が契約で特定されているかも確認します。何が納品物かが曖昧だと、不具合かどうかの判断もできません。契約の構成を確認する際は、IPAが公開している「情報システム・モデル取引・契約書」第二版が参考になります。2020年12月22日に公開され、最終更新日は2026年9月11日です。第二版では主な論点が5件見直されています (出典: IPA『情報システム・モデル取引・契約書』第二版)。

発注時の書面についても決まりがあります。取適法では、発注時に明示が必要な事項が11項目とされています。委託事業者には、書類または電磁的記録を2年間保存する義務もあります (出典: 公正取引委員会『委託事業者の義務』)。取適法は2026年1月1日に施行されました (出典: 公正取引委員会『2026年1月から「下請法」は「取適法」へ』)。

### 所要時間の目安とつまずきやすい点

発注側の作業として見込む時間は、次のとおりです。

1. **契約書の該当条項を探す。** 所要時間の目安は30分です。つまずきやすい点は、条項名が「瑕疵担保責任」のままになっていて見つけにくいことです。
2. **期間と起算日を読み取る。** 所要時間の目安は30分です。つまずきやすい点は、起算日が書かれておらず、いつから数えるかが分からないことです。
3. **納品物の範囲と突き合わせる。** 所要時間の目安は1時間です。つまずきやすい点は、納品物が「本件システム一式」としか書かれていないことです。

3つ目で範囲が特定できない場合は、次の契約から直してください。すでに納品を受けている案件については、仕様書と設計書を手がかりに範囲を確認することになります。

次の見出しで、検収と契約不適合責任の役割の違いを整理します。

## 検収と契約不適合責任は、役割が別です

検収は、納品物が契約の内容に合っているかを確かめる手続きです。契約不適合責任は、その後に不具合が見つかった場合の責任です。検収に合格したからといって、その後の責任がすべて消えるわけではありません。

### 検収で見るものと、後から出るものの違い

2つの違いは、確認できるタイミングにあります。

| 区分 | 確認する場面 | 見つかるものの性格 |
| --- | --- | --- |
| 検収 | 納品時に、決めた項目を確認する | 仕様書と照らして確かめられるもの |
| 契約不適合責任 | 検収の後、運用の中で見つかる | 一定の条件がそろったときにだけ現れるもの |

検収は、あらかじめ決めた項目を確認する手続きです。限られた時間で全部の組み合わせを試すことはできません。そのため、検収の範囲と、契約不適合責任の範囲は重なりません。

契約の構成を確認する際は、IPAの「情報システム・モデル取引・契約書」第二版が参考になります。納品物と検査の範囲を契約にどう書くかという考え方が整理されています (出典: IPA『情報システム・モデル取引・契約書』第二版)。

### 検収に合格した後に見つかる不具合の例

実際に後から出てくるものには、次のような傾向があります。

- 月末や年度末など、特定の時期にしか動かない処理の不具合。検収の期間に該当する日が含まれていなければ、確認できません。
- データ量が増えたときに現れる不具合。検収時のテストデータは、本番より件数が少ないことが一般的です。
- 特定の組み合わせでのみ発生する不具合。入力値の組み合わせをすべて試すことは現実的ではありません。
- 外部サービスとの連携で、相手側の応答が遅い場合や失敗した場合の処理。

1つ目は見落とされやすい項目です。検収を月初に行い、月末処理を確認しないまま合格とする例があります。この場合、最初の月末までは不具合が表に出ません。

こうした性格の不具合があるため、検収が終わった後にも一定の期間を設ける意味があります。では、その期間をどう決めるのか。次の見出しで、起算日と長さの考え方を整理します。

## 通知の期間は何を基準に決めるかを押さえます

通知の期間は、起算日と長さの2つで決まります。起算日を検収の完了日にするのか、引き渡しの日にするのかで、実質の長さが変わります。どちらも契約書で明示してください。

### 起算日の決め方

起算日の候補は3つあります。

| 起算日 | 特徴 |
| --- | --- |
| 引き渡しの日 | 物理的に受け取った日。検収に時間がかかる案件では、実質の期間が短くなります |
| 検収の完了日 | 合格の判定をした日。発注側から見て分かりやすい基準です |
| 本番稼働の開始日 | 実際に使い始めた日。検収後に稼働まで間が空く案件では、最も長くなります |

どれを選ぶかで、使いながら不具合を見つけられる期間が変わります。発注側としては、検収の完了日か本番稼働の開始日を基準にするほうが実態に合います。

起算日が書かれていない契約書は少なくありません。その場合、いつから数えるかで解釈が分かれます。次の契約から明示してください。

### 長さの決め方 (6か月・1年などの考え方)

長さは、業務の周期をどこまでカバーするかで考えると決めやすくなります。

1. **月次の処理までをカバーする。** 月末や月初の処理を1回から数回試せる長さです。短期間で区切る場合の下限の目安になります。
2. **四半期の処理までをカバーする。** 四半期ごとの集計や締めの処理がある業務で、1回は通る長さです。
3. **年次の処理までをカバーする。** 年度末の処理、年次の集計、年に1回しか動かない機能まで含める長さです。

対象のシステムに年次の処理があるなら、3つ目を選ぶのが実務に合います。逆に、日次の処理だけで構成されるシステムであれば、1つ目でも足ります。

長さを決めるときは、受注側の負担も考慮してください。長く設定するほど、受注側は見積もりにその分を織り込みます。期間だけを伸ばしても、費用に跳ね返れば意味がありません。

### 期間内に何をすれば通知したことになるか

ここが抜けやすい点です。期間内に「通知した」と言えるために、何をすればよいかを契約で決めておきます。

- 通知の方法。メール、書面、専用の管理ツールのいずれかを指定します。
- 通知の宛先。担当者個人ではなく、部署名やメールアドレスで指定します。
- 通知に書く内容。発生した事象、発生した日時、再現の手順の3点を最低限とします。

通知の方法を決めていないと、口頭で伝えたかどうかで争いになります。記録が残る方法を1つ指定してください。

次の見出しで、これらを契約書の文言としてどうそろえるかを整理します。

## 契約書への書き方は4つの要素でそろえます

起算日、期間の長さ、通知の方法、対象外とする事項の4つを書けば、後から争いになりにくくなります。どれか1つでも欠けると、解釈の幅が残ります。

### 4つの要素と書き方の順序

条項に入れる順序は、次のとおりです。

1. **起算日を書く。** 「検収完了の日から」のように、日付を特定できる表現にします。
2. **期間の長さを書く。** 「1年間」のように、単位と数を明示します。
3. **通知の方法を書く。** 「書面または電子メールにより」のように、記録が残る方法を指定します。あわせて宛先も書きます。
4. **対象外とする事項を書く。** 責任の範囲から外すものを列挙します。

4つ目を先に書くと、条項全体が制限の話に見えてしまいます。原則を先に、例外を後に置いてください。

### 対象外にする事項の決め方

受注側から、対象外とする事項の提案を受けることがあります。内容を見て判断してください。

| 対象外の候補 | 発注側から見た妥当性 |
| --- | --- |
| 発注側が指定した仕様どおりに作った結果の不具合 | 妥当。ただし、受注側が問題点を指摘していたかは確認します |
| 発注側が無断で変更した部分 | 妥当。変更の記録を残す運用が前提です |
| 発注側の運用環境の変更に起因するもの | 妥当。どこまでが運用環境かを定義します |
| 第三者のソフトウェアに起因するもの | 内容による。選定した側がどちらかで変わります |
| 発注側が通知を怠った結果、拡大した損害 | 妥当。通知の方法が明確である前提です |

4つ目は慎重に見てください。受注側が選んだ部品に起因するものまで一律に対象外とする文言であれば、範囲を狭めるよう交渉する余地があります。

### 参照できる公的なひな型

条文をゼロから作る必要はありません。IPAが公開している「情報システム・モデル取引・契約書」第二版が参照できます。2020年12月22日に公開され、最終更新日は2026年9月11日です。受託開発と保守運用を対象とした本文、逐条解説、ひな型がWord形式で配布されています (出典: IPA『情報システム・モデル取引・契約書』第二版)。

このひな型は、納品物と検査の範囲を契約にどう書くかの考え方も含んでいます。契約不適合責任の条項だけを単独で直すのではなく、納品物の定義と検収の条項とあわせて見直してください。

実際の条文は、案件の性質と社内の方針に合わせて調整が必要です。顧問の専門家に確認する前提で進めてください。

## 不具合が見つかったときの進め方は5つのステップです

事象の記録、再現の確認、通知、対応範囲の合意、完了の確認という5つの順で進めます。最初の2つを飛ばして連絡すると、原因の切り分けに時間がかかります。

### ステップ1から5までの流れ

1. **事象を記録する。** 発生した日時、操作した内容、表示された画面、入力したデータの条件を記録します。画面の画像も残します。
2. **再現を確認する。** 同じ手順でもう一度起きるかを試します。起きない場合は、起きた条件を絞り込みます。
3. **通知する。** 契約で決めた方法と宛先へ、記録した内容を添えて連絡します。通知した日付が後で意味を持ちます。
4. **対応範囲を合意する。** 契約不適合責任で直すのか、保守の範囲か、別途の見積もりかを確認します。
5. **完了を確認する。** 修正後に、同じ手順で起きないことを確かめます。他の機能に影響が出ていないかも見ます。

ステップ3で、期間の終わりが近い場合は先に通知してください。再現の確認が終わっていなくても、事象を記録した時点で連絡する判断があります。

### 各ステップの所要時間の目安とつまずきやすい点

| ステップ | 所要時間の目安 | つまずきやすい点 |
| --- | --- | --- |
| 1. 事象の記録 | 発生時に15分から30分 | 気づいた人が記録せず、後から思い出せない |
| 2. 再現の確認 | 30分から半日 | 本番環境で試してしまい、データが変わる |
| 3. 通知 | 30分 | 担当者個人の携帯に電話して記録が残らない |
| 4. 対応範囲の合意 | 数日から2週間 | どちらの費用かの協議が長引く |
| 5. 完了の確認 | 半日から1日 | 直った箇所だけを見て、影響範囲を確認しない |

2つ目について補足します。再現の確認は、可能であれば検証用の環境で行ってください。本番環境で試すと、データが書き換わって元の状態に戻せなくなることがあります。

### 実装者視点の注意点 (運用環境の変更との切り分け)

手を動かす側から見て、判断が分かれやすいのがここです。システムそのものは変わっていなくても、周りの環境が変わって動かなくなることがあります。

- ブラウザやOSが自動で更新された。
- 連携先の外部サービスの仕様が変わった。
- ネットワークの設定や証明書が更新された。
- 社内で使うソフトのバージョンが上がった。

これらは契約不適合とは性格が異なります。納品時には正しく動いていたためです。通知の前に、次の2点を確認しておくと切り分けが早くなります。

1. いつから起きているか。ある日を境に起きるようになった場合は、環境の変更を疑います。
2. 他の端末でも起きるか。特定の端末だけで起きる場合は、その端末の設定を確認します。

この確認をしてから通知すると、受注側の調査も早く進みます。環境の変更に起因するものが対象外とされているかは、前の見出しで触れた契約の条項で決まります。

## 保守契約との役割分担を決めておきます

契約不適合責任で直すものと、保守契約で対応するものを分けておきます。分けていないと、不具合が出るたびにどちらの費用で対応するかの協議が発生します。

### 契約不適合責任と保守の線引き

2つは目的が異なります。整理すると、次のようになります。

| 区分 | 対象 | 費用 |
| --- | --- | --- |
| 契約不適合責任 | 納品時点で契約の内容に合っていなかった部分 | 受注側が負担する前提 |
| 保守契約 | 稼働後の運用支援、環境の変化への追随、軽微な改善 | 保守料に含まれるか、別途見積もり |

線引きの基準は「納品の時点でどうだったか」です。納品時点で仕様と違っていたなら前者、納品後の変化への対応なら後者になります。

ただし、実際には判断が分かれる場面があります。前の見出しで触れた環境の変更に起因するものが典型です。次の3点を契約で決めておくと、協議が短くなります。

1. 判断に迷う場合の扱い。まず調査を行い、調査の結果で区分を決める、といった手順を書きます。
2. 調査そのものの費用。どちらが負担するかを決めます。原因が契約不適合だった場合は受注側、そうでなければ発注側、という分け方があります。
3. 緊急時の対応。業務が止まる不具合は、区分の決定を待たずに先に復旧する、という順序を決めます。

3つ目は実務上とくに重要です。区分の協議を先にすると、復旧が遅れます。

納品物の範囲が契約で特定されていることが、この線引きの前提になります。何が納品物かが曖昧であれば、どちらの区分かも決められません。契約の構成については、IPAの「情報システム・モデル取引・契約書」第二版が参考になります (出典: IPA『情報システム・モデル取引・契約書』第二版)。

### 見積もりの段階で確認すること

保守の見積もりを受け取ったら、次の点を確認してください。

- 契約不適合責任の期間中に、保守料が発生するのか。期間が重なる場合の扱いを確認します。
- 保守に含まれる作業の範囲。障害対応だけか、問い合わせへの回答も含むかを確認します。
- 対応の時間帯と連絡方法。業務時間外に不具合が出た場合の扱いを確認します。

1つ目は見落とされやすい点です。契約不適合責任の期間と保守期間が重なっていると、同じ不具合に対して二重に費用が発生していないかを確認する必要があります。

契約の条文と見積もりの内訳は、分けて読まずに突き合わせてください。当社 (株式会社ノーティックラボ) でも、システム開発の発注にあたって契約条件と保守の範囲を整理する段階からのご相談を承っています。

## よくあるご質問

この記事に関して多い質問と回答をまとめます。

### 納品後に不具合が見つかった場合、いつまでに言えば直してもらえますか

契約書に定めた期間内です。多くの契約では、起算日と期間の長さが条項に書かれています。まず契約書の契約不適合責任の条項を確認してください。条項に定めがない場合は法律の原則で判断されるため、顧問の専門家に確認することをおすすめします。

### 検収に合格した後でも、不具合の修正を求められますか

検収と契約不適合責任は役割が別です。検収はあらかじめ決めた項目を確認する手続きで、限られた時間ですべての組み合わせを試すことはできません。月末処理のように特定の時期にしか動かない機能や、データ量が増えたときに現れる不具合は、検収の後に見つかります。契約で定めた期間内であれば、通知の対象になります。

### 通知の期間は契約書に書かれていない場合どうなりますか

法律の原則で判断されます。実務では、解釈が分かれて協議が長引くことがあります。次の契約からは、起算日と期間の長さを明示してください。起算日は、引き渡しの日、検収の完了日、本番稼働の開始日のいずれかを特定できる形で書きます。

### 通知はメールでもよいのですか

契約で定めた方法によります。「書面または電子メールにより」のように、記録が残る方法を契約で指定しておくことをおすすめします。あわせて宛先も、担当者個人ではなく部署名やメールアドレスで指定してください。口頭だけで伝えると、通知したかどうかで争いになります。

### 契約不適合責任と保守契約の違いは何ですか

対象になるものが違います。契約不適合責任は、納品の時点で契約の内容に合っていなかった部分が対象です。保守契約は、稼働後の運用支援、環境の変化への追随、軽微な改善が対象です。線引きの基準は「納品の時点でどうだったか」です。判断に迷う場合の扱いと、調査費用の負担を契約で決めておくと、協議が短くなります。
