# リニューアル公開後の再クロール｜待つ期間と操作

## 公開後にサイトマップを送り直す必要は？

URLが変わる移転をした場合は、新しいサイトマップを用意して送信します。URLが変わらない場合は、更新日の反映だけで足ります。

分岐はこの1点だけです。リニューアルでページのアドレスが変わったかどうかを、先に確認してください。

Googleはサイト移転を、URLの変更を伴う場合と伴わない場合に分けて説明しています。必要な操作も、この区分で変わります。

### URLが変わる移転の場合

旧URLから新URLへ対応付けが発生するため、送信するサイトマップも新しくなります。進め方は次のとおりです。

1. 新しいURLだけを収めたサイトマップを用意します。
   つまずきやすい点: 旧URLが残ったままのサイトマップを送ると、転送先と転送元が混在します。
2. Search Consoleの新しいサイトのプロパティから送信します。
3. 旧URLのサイトマップは、転送が有効なうちは残しておきます。
   つまずきやすい点: すぐ削除すると、Googlebotが旧URLを再訪する手がかりが減ります。

Google検索セントラル「URLの変更を伴うサイト移転」によると、Googlebotが移転の完了を認識するには、新旧両サイトの各URLへ1回以上アクセスする必要があります。旧側を消さずに残す理由はここにあります。

同ガイドは、小規模から中規模のサイトではすべてのURLを一度に移転することを推奨しています。分割すると、認識が完了するまでの期間が延びます。

### URLが変わらない移転の場合

デザインやサーバだけを変えてアドレスが同じなら、サイトマップの中身は変わりません。この場合にやることは2つです。

| 作業 | 必要性 |
|---|---|
| サイトマップの再送信 | 不要です。内容が同じであれば送り直す意味がありません |
| サイトマップ内の更新日の反映 | 必要です。更新したページの日付が新しくなっているか確認します |

更新日が古いまま出力される設定になっていると、更新を知らせる手がかりが弱くなります。公開後に1度、サイトマップの中身を開いて日付を確認してください。所要時間の目安は10分程度です。

実装の側から1点補足します。URLが変わらない移転でも、サーバを移す場合はDNSの切り替えが絡みます。同ガイドは、URLを変えない移転ではDNSのTTLを1週間以上前に下げておくとしています。公開後の作業ではなく、公開前に済ませる準備です。

どちらの移転でも、送信した後は待つ時間が必要です。期間の目安は後述します。

## 公開直後にやる操作の順番は？

転送の確認、サイトマップの送信、主要ページの登録依頼の順に進めます。アドレス変更ツールが必要かは移転の種類で変わります。

順番に意味があります。転送が正しく動いていない状態でサイトマップを送っても、転送先が確定しません。

公開当日に全部を終える必要はありません。当日に必要なのは、転送の確認までです。

### 公開当日に行う操作

1. 主要な旧URLをブラウザで開き、新URLへ転送されるか確認します。所要時間の目安は30分程度です。
   つまずきやすい点: トップページだけ確認して終わる例が多く、下層ページの対応付けが抜けます。
2. 転送が多段になっていないか確認します。
   つまずきやすい点: 旧サイトの内部で一度転送してから新URLへ送る構成になっていることがあります。
3. 新しいサイトマップを送信します。
4. 主要ページのURLを、個別に登録を依頼します。

Google検索セントラル「URLの変更を伴うサイト移転」によると、推奨されるリダイレクトチェーンの長さは5未満で、理想は3以下です。Googlebotがたどれる上限は10ホップとされています。

2番目の確認はここに関わります。上限に達していなくても、多段になるほど処理は不利になります。実装の側では、公開直後に転送の段数を1つずつ数える作業を必ず入れています。

### アドレス変更ツールが必要な場合

アドレス変更ツールは、常に使うものではありません。移転の種類で分かれます。

| 移転の種類 | アドレス変更ツール |
|---|---|
| ドメインが変わる移転 | 使います |
| 同じドメイン内でURLの構造が変わる移転 | 使いません |
| HTTPからHTTPSへの変更 | 不要です |
| URLが変わらない移転 | 使いません |

Google検索セントラルは、アドレス変更ツールがHTTPからHTTPSでは不要であるとしています。常時SSL化に伴う作業と、ドメイン移転の作業を混同しないでください。

### Search Consoleのプロパティの扱い

プロパティを作り直すかどうかも、同じ資料で判断できます。

同ガイドによると、URLプレフィックスプロパティはプロトコルごとに別のものとして扱われ、ドメインプロパティはプロトコルを集約します。HTTPSへ切り替えた場合、URLプレフィックスで登録していたならHTTPS側の登録が別に必要です。

| 登録の形 | HTTPSへの切り替え後 |
|---|---|
| URLプレフィックスプロパティ | HTTPS側のプロパティを追加します |
| ドメインプロパティ | 追加は不要です。プロトコルは集約されます |

ドメインが変わる移転の場合は、新ドメインのプロパティを新たに登録します。旧ドメインのプロパティは、転送の状況を確認するために残しておいてください。

## クロールされ直すまでどれくらい待ちますか？

Googleは移転の反映に数週間かかるとしています。リダイレクトは1年以上維持することが推奨されています。

待つ期間と、転送を残す期間は別の話です。反映が終わっても、転送はさらに長く残します。

公開から1日や2日で結論を出さないでください。期間の根拠を示します。

### 反映の期間の目安

Google検索セントラル「URLの変更を伴うサイト移転」によると、中規模のサイトでは大半のページの移転が反映されるまでに数週間かかります。

| 項目 | 公式の記述 |
|---|---|
| 大半のページの移転が反映されるまで | 数週間 |
| Googlebotが移転の完了を認識するためのアクセス | 新旧両サイトの各URLへ1回以上 |
| 推奨される移転の分け方（小規模から中規模） | すべてのURLを一度に移転する |

2行目が待ち時間の実体です。Googlebotが旧URLと新URLの両方を訪れるまでは、移転が終わったと認識されません。ページ数が多ければ、それだけ時間がかかります。

3行目の一括移転が推奨される理由も同じです。分割すると、認識が完了するまでの期間が延びます。

### リダイレクトを外してよい時期

反映が終わったように見えても、転送はすぐに外さないでください。

同ガイドは、サイト移転後にリダイレクトを保持する期間として1年以上を案内しています。理由は2つあります。

1. 検索結果以外から旧URLへ来る経路が残っているためです。
   他社サイトからのリンク、メールの署名、印刷物のURLなどが対象です。
2. 訪問の頻度が低いページは、Googlebotの再訪も遅れるためです。
   つまずきやすい点: 主要ページの反映を見て全体が終わったと判断すると、下層ページの転送を早く外してしまいます。

実装の側から言うと、1年という期間はサーバの契約にも関わります。旧ドメインや旧サーバを維持する費用が、その期間ぶん発生します。リニューアルの見積もりを取る段階で、旧環境をいつまで残すかを決めておいてください。旧サーバの解約時期の判断は、別の記事で詳しく触れています。

転送を外す場合も、一斉にではなく、流入が残っているURLを確認してから進めます。Search Consoleで旧URLへのアクセスが続いているかを見れば判断できます。

## 待っている間に数値が落ちるのは正常ですか？

移転の直後に数値が動くこと自体は想定の範囲です。経過か異常かは、転送の設定とインデックスの状況を見て切り分けます。

判断の軸は「新URLが認識されつつあるか」です。認識が進んでいる途中なら経過、進んでいないなら異常として扱います。

Googleは中規模のサイトで大半のページの反映に数週間かかるとしています。この期間内の変動は、それだけでは異常の根拠になりません。

### 経過として説明できる動き

次の動きは、反映の途中として説明できます。

| 観察される動き | 経過としての説明 |
|---|---|
| 新URLの表示回数が少しずつ増えている | 認識が進んでいます |
| 旧URLの表示回数が少しずつ減っている | 置き換わりが進んでいます |
| 新旧が両方表示されている期間がある | 両方を訪れて認識する過程です |
| 下層ページの反映が主要ページより遅い | 訪問の頻度の差によるものです |

1行目と2行目が同時に起きているなら、置き換わりが進んでいます。合計で見れば一時的に下がっても、方向は正常です。

4行目は特に焦りやすい箇所です。主要ページが戻っているのに下層が戻らない状態は、よく起きます。

### 異常として扱う動き

一方、次の動きは経過では説明できません。待たずに確認してください。

1. 新URLが1件もインデックスされていない
   つまずきやすい点: サイトマップを送っていない、またはnoindexが残っている可能性があります。
2. 旧URLの表示回数が減らず、新URLも増えない
   転送が動いていない可能性があります。
3. 旧URLを開くと転送されずに旧ページが表示される
   転送の設定が反映されていない状態です。
4. 新URLを開くとエラ画面が出る
   公開作業そのものが途中で止まっています。
5. 新旧の両方が同じ内容で長期間表示され続ける
   転送ではなく複製の状態になっている可能性があります。

1番目と5番目は、実装の側で実際に多く見かける状態です。テスト環境の設定がそのまま本番に残り、noindexが付いたまま公開されている例があります。公開直後にインデックスの状況を1度確認しておけば、数週間待たずに気づけます。

数値の動きそのものより、転送が動いているかを先に見てください。転送が正しければ、あとは待つ時間の問題になります。原因の切り分けの詳しい手順は、順位が下がった場合を扱った別の記事で触れています。

## アップデートと重なった場合はどう見ますか？

Googleのランキング更新の記録と自社の公開日を並べて確認します。コアアップデートの展開には所要期間があり、完了後に待つ期間も示されています。

リニューアルの直後にコアアップデートが重なると、原因が2つになります。切り分けには、公式の記録を使います。

記録は日付と所要期間で公開されています。自社の公開日が展開期間に入っていたかを見ます。

### 公開日と更新履歴の照合

Google Search Status Dashboardのランキング更新の履歴によると、近年のコアアップデートの所要期間は次のとおりです。

| アップデート | 所要期間 |
|---|---|
| 2024年3月（記録のうち最も長い例） | 45日 |
| 2024年11月 | 23日13時間 |
| 2025年12月 | 18日2時間 |
| 2026年3月 | 12日4時間 |
| 2026年5月 | 11日21時間 |
| 2024年12月（記録のうち短い例） | 6日4時間 |

直近では、2026年11月のコアアップデートが2026年11月10日に展開を開始しています。出典はいずれもGoogle Search Status Dashboard ランキング更新の履歴です。

照合の手順は次のとおりです。所要時間の目安は30分程度です。

1. 自社のリニューアル公開日を確認します。
2. 履歴で、公開日の前後に展開期間が重なるアップデートがあるかを調べます。
3. 重なっていた場合、数値の変動を移転だけに帰することはできません。
4. 重なっていない場合、移転の経過として見ます。

つまずきやすい点は、アップデートの「開始日」だけを見ることです。展開には6日から45日の幅があるため、開始日が公開日より前でも、期間が重なっていることがあります。

### 判断を保留する期間

重なっていた場合、いつ判断するかも公式に示されています。

Google検索セントラル「Google検索のコアアップデートとウェブサイト」によると、コアアップデートの完了後、Search Consoleで分析を始める前に1週間以上待つことが推奨されています。

つまり、重なっていた場合に見る時期は次のようになります。

| 状況 | 分析を始める時期 |
|---|---|
| アップデートが重なっていない | 移転の反映を待つ数週間後 |
| 展開中 | 完了を待ちます |
| 完了済み | 完了から1週間以上後 |

実装の側から言うと、この期間は社内の説明で効きます。公開直後に数値が落ちると「リニューアルが失敗した」と見られがちですが、公式に待つ期間が示されていれば、いつ判断するかを先に合意できます。公開前にこの期間を共有しておくと、途中で手を入れる判断を避けられます。

更新履歴との照合そのものの手順は、アップデートの確認方法を扱った別の記事で詳しく触れています。

## いつまで待っても戻らない場合の確認は？

転送の対応付け、旧URLの扱い、サイトマップの内容の3点を順に確認します。多くは転送の設定に原因があります。

数週間待って新URLのインデックスが進まない場合、待ち時間の問題ではありません。設定のどこかが止まっています。

順序に意味があります。上から確認すると、下の確認が不要になることがあります。

### 確認する3点と順序

1. 転送の対応付けを確認します。所要時間の目安は、ページ数が数十なら1時間程度です。
   旧URLの一覧を用意し、1件ずつ開いて転送先が正しいかを見ます。
   つまずきやすい点: 全てトップページへ転送されている設定になっている例が最も多く見られます。
2. 旧URLの扱いを確認します。所要時間の目安は30分程度です。
   転送ではなく、旧ページがそのまま表示されていないかを見ます。
   つまずきやすい点: 旧サーバが生きていると、DNSの切り替え前のキャッシュで旧ページが見えることがあります。
3. サイトマップの内容を確認します。所要時間の目安は30分程度です。
   送信したサイトマップを開き、新URLだけが入っているかを見ます。
   つまずきやすい点: 旧URLが残っている場合、転送元と転送先が同じ一覧に並びます。
4. 新URLにnoindexが残っていないかを確認します。
   つまずきやすい点: テスト環境の設定が本番に残る例があり、この場合は転送が正しくてもインデックスされません。

4番目は実装の側で最も多く見かける原因です。転送の設定を疑って時間を使った結果、noindexが1行残っていただけという例があります。1と4を先に見ると早く済みます。

### 制作会社に依頼する範囲

確認の結果によって、依頼する内容が変わります。

| 確認結果 | 依頼する内容 |
|---|---|
| 転送先が一律トップページ | ページ単位の対応付けへの修正 |
| 転送が多段になっている | 1段で新URLへ送る設定への修正 |
| 旧ページがそのまま表示される | 転送設定の反映と旧サーバの扱いの確認 |
| サイトマップに旧URLが混在 | 新URLのみのサイトマップの再出力 |
| noindexが残っている | 該当ページの設定の削除 |

依頼するときは、確認した旧URLと実際の転送先を一覧で渡してください。症状だけを伝えると、調査からやり直しになります。

修正が公開されても、すぐには戻りません。Googleは中規模のサイトで大半のページの反映に数週間かかるとしており、修正後も同じだけ待つ期間が必要です。修正した日を記録しておき、そこから数えてください。

転送の設定方法そのものは、301リダイレクトを扱った別の記事で詳しく触れています。

## 公開前にやっておくと楽になることは？

旧URLと新URLの対応表、公開前の数値の記録、サイトマップの事前作成の3つです。公開後の確認がそのまま進みます。

公開後に困る原因の多くは、比べる材料がないことです。公開前の状態を記録していないと、変動の大きさも判断できません。

いずれも公開の直前に用意できます。制作会社に依頼するものではなく、発注側で持つ資料です。

### 公開前に用意する3点

1. 旧URLと新URLの対応表を作ります。所要時間の目安は、ページ数が数十なら2時間程度です。
   つまずきやすい点: 統合して無くなるページは、転送先をどこにするかを決めて表に書いておきます。
2. 公開前の数値を記録します。所要時間の目安は1時間程度です。
   主要ページの表示回数と平均掲載順位を、期間を明記して保存します。
   つまずきやすい点: 画面を見るだけでは後から比べられないため、書き出して保存してください。
3. 新URLのサイトマップを事前に作っておきます。所要時間の目安は30分程度です。
   つまずきやすい点: 公開当日に作ると、旧URLが混在したまま送ってしまう事故が起きます。
4. DNSのTTLを事前に下げます。
   Google検索セントラル「URLの変更を伴わないサイト移転」は、DNSのTTLを1週間以上前に下げておくとしています。

1番目の対応表は、公開後の確認でそのまま使えます。転送が正しいかを1件ずつ見る作業は、この表がないと始められません。

4番目は、サーバを移す場合に必要な準備です。公開の1週間以上前に手を付けます。

### 次回のリニューアルに残す記録

今回の公開で記録しておくと、次回が楽になるものがあります。

| 残す記録 | 次回の使い道 |
|---|---|
| 公開日と、反映が落ち着いた日 | 次回に待つ期間の見込みが立ちます |
| 転送の修正が必要だった箇所 | 同じ設定の誤りを事前に確認できます |
| 公開前後の数値と期間 | 変動の幅が自社の実績として残ります |
| アップデートと重なったかどうか | 変動の原因を後から説明できます |

実装の側から言うと、1行目が最も価値があります。公式の案内は数週間という幅ですが、自社のサイトで実際にどれだけかかったかを1度記録しておけば、次回は社内への説明が具体的になります。

リニューアルは、公開して終わる作業ではありません。公開後の数週間が、設定の誤りを見つける唯一の機会になります。当社ではリニューアルの公開後も、転送の確認とインデックスの状況を見る期間までを作業範囲に含めています。公開後の確認を自社だけで進めるのが不安な場合は、[無料診断](/diagnostic)からご相談ください。

## 公開後の再クロールに関するよくある質問

公開直後に問い合わせの多い5点をまとめます。

### サイトマップはどのタイミングで送り直せばよいですか？

URLが変わる移転なら、転送の確認が済んだ後に送ります。新URLだけを収めたサイトマップを用意し、新しいサイトのプロパティから送信します。

URLが変わらない移転では、再送信は不要です。更新したページの日付が新しくなっているかだけを確認してください。

### リダイレクトはいつまで残す必要がありますか？

Google検索セントラル「URLの変更を伴うサイト移転」は、サイト移転後にリダイレクトを保持する期間として1年以上を案内しています。

検索結果以外から旧URLへ来る経路が残るためです。他社サイトからのリンクや、印刷物に載ったURLが対象になります。旧ドメインや旧サーバの維持費は、この期間ぶん見込んでおいてください。

### 公開後1週間で順位が戻らないのは異常ですか？

異常とは言えません。同ガイドは、中規模のサイトで大半のページの移転が反映されるまでに数週間かかるとしています。

Googlebotが移転の完了を認識するには、新旧両サイトの各URLへ1回以上アクセスする必要があります。新URLのインデックスが少しずつ増え、旧URLが減っているなら、置き換わりは進んでいます。

ただし新URLが1件もインデックスされていない場合は、待つ前に転送とnoindexの設定を確認してください。

### アドレス変更ツールは必ず使う必要がありますか？

移転の種類で変わります。ドメインが変わる移転では使いますが、同じドメイン内でURLの構造が変わる移転では使いません。

Google検索セントラルは、アドレス変更ツールがHTTPからHTTPSでは不要であるとしています。常時SSL化の作業とドメイン移転の作業は分けて考えてください。

### Search Consoleのプロパティは作り直す必要がありますか？

登録の形によって変わります。同ガイドによると、URLプレフィックスプロパティはプロトコルごとに別のものとして扱われ、ドメインプロパティはプロトコルを集約します。

HTTPSへ切り替えた場合、URLプレフィックスで登録していたならHTTPS側の追加が必要です。ドメインプロパティなら追加は不要です。ドメインが変わる移転では新ドメインのプロパティを登録し、旧ドメインのプロパティは転送の確認のために残しておきます。
