# 開発会社の廃業に備える業務システムの引き継ぎ準備

## 開発会社が廃業したら、業務システムは引き継げますか？

引き継げるかどうかは、廃業してから動くのではなく、契約の時点で何を取り決めていたかで決まります。要になるのは著作権の扱いと、ソースコードと設計書の預け先です。

相手の会社が無くなった後では、交渉する相手がいません。資料を渡してもらうことも、質問に答えてもらうこともできません。残った資料の範囲で、別の会社が保守を引き受けられるかどうかが決まります。

### 引き継ぎを左右する3つの取り決め

| 取り決め | 決めていないと起きること |
| --- | --- |
| 著作権の帰属と改変の可否 | ソースコードが手元にあっても、手を入れてよいかが不明になります |
| 納品物に含める書類の範囲 | 設計書や手順書が無く、別の会社が構造を読み解けません |
| ソースコードと設計書の預け先 | 開発会社の社内にしか無く、廃業と同時に取り出せなくなります |

3つは別の話です。著作権を譲り受けていても、設計書が無ければ保守の見積もりが取れません。設計書を受け取っていても、改変の権利が移っていなければ手を入れられません。それぞれの詳細は後述します。

### 廃業がわかってからできることの限界

できることは残っていますが、範囲は限られます。

1. 稼働中のシステムから、画面と設定とデータを書き出します。つまずきやすい点は、サーバの管理画面にログインできない場合です。認証情報が開発会社側にしか無いことがあります。
2. 契約書と発注書を集め、著作権の扱いと納品物の範囲を確認します。所要時間の目安は半日です。
3. 残っている担当者に連絡を取り、ソースコードと設計書の提供を依頼します。会社が清算に入ると、窓口が管財人に移ることがあります。

実装者として申し上げると、ここで一番効くのは稼働中のサーバに入れるかどうかです。ソースコードが無くても、動いているサーバの中身を取り出せれば、別の会社が引き継げる可能性が残ります。逆に、サーバの認証情報を開発会社だけが持っている構成では、動いているシステムに触れないまま期限を迎えます。

つまり、備えの本体は廃業の前にあります。次のセクションから、契約の時点で何を決めておくかを順に扱います。

## ソースコードを受け取っていれば改造できますか？

受け取っているだけでは改造できないことがあります。著作権法では、改変と二次的著作物の利用に関する権利は契約で特掲しなければ移らない扱いになっています。

特掲とは、譲渡の対象としてその権利を名指しで書くことです。「著作権を譲渡する」という一文だけでは足りません。

### 著作権が誰に発生するか

出発点は、費用を払った側ではなく作った側です。著作権法第15条第2項は、法人等の発意に基づき業務に従事する者が職務上作成するプログラムの著作物の著作者は、契約や勤務規則に別段の定めがない限りその法人等とすると定めています。出典: e-Gov法令検索「著作権法」(昭和45年法律第48号) 第15条第2項。

つまり、契約で定めない限り、著作権は開発会社側に発生している状態から話が始まります。譲渡そのものは可能で、第61条第1項は著作権の全部または一部を譲渡できると定めています。

### 契約書で特掲が必要になる権利

見落とされやすいのが第61条第2項です。

| 条項 | 内容 |
| --- | --- |
| 第61条第2項 | 第27条または第28条の権利が譲渡の目的として特掲されていないとき、これらの権利は譲渡した者に留保されたものと推定します |
| 第27条 | 翻訳、編曲、変形、脚色、映画化その他の翻案を行う権利 |
| 第28条 | 二次的著作物の利用に関する原著作者の権利 |
| 第59条 | 著作者人格権は著作者の一身に専属し、譲渡できません |
| 第20条第2項第3号 | 特定の電子計算機で実行できないプログラムを実行できるようにするため等の必要な改変には、同一性保持権を適用しません |

出典: e-Gov法令検索「著作権法」(昭和45年法律第48号) 第61条第2項・第27条・第28条・第59条・第20条第2項第3号。

ソースコードを後から改造する行為は、第27条の翻案に当たる整理になります。別の会社に引き継いで手を入れてもらう前提なら、第27条と第28条を特掲した契約が必要です。第59条の著作者人格権は譲渡できないため、実務では不行使の取り決めを別に置きます。

契約書のひな型は、IPAが「情報システム・モデル取引・契約書」として公開しています。公開日は2020年12月22日で、受託開発と保守運用の契約書 (第二版) のWord文書は2025年4月8日に更新されています。Word形式の文書は自由にカスタマイズして利用できると明記されています。出典: IPA「情報システム・モデル取引・契約書 (第二版)」。

実装者の実務では、ここが一番の分かれ目です。改造の権利が移っていないシステムは、引き受ける側から見ると手を出しにくい案件になります。相手の会社が無くなっていて権利の確認も取れないため、見積もりを断られることがあります。

## ソフトウェア・エスクロウ制度とは何ですか？

ソフトウェア・エスクロウ制度とは、ソースコードや技術情報を第三者の機関に預ける仕組みです。開発会社の破産や事故が起きた場合に限って開示を受けられます。日本では一般財団法人ソフトウェア情報センタが預託先を務めています。

提供する側と受け取る側の双方に都合があります。開発会社は通常時はソースコードを渡さずに済みます。発注側は相手が無くなった場合の道筋を確保できます。

### 預けられるものと開示の条件

仕組みは次の流れです。

1. 取引の開始時に、提供者 (ライセンサ) と被提供者 (ライセンシ) が預託の契約を結びます。ソースコードや技術情報などを第三者 (エスクロウ・エージェント) に預けます。
2. 契約で開示条件を事前に定めます。つまずきやすい点は、どの事象を開示の引き金にするかの合意です。破産や事故が典型です。
3. 条件を満たした場合に限り、エージェントが預託物をライセンシに開示します。条件が満たされなければ開示されません。

預託の対象はソースコードや技術情報などです。媒体としてFDやCD-ROM、CD-Rといった磁気や光学の媒体、紙ベースのドキュメント類が挙げられています。出典: 一般財団法人ソフトウェア情報センタ「ソフトウェア・エスクロウ」。

開示されない条件で預かる点が、この制度の性格です。発注側が自由に中身を見られる仕組みではありません。

### 日本での預託先と開始時期

一般財団法人ソフトウェア情報センタ (SOFTIC) が預託先です。1997年7月1日から日本のエスクロウ・エージェントとして業務を行っています。出典: 一般財団法人ソフトウェア情報センタ「ソフトウェア・エスクロウ」。

クラウド上での預託は令和8年4月から開始予定と案内されています。媒体を物理的に預ける形が基本であった制度に、クラウドでの預託が加わります。出典: 一般財団法人ソフトウェア情報センタ「ソフトウェア・エスクロウ」。

実装者の視点で補足すると、預けるのはソースコードだけでは足りません。ビルドに必要な設定、外部サービスの接続情報の構成、データベースの定義がないと、受け取った側はシステムを立ち上げられません。預託物の中身は、別の会社が同じ環境を再現できるかという基準で選んでください。

費用は次のセクションで扱います。

## 預託の費用はいくらかかりますか？

新規契約手数料は年額で16万2000円から、契約更新手数料は年額で14万3000円からです。いずれも1件あたりで消費税は別です。

金額は一般財団法人ソフトウェア情報センタのページに公開されています。賛助会員の価格と一般の価格があり、ライセンサとライセンシのどちらかが賛助会員であれば会員価格が適用されます。

### 手数料の一覧と会員価格

| 区分 | 一般 | 賛助会員 |
| --- | --- | --- |
| 新規契約手数料 (年額・1件) | 16万2000円 | 14万3000円 |
| 新規契約手数料 (年額・1件、クラウド型) | 23万円 | 20万円 |
| 契約更新手数料 (年額・1件) | 14万3000円 | 12万4000円 |
| 契約更新手数料 (年額・1件、クラウド型) | 20万円 | 17万5000円 |
| 預託物交換手数料 (1回) | 7700円 | 7700円 |

出典: 一般財団法人ソフトウェア情報センタ「ソフトウェア・エスクロウ」。金額はいずれも消費税別です。

年額である点に注意してください。預託は1回払いではなく、更新を続ける前提の費用になります。

### クラウドでの預託の扱い

クラウド型は物理媒体の預託より手数料が高く設定されています。新規契約で比べると、一般の価格は23万円で、物理媒体の16万2000円より6万8000円高い水準です。出典: 一般財団法人ソフトウェア情報センタ「ソフトウェア・エスクロウ」。

更新の手続は次の流れで考えます。

1. 預託する内容を確定し、申込を行います。つまずきやすい点は、開発会社の協力が前提になることです。預けるのは開発会社側です。
2. 手数料を支払い、預託物を預けます。所要時間の目安は、社内の決裁を含めて1か月です。
3. システムを改修したタイミングで預託物を交換します。1回あたり7700円です。交換を怠ると、預けてあるのが古い版のままになります。

実装者としてお伝えしたいのは、3番の交換が実務の弱点になりやすい点です。改修を重ねたシステムで、預けてあるのが2年前の版では、受け取っても現在の動作と合いません。改修の完了を預託物の交換の引き金にする取り決めを、保守契約側に書いておく形が確実です。

費用を払うのは発注側になるのが通例です。この費用を保守費に含めるか別に見るかは、見積もりの段階で決めておいてください。

## 預託のほかに契約で決めておくことは？

納品物として何を受け取るかを契約に書くことが先です。公的なモデル契約書を土台にすると、設計書や手順書の抜けを防げます。

預託は、相手が無くなった場合の最後の備えです。日常的に手元にある資料が足りていれば、そもそも預託に頼らずに引き継げます。

### 納品物に入れる書類の一覧

受け取る書類は、別の会社が構造を読み解ける範囲で決めます。

| 書類 | 無いと困る場面 |
| --- | --- |
| 画面と機能の仕様書 | どの処理がどの画面につながるかを追えません |
| データベースの定義書 | 項目の意味と関連がわからず、改修で壊します |
| 外部サービスとの連携仕様 | 接続先と認証の方式が不明になります |
| 環境構築と配備の手順書 | 別のサーバで同じ環境を再現できません |
| 運用の手順書と障害時の対応手順 | 止まったときに誰も復旧できません |

契約書のひな型は、IPAが「情報システム・モデル取引・契約書」として公開しています。公開日は2020年12月22日です。受託開発と保守運用を対象とする第二版と、条文のみのひな型が収録されています。パッケージとSaaS/ASP活用向けの第二版追補版もあります。出典: 独立行政法人情報処理推進機構「情報システム・モデル取引・契約書 (第二版)」。

### 引き継ぎを想定した保守契約の書き方

保守契約側には、次の3点を入れておきます。

1. 資料の更新の義務を書きます。改修のたびに仕様書と手順書を直し、最新版を発注側に渡す形にします。つまずきやすい点は、更新の対象を「変更があった箇所」に限ると、全体像を示す資料が古いまま残ることです。
2. サーバとサービスの契約名義を発注側にします。所要時間の目安は、名義の移管で2週間です。開発会社の名義のままでは、廃業時に止まります。
3. 認証情報の保管先を社内に置きます。管理画面のアカウントとドメインの管理権限は、発注側が常に持てる形にします。

実装者の経験では、ここが整っている案件は、開発会社が変わっても引き継ぎが短期間で済みます。逆に、名義と認証情報が開発会社に集まっている構成は、相手が健在であっても別の会社に移れません。預託を検討する前に、名義の確認から始めてください。

## 引き継ぎの備えは誰が社内で見ますか？

中小企業ではシステム担当者が不在か兼任である場合が多く、備えが抜けやすい点が実情です。担当を決めて年に1回の確認を回す形が現実的です。

備えが抜ける原因は、気の緩みではありません。見る人がいないという構造にあります。

### 担当者不在と兼任の実情

株式会社kubellが2025年12月に発表した「中小企業のデジタル化に関するアンケート調査」があります。社外への委託と他業務との兼務を含めても、システム担当者がいない企業は27.5パーセントでした。従業員数10名から299名の中小企業から有効回答1,093サンプルを得た調査です。

| 従業員規模 | 担当者の不在率 |
| --- | --- |
| 10名から29名 | 48.2パーセント |
| 30名から49名 | 29.8パーセント |
| 50名から99名 | 20.1パーセント |
| 100名から299名 | 13.2パーセント |

出典: 株式会社kubell「中小企業のデジタル化に関するアンケート調査」(2025年12月発表)。

30名未満ではほぼ半数の企業に担当者がいません。兼任も増えています。ノークリサーチが2025年5月に実施した調査を見ます。対象は年商500億円未満の中堅・中小企業800社です。年商5億円から50億円の層では、情報システムの担当が他業務と兼任である割合が2023年の48.0パーセントから2025年の61.1パーセントへ増えました。13.1ポイントの増加です。出典: ノークリサーチ 2025年5月調査。

いずれも民間調査です。調査ごとに対象の規模と設問の定義が違いますので、自社に近い条件の数値で見てください。

### 年1回の棚卸しで確認する項目

兼任の担当者が1年に1回で回せる範囲に絞ります。

1. サーバとドメイン、外部サービスの契約名義を確認します。所要時間の目安は1時間です。
2. 管理画面のアカウントに自社の担当者が入れるかを実際に試します。つまずきやすい点は、退職者のアカウントで運用が続いている場合です。
3. 手元にある設計書と手順書の日付を確認します。最後の改修より古ければ、更新を依頼します。
4. 預託をしている場合は、預けてある版が現在の版かを確認します。所要時間の目安は30分です。

4項目で半日かかりません。棚卸しの時期を決算や保守契約の更新に合わせると、確認を忘れにくくなります。

実装者として付け加えると、2番を書面の確認で済ませないことが大切です。アカウントが残っているという記録があっても、実際にログインできるかは別です。年に1回、画面に入るところまで試してください。

## 備えが抜けていた場合は何から手を付けますか？

いま動いているシステムの状態を記録することから始めます。稼働中のうちに集められる情報が、引き継ぎの可否をほぼ決めます。

契約を結び直すのは時間がかかります。先に手を動かせるのは、動いている環境の側です。

### 稼働中に集めておく情報

優先順に並べます。

1. サーバと外部サービスの管理画面に、自社の担当者で入れるかを確認します。入れない場合は、名義と権限の移管を依頼します。所要時間の目安は2週間です。
2. データを定期的に書き出す仕組みを用意します。つまずきやすい点は、画面からの出力だけで満足してしまうことです。項目の関連がわかる形で丸ごと取り出す必要があります。
3. 画面と帳票の一覧を作ります。業務の担当者が画面を順に開き、名称と用途を書き出すだけでも、引き継ぐ側の読み解きが速くなります。
4. 設計書と手順書の有無を確認し、無い範囲を洗い出します。所要時間の目安は半日です。
5. 改修の履歴を集めます。いつ何を直したかの記録は、現在の構成を知る手がかりになります。

集めた情報は社内で保管します。開発会社の共有フォルダに置いたままでは、相手が止まったときに一緒に消えます。

実装者の経験では、2番のデータの書き出しが最も効きます。ソースコードも設計書も無い状態でも、データが揃っていれば別の仕組みへ移す道が残ります。逆に、データを取り出せない構成では、業務そのものを止めることになります。

### 当社でお手伝いできること

外注したシステムが動いている間は、備えの話は後回しになります。日々の業務が回っているため、着手の動機が生まれにくいという事情があります。

原因は、何が足りていないかが見えない点にあります。契約書と資料と環境を突き合わせて初めて、名義が相手側にある、設計書が無い、データを取り出せないといった穴がわかります。穴が見えれば、優先順に埋められます。

当社は業務システムの構築とDXの伴走支援を手がけています。既存システムの引き継ぎ可否の確認、資料の棚卸し、データの書き出しの仕組みづくりまで、実装の側からお手伝いできます。他社が作ったシステムの引き継ぎも扱います。

いま抱えているシステムが引き継げる状態かを確かめたい場合は、[無料診断](/diagnostic)をご利用ください。社内で何から整えるかを検討したい場合は、[DXガイドブックのダウンロード](/guidebook)もご用意しています。

## よくあるご質問

この記事に関して多い質問と回答をまとめます。

### 開発会社が廃業したあとでもソースコードを受け取れますか？

会社が清算に入ると、窓口が管財人に移ることがあります。預託をしていない場合、受け取れるかどうかは残った関係者の協力次第です。稼働中のサーバに自社で入れるかを先に確認してください。

### ソースコードを預けてもらう費用は誰が払うのですか？

発注側が払うのが通例です。手数料は年額で、新規契約が16万2000円から、更新が14万3000円からです。いずれも1件あたりで消費税は別です。出典: 一般財団法人ソフトウェア情報センタ「ソフトウェア・エスクロウ」。

### 開発会社が預託を断る場合はどうすればよいですか？

預けるのは開発会社側のため、協力が前提になります。断られた場合は、納品物の範囲を広げる交渉に切り替えてください。設計書と手順書を受け取る形でも、引き継ぎの余地は広がります。

### クラウドで動いているシステムでも預託は意味がありますか？

意味はありますが、預託だけでは足りません。クラウドの契約名義が開発会社のままなら、サービスごと止まります。名義と認証情報を自社で持つ方が先です。

### 著作権を譲り受けていれば預託は不要ですか？

権利と資料は別の問題です。著作権法第61条第2項により第27条と第28条を特掲して譲り受けていても、資料が無ければ改修を頼めません。設計書とソースコードが手元にあるかを別に確認してください。出典: e-Gov法令検索「著作権法」第61条第2項。

### 別の会社に引き継ぐとき、何があれば保守を受けてもらえますか？

最低限は、動く環境と、データ、画面の一覧です。設計書が揃っていれば見積もりが出やすくなります。改変の権利が移っているかも、引き受ける側が必ず確認します。
