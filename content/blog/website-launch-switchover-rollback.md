# リニューアル公開当日の切り替え手順と切り戻し

## 公開当日は、何をどの順番で切り替えますか？

順序は4段です。公開前の確認、クロール拒否の解除、DNSまたは公開設定の切り替え、公開後の確認の順に進めます。この順なら、検索から見えない状態で最終確認ができます。

順序を入れ替えると戻せなくなります。切り替えを先に行うと、確認の途中の状態が公開されます。

### 当日の作業を4段に分ける

作業は次の4段で整理します。段の境目で必ず確認を挟んでください。

| 段 | 作業 | 確認すること |
|---|---|---|
| 1. 公開前の確認 | 新サイトの表示、フォームの送信、リンク切れ | 検索から見えない状態のまま全ページを開く |
| 2. クロール拒否の解除 | robots.txtとnoindexの指定を外す | 解除の対象が漏れていないか |
| 3. 切り替え | DNSの変更、または公開設定の変更 | 旧サイトの転送が動いているか |
| 4. 公開後の確認 | 表示、フォーム、転送、Search Consoleへの送信 | 主要な導線が機能しているか |

robots.txtとは、クロールしてよい範囲をサイト全体に対して指定するファイルです。noindexとは、そのページを検索結果に表示しないようGoogleへ伝える指定です。

Googleは移転の手順として、移転前の準備に新しいURLを含むサイトマップファイルの作成と、新規サイトのrobots.txtにクロール対象から除外する部分を正しく反映することを挙げています。移転中の作業としては、個々のURLをテストするにはURL検査ツールを使い、ドメイン名またはサブドメインを変更している場合はアドレス変更ツールを送信し、Search Consoleで新しいサイトマップを送信するよう案内しています。

出典: Google検索セントラル「URLの変更を伴うサイト移転」(https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes?hl=ja)

### 段ごとの所要時間の目安

時間は規模で変わりますが、目安は次のとおりです。当日の予定を組む基準に使ってください。

1. 公開前の確認 (ページ数20程度で所要2時間。フォームの送信テストは実際に送って受信まで確認します)
2. クロール拒否の解除 (所要15分。ただし反映には時間差があります)
3. 切り替え (所要15分。DNSの場合は反映の待ち時間が別に発生します)
4. 公開後の確認 (所要1時間。主要なページと導線に絞ります)

つまずきやすいのは1番目です。ページ数が50を超えると、当日の2時間では終わりません。公開日の前日までに確認を終え、当日は差分だけを見る段取りにしてください。

もう1点、2番目の反映の時間差に注意が必要です。設定を外した瞬間にGoogleが認識するわけではありません。この時間差については後のセクションで扱います。

### 立ち会う人と連絡の取り方を決める

当日は3つの役割が必要です。人数ではなく役割で決めてください。

| 役割 | やること | 決めておくこと |
|---|---|---|
| 作業する人 | 設定の変更と切り替えの実行 | 誰が、どの時刻に実行するか |
| 確認する人 | 表示とフォームの動作確認 | どの端末とブラウザで確認するか |
| 判断する人 | 続行か切り戻しかの決定 | 連絡が取れる時間帯 |

判断する人を決めていない案件が最も混乱します。不具合が出た場面で、直して進めるのか戻すのかを決める権限がなければ、作業は止まったままになります。

確認する端末も先に決めてください。担当者の端末で表示できても、社内の別の端末では古い内容が見えることがあります。スマートフォンの回線と社内の回線の両方で確認する体制にしておくと、切り替えの反映状況を早く把握できます。

公開前に残しておく記録については、次のセクションで扱います。

## 公開前に何を確認しておきますか？

旧サイトの記録と、新サイトのクロール拒否の設定の2点です。記録は公開後に取り直せません。公開日より前の日付で残しておく必要があります。

この2点を飛ばすと、後で判断の材料がなくなります。公開後に「前はどうだったか」を調べても答えは出ません。

### 公開前に残しておく記録と、取得できる期間

記録は4項目です。いずれも公開日の前日までに保存してください。

| 記録する項目 | 取得元 | 取得の単位 |
|---|---|---|
| クリック数、表示回数、CTR、平均掲載順位 | Search Console 検索パフォーマンス | 公開直前の4週間、ページ別とクエリ別 |
| 表示回数上位20ページのURLの一覧 | Search Console 検索パフォーマンス | 公開直前の4週間 |
| インデックスに登録されているURLの数 | Search Console インデックス作成 | 公開直前の1時点 |
| Core Web Vitalsの3指標の判定 | Search Console Core Web Vitals | 公開直前の1時点 |

2番目の一覧が、当日と翌日の確認で最もよく使います。転送先が正しいかを確認する対象そのものになります。

取得できる期間には上限があります。Search Consoleの検索パフォーマンスで遡れる最長期間は16か月です (出典: Search Consoleヘルプ「検索パフォーマンス レポート (検索結果): 概要と基本設定」https://support.google.com/webmasters/answer/7576553?hl=ja)。

Googleアナリティクス4は設定次第です。無料版のデータ保持期間の上限は14か月で、既定値は2か月です (出典: アナリティクスヘルプ「データ保持期間」https://support.google.com/analytics/answer/7667196?hl=ja)。設定を変えていなければ、2か月より前のデータは残っていません。

保存の手順は次のとおりです。

1. Search Consoleの管理画面から各レポートをCSVで書き出す (所要30分)
2. 画面の表示もそのまま画像で保存する (所要15分)
3. Googleアナリティクス4のデータ保持の設定値を確認し、必要なら14か月に変更する (所要10分)
4. 保存したファイルを日付入りのフォルダ名でまとめる (所要10分)

つまずきやすいのは3番目です。設定を14か月に変えても、過去に遡って復元されるわけではありません。変更した日以降のデータが対象になります。リニューアルの検討を始めた時点で変えておくのが実務的です。

### テスト環境の設定が残っていないかの確認

もう1点は、新サイト側の設定です。公開前のテスト中は、社外から見えないようにクロール拒否の設定を入れます。これを公開時に外し忘れると、新サイトが検索対象になりません。

確認は3箇所です。いずれも当日の作業の第2段で外します。

1. サイトのrobots.txtを直接開き、全体を拒否する記述が残っていないかを見る
2. 各ページのnoindexの指定が残っていないかを見る
3. CMSの管理画面にある検索エンジンへの表示の可否が、表示する側になっているかを見る

3番目が最も見落とされます。HTMLには書かれていないのに、CMSの設定の1項目が全ページにnoindexを付けている構成があります。当社が公開に立ち会う場合も、この項目は作業の直前に画面で確認します。

なお、外した設定がGoogleに反映されるまでには時間差があります。この時間差が切り戻しの判断にも影響するため、次のセクションで扱います。

## 旧サイトへ戻せますか？

条件付きで戻せます。ただし、切り替えの方式によって戻るまでの時間が変わります。DNSを切り替えた場合は、設定したTTLの時間だけ新旧が混在します。

即座に元の状態に戻る方式は限られます。方式を選ぶ段階で、戻すときの時間も一緒に確認してください。

### 方式ごとに戻るまでの時間が変わる

切り替えの方式は主に3つです。戻すときの挙動が異なります。

| 方式 | 切り替えの内容 | 戻すときの時間 |
|---|---|---|
| 同じサーバ内で公開設定を変える | CMSの公開設定またはファイルの差し替え | ほぼ即時に戻せます |
| 同じサーバでドキュメントルートを切り替える | 参照先のフォルダを変更する | ほぼ即時に戻せます |
| DNSを変更してサーバを移す | 参照先のIPアドレスを変える | TTLの時間だけ混在します |

TTL (Time To Live) とは、DNSの情報をキャッシュに保持してもよい時間を秒単位で示す値です。JPRSの用語辞典によると、例として3600秒のTTLが設定されている場合、そのリソースレコードは最大で3600秒 (1時間) キャッシュされます。TTLはキャッシュに保持されたのち減少し、ゼロになるとキャッシュから削除されます。

出典: JPRS用語辞典「TTL」(https://jprs.jp/glossary/index.php?ID=0136)、「キャッシュ」(https://jprs.jp/glossary/index.php?ID=0181)

つまり、TTLが3600秒のまま切り替えると、戻す操作をしても最大1時間は新旧どちらに届くか分かりません。対策は、切り替えの数日前にTTLを短い値へ変更しておくことです。この作業を制作会社の作業範囲に含めるかどうかは、発注時に確認してください。

### robots.txtの反映には時間差がある

クロール拒否の設定も即時ではありません。Googleは通常robots.txtファイルの内容を最大24時間キャッシュに保存するとしています。タイムアウトや5xxエラーが発生した場合はさらに長期間キャッシュを保持することがあり、max-age Cache-Control HTTPヘッダに基づいてキャッシュ期間を延長または短縮する場合があるとされています。

出典: Google検索セントラル「robots.txt の書き方、設定と送信」(https://developers.google.com/search/docs/crawling-indexing/robots/robots_txt?hl=ja)

この時間差の意味は2つあります。1つは、公開当日に拒否を外しても、その日のうちにクロールされるとは限らないことです。もう1つは、誤って拒否を入れたまま公開した場合も、外せばいずれ反映されるということです。

慌てて他の設定まで変えないでください。拒否の設定だけを直し、反映を待つのが正しい対応です。

### 戻す判断をしても転送は外さない

旧サイトに戻す場合でも、旧URLから新URLへの転送は外しません。Googleは移転後のリダイレクトの保持期間として「一般的には1年以上」と記載しています (出典: Google検索セントラル「URLの変更を伴うサイト移転」https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes?hl=ja)。

ドメインを変更した場合はさらに明確です。Search Consoleヘルプには、アドレス変更ツールによる転送の処理は移行を開始してから180日間続くとされ、リダイレクトは「少なくとも180日間」維持するよう案内されています (出典: Search Consoleヘルプ「アドレス変更ツール」https://support.google.com/webmasters/answer/9370220?hl=ja)。

そのため、実務では「表示を旧サイトに戻す」と「転送を元に戻す」を分けて考えます。戻すのは表示の側だけです。当社が切り戻しの手順を用意する場合も、転送の設定は触らない前提で作ります。

戻す判断の基準そのものは、次のセクションで扱います。

## 切り戻しの判断は、何を基準にしますか？

順位の動きではなく、機能が止まっているかどうかで判断します。公開直後の順位変動はGoogleが通常のことと説明しているため、順位を理由に戻す判断はしません。

判断の軸を事前に文章にしておいてください。当日に決めようとすると、その場の印象で判断が揺れます。

### すぐ戻す症状と、直して進める症状

境目は、業務または売上が止まっているかどうかです。次の表を当日の判断表として使ってください。

| 症状 | 判断 | 理由 |
|---|---|---|
| 問い合わせフォームが送信できない | すぐ戻す | 商談の機会が失われ、復旧まで代替手段がありません |
| 決済や予約の機能が動かない | すぐ戻す | 売上に直接影響します |
| 全ページが表示されない | すぐ戻す | 復旧の見込みが立つまで公開を続ける意味がありません |
| 一部のページでレイアウトが崩れている | 直して進める | 該当ページを一時的に非公開にする対応も取れます |
| 旧URLの一部が転送されていない | 直して進める | 転送の追加設定で当日中に対応できます |
| 検索順位が下がった | 戻さない | 公開直後の変動は正常な範囲に含まれます |

最後の行が判断を誤りやすい箇所です。Googleは「移転中は、検索でのコンテンツ掲載順位が一時的に変動することがあります。これは通常のことであり、サイトのランキングは時間の経過とともに安定します」と記載しています。反映についても、小規模から中規模のサイトで大半のページの移転が反映されるまでには数週間かかるとされています。

出典: Google検索セントラル「URLの変更を伴うサイト移転」(https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes?hl=ja)

公開当日の順位は、そもそも反映が始まったばかりの状態です。判断の材料になりません。

### 判断の期限を事前に決めておく

期限は2段で決めます。当日と、翌営業日です。

1. 当日の期限 (切り替えから2時間。この間に機能の確認を終え、続行か切り戻しかを決めます)
2. 翌営業日の期限 (レイアウトと転送の不具合を直す期限。直らない箇所は一時的に非公開にします)
3. 1週間後の確認 (インデックスの入れ替わりの確認。この時点でも表示されないURLがあれば点検します)

つまずきやすいのは1番目です。2時間という枠を決めていないと、確認と修正を繰り返したまま夜になります。作業する人と判断する人の双方が対応できる時間帯に切り替えを設定してください。

期限と併せて、次の3点も文章にしておきます。

| 決めておくこと | 例 |
|---|---|
| 誰が判断するか | Web担当者が一次判断し、決済に関わる場合は責任者が決定する |
| 何をもって続行とするか | フォームの送信と主要10ページの表示が確認できれば続行 |
| 戻した場合の次の予定 | 原因の特定後、翌週の同じ曜日に再度公開する |

3番目を決めておく理由があります。戻すこと自体は失敗ではありません。次の公開日が決まっていないと、戻した後に計画が止まります。再公開の候補日を事前に押さえておくと、判断が早くなります。

なお、切り戻しの作業が見積もりに含まれているかどうかは別の論点です。最後のセクションで、発注前に確認する項目としてまとめます。

## ドメインを変える場合は何が増えますか？

転送を維持する期間の管理と、Search Consoleの設定が増えます。ドメイン名の管理先を変える場合は、その手続きも当日の作業とは別に必要です。

いずれも公開当日だけで終わりません。期間をまたぐ作業として、担当を決めておいてください。

### 転送を維持する期間と担当

転送は長く残します。Googleは移転後のリダイレクトの保持期間として「一般的には1年以上」と記載しています (出典: Google検索セントラル「URLの変更を伴うサイト移転」https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes?hl=ja)。

ドメインを変更した場合の期間はより具体的です。Search Consoleヘルプには、アドレス変更ツールによる転送の処理は移行を開始してから180日間続くとされ、リダイレクトは「少なくとも180日間」維持するよう案内されています。ツールはドメインレベルのプロパティでのみ使用でき、以前のプロパティと新しいプロパティの両方の所有者である必要があります。

出典: Search Consoleヘルプ「アドレス変更ツール」(https://support.google.com/webmasters/answer/9370220?hl=ja)

ここで問題になるのが契約の期間です。旧ドメインの契約と、旧サーバの契約が180日より早く切れると、転送そのものが止まります。次の3点を先に確認してください。

1. 旧ドメインの有効期限と、更新の担当者
2. 旧サーバの契約期間と、解約の予定日
3. 転送の設定を誰が保守するか (制作会社の保守契約に含まれるかどうか)

つまずきやすいのは2番目です。費用を抑えるために公開の翌月に旧サーバを解約する判断をすると、転送が消えます。旧サーバは少なくとも180日は残す前提で予算を組んでください。

### Search Consoleの所有権と権限の引き継ぎ

新しいドメインでも、Search Consoleの登録が必要です。Googleはプロパティに対する役割として、所有者とユーザの2種類を定めています (出典: Google Search Consoleヘルプ「所有者、ユーザー、権限の管理」https://support.google.com/webmasters/answer/7687615?hl=ja)。

アドレス変更ツールを使うには、旧と新の両方で所有者である必要があります。つまり、制作会社だけが所有者になっている状態では、御社が自分でツールを使えません。

確認と設定の手順は次のとおりです。

1. 旧ドメインのプロパティで、御社のアカウントが所有者になっているかを確認する (所要10分)
2. なっていない場合、現在の所有者に所有権の付与を依頼する (依頼から反映まで数日)
3. 新ドメインのプロパティを作成し、御社のアカウントを所有者として登録する (所要30分)
4. 公開後、アドレス変更ツールを送信する (所要15分)

2番目に日数がかかることがあります。制作会社の担当者が不在だと止まります。公開日の2週間前までに終わらせてください。

### ドメイン名の指定事業者を変える場合の手続き

ドメイン名の管理先そのものを変える場合は、別の手続きが必要です。JPドメイン名では、管理指定事業者の変更に認証コード (AuthCode) の仕組みがあり、2022年11月13日から利用が開始されています (出典: JPRS「ドメイン名の管理指定事業者の変更」https://jprs.jp/about/dom-rule/agent-change/index.html)。

この手続きは公開当日の作業とは切り離してください。移管の途中でDNSの設定が引き継がれず、サイトが見えなくなる事故が起きます。移管を先に完了させ、動作を確認したうえで公開の切り替えに進む段取りが安全です。

なお、制作会社を変えるリニューアルでは、著作権の扱いも確認の対象になります。著作権法第61条第2項では、譲渡の契約に第27条と第28条の権利が特掲されていない場合、これらの権利は譲渡人に留保されたものと推定すると定められています (出典: 著作権法第61条第2項、e-Gov法令検索 https://laws.e-gov.go.jp/law/345AC0000000048)。デザインやコードを今後改変していく前提なら、契約書の記載を公開前に確認してください。この点の詳細は当社の別の記事で扱っています。

## 公開後はいつまで何を見ますか？

当日は機能の確認、翌日以降はインデックスの入れ替わりと表示速度を見ます。反映には数週間かかるため、当日の数値で成否を判断しません。

見る項目を日ごとに決めておくと、確認が習慣になります。決めていないと3日目で見なくなります。

### 当日に見る項目と、翌週以降に見る項目

時期ごとに見る対象が変わります。次の表のとおりです。

| 時期 | 見る項目 | 確認の方法 |
|---|---|---|
| 当日 | 主要ページの表示、フォームの送信、決済や予約の動作 | 実際に操作して結果を受信まで確認します |
| 当日 | 旧URLからの転送 | 公開前に保存した上位20ページのURLを順に開きます |
| 翌日 | 新URLのインデックス登録 | Search ConsoleのURL検査ツールで上位ページを検査します |
| 1週間後 | 旧URLの減少と新URLの増加 | インデックス作成レポートで両者の増減を見ます |
| 1週間後 | 表示速度の判定 | Core Web Vitalsのレポートで3指標を確認します |
| 1か月後 | 表示回数と平均掲載順位 | 公開前に保存した4週間の記録と比較します |

当日の2行は、公開前に保存した記録がそのまま確認の材料になります。上位20ページのURLの一覧を用意していれば、転送の確認は30分で終わります。

1か月後の比較についても、反映の期間を踏まえてください。Googleは小規模から中規模のサイトで大半のページの移転が反映されるまでに数週間かかるとしています (出典: Google検索セントラル「URLの変更を伴うサイト移転」https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes?hl=ja)。1か月後が最初の比較の時期になります。

### 表示速度の合否は基準値で判定する

表示速度は、過去との比較を必要としません。Core Web Vitalsには絶対的な合格の基準があります。

Core Web Vitalsとは、ページの表示や操作の快適さをGoogleが定義した指標の組み合わせです。良好とされる基準は次のとおりです。

| 指標 | 良好の基準 | 何を測るか |
|---|---|---|
| LCP (Largest Contentful Paint) | 2.5秒以内 | 主要な内容が表示されるまでの時間 |
| INP (Interaction to Next Paint) | 200ミリ秒以下 | 操作に対する反応の速さ |
| CLS (Cumulative Layout Shift) | 0.1以下 | 表示中のレイアウトのずれの量 |

出典: web.dev「Web Vitals」(https://web.dev/articles/vitals)

判定には実際のユーザのデータが使われ、75パーセンタイルの値で評価されます (出典: web.dev「How the Core Web Vitals metrics thresholds were defined」https://web.dev/articles/defining-core-web-vitals-thresholds)。

この75パーセンタイルという条件が実務では重要です。御社の担当者の端末で速く表示されても、合格しているとは限りません。4人のうち3人が基準内である必要があります。

また、実際のユーザのデータが集まるまでには時間がかかります。公開の翌日に判定が出るわけではありません。1週間から1か月の幅で見てください。

確認の手順をまとめると次のとおりです。

1. 当日は機能の確認に集中する (所要1時間)
2. 翌日にURL検査ツールで上位ページの登録を確認する (1本あたり所要2分)
3. 1週間後にインデックスの増減とCore Web Vitalsを確認する (所要30分)
4. 1か月後に公開前の記録と比較する (所要1時間)

つまずきやすいのは4番目です。比較する期間の曜日構成を揃えてください。月単位で比較すると土日の数が変わり、その差が変動として現れます。公開前に保存した4週間と、公開後の4週間で比べるのが確実です。

## 発注前に制作会社へ何を確認しますか？

切り替えの方式、切り戻しの可否と所要時間、当日の立ち会いの体制の3点です。いずれも見積もりの範囲に含まれるかどうかで費用が変わります。

見積もりの段階で聞いてください。公開の直前に聞くと、追加費用として扱われます。

### 確認する項目の一覧

質問はそのまま使える形で並べます。回答を書面で受け取ってください。

| 確認する項目 | 具体的な質問 | 回答で見る点 |
|---|---|---|
| 切り替えの方式 | 公開はDNSの変更ですか、同じサーバ内の設定変更ですか | DNSなら戻すまでの時間が発生します |
| TTLの事前調整 | 切り替えの前にTTLを短くしますか。作業範囲に含まれますか | 含まれない場合、誰がやるかを決めます |
| 切り戻しの可否 | 不具合が出た場合、どのくらいで旧サイトに戻せますか | 時間が示せるかどうかで準備の有無が分かります |
| 切り戻しの費用 | 戻す作業は見積もりに含まれますか | 含まれない場合の単価を確認します |
| 立ち会いの体制 | 公開当日は何時から何時まで対応しますか | 連絡手段と対応時間を確認します |
| 公開後の対応 | 翌営業日以降の不具合は保守の範囲ですか | 保守契約の開始時期を確認します |
| 記録の取得 | 公開前の記録は御社が取りますか、当社が取りますか | 担当を明確にします |

3番目と4番目を聞かない発注が多いです。切り戻しの手順を用意していない会社もあります。時間を即答できるかどうかで、準備の有無が判断できます。

確認の手順は次のとおりです。

1. 上の表をそのまま質問票にして、見積もり依頼と一緒に送る (所要30分)
2. 回答を書面で受け取り、見積もりの内訳と照らす (所要1時間)
3. 含まれていない作業を一覧にし、誰がやるかを決める (所要30分)
4. 決めた内容を発注書または仕様書に反映する (所要1時間)

つまずきやすいのは3番目です。含まれていない作業を放置すると、当日に誰もやりません。TTLの調整のように、作業自体は15分で終わるものでも、担当が決まっていなければ実施されません。

### 見積もりと契約に書いておくこと

書面に残すのは次の4点です。口頭の合意は当日の判断で揺れます。

1. 公開の切り替えの方式と、実施する時刻
2. 切り戻しの条件、想定の所要時間、費用の扱い
3. 当日の対応時間と連絡手段、連絡がつかない場合の扱い
4. 転送の設定を維持する期間と、その保守の担当

4番目は公開の何か月も後に効いてきます。ドメインを変更した場合、リダイレクトは少なくとも180日間維持する必要があります (出典: Search Consoleヘルプ「アドレス変更ツール」https://support.google.com/webmasters/answer/9370220?hl=ja)。保守契約の期間がこれより短い場合、期間中に担当がいなくなります。

当社がリニューアルの公開に立ち会う場合も、この4点を事前に書面で確定させます。特に切り戻しの条件は、実行するかどうかではなく、実行できる状態を保っておくことが目的です。準備があれば、当日の判断に迷いが出ません。

公開当日の段取りをこれから詰める段階であれば、無料診断 (/diagnostic) で現在のサイトの構成をもとに、切り替えの方式と当日に確認すべき項目をお伝えしています。制作会社への質問票を作る材料としてもご利用いただけます。

## よくあるご質問

公開当日の切り替えについて多い質問と回答をまとめます。

### 公開の切り替えにはどのくらい時間がかかりますか？

切り替えの操作自体は15分程度です。ただし、方式によって反映の待ち時間が加わります。

同じサーバ内で公開設定を変える方式なら、操作の直後から新しい内容が見えます。DNSを変更してサーバを移す方式では、設定したTTLの時間だけ待ちが発生します。JPRSの用語辞典によると、TTLが3600秒の場合、そのリソースレコードは最大で3600秒 (1時間) キャッシュされます (出典: JPRS用語辞典「TTL」)。

当日の予定は、操作の時間ではなく確認の時間で組んでください。公開前の確認と公開後の確認を合わせて3時間程度を見込むのが実務的です。

### 公開当日に順位が下がったら、すぐ戻すべきですか？

戻しません。公開直後の変動は正常な範囲に含まれます。

Googleは「移転中は、検索でのコンテンツ掲載順位が一時的に変動することがあります。これは通常のことであり、サイトのランキングは時間の経過とともに安定します」と記載しています。反映についても、小規模から中規模のサイトで大半のページの移転が反映されるまでには数週間かかるとされています (出典: Google検索セントラル「URLの変更を伴うサイト移転」)。

戻す判断は、フォームの送信や決済のように機能が止まっている場合に限ります。

### DNSを切り替えた直後に、新旧どちらのサイトが見えますか？

どちらも見えます。TTLの期間だけ、見る人や回線によって新旧が混在します。

TTLは、DNSの情報をキャッシュに保持してもよい時間を秒単位で示す値です。キャッシュが残っている間は古い情報が使われ、TTLが経過すると新しい情報に切り替わります (出典: JPRS用語辞典「TTL」「キャッシュ」)。

そのため、社内の1台で古い内容が見えても異常ではありません。複数の回線と端末で確認し、切り替わり方を把握してください。切り替えの数日前にTTLを短くしておけば、この混在の時間を短縮できます。

### 切り戻しの作業は見積もりに含まれていますか？

会社によって異なります。含まれていない場合も多いため、発注前に確認してください。

確認する内容は3点です。戻すまでの想定の所要時間、作業の費用の扱い、そして戻す判断ができる時間帯です。時間を即答できる会社は、手順を用意していると判断できます。

含まれていない場合は、単価と対応時間を書面で確認し、発注書または仕様書に反映してください。

### 公開は何曜日に設定するのがよいですか？

翌営業日が確保できる曜日です。具体的には、火曜日から木曜日が扱いやすくなります。

理由は、不具合が残った場合の対応です。公開当日に直しきれない箇所は、翌営業日に対応します。金曜日に公開すると、不具合を抱えたまま土日を越えることになります。

あわせて、時刻も決めてください。アクセスが少ない時間帯で、かつ判断する人が連絡を取れる時間帯にします。深夜に設定すると、判断が必要な場面で連絡がつきません。午前中の早い時間帯に切り替え、その日のうちに確認を終える段取りが取りやすいです。
