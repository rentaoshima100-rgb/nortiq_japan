# 介護のLIFEデータ提出｜CSV連携仕様と外注要件

## LIFEへのデータ提出は、記録システムの何を決めれば実現しますか？

厚生労働省が公開するCSV連携仕様の版を要件に明記し、提出する様式ごとに記録画面の項目を対応づけることから始めます。仕組みを選ぶ前に、算定する加算と提出する様式を確定させるのが先です。

LIFEとは、科学的介護情報システムのことです。事業所が利用者の状態やケアの内容を厚生労働省へ提出し、返ってくる分析結果を活用するための仕組みです。

この順番には理由があります。提出する様式が決まらなければ、記録画面に必要な項目もわかりません。項目が決まらなければ、出力するCSVの中身も決められません。

### 先に確定させるのは提出する様式です

最初に決めるのは、算定する加算と、それに伴って提出する様式です。

1. 算定する加算を一覧にします。所要時間の目安は半日です。
2. 加算ごとに提出する様式を確認します。厚生労働省の通知を参照してください。
3. 様式ごとの提出頻度を書き出します。加算によって頻度が異なります。
4. 提出対象の利用者の範囲を確認します。全利用者が対象の加算もあります。

つまずきやすいのは2番目です。加算名だけで様式を推測すると、必要な項目が抜けます。通知に示された様式例そのものを見て確認してください。

### 記録画面の項目と様式の項目を突き合わせます

様式が決まったら、いま使っている記録の項目と突き合わせます。作業は表を1枚作るだけです。

| 確認すること | 具体的にみる点 |
| --- | --- |
| 様式の項目が記録に存在するか | 記録画面に該当する入力欄があるか |
| 記録の粒度が合っているか | 様式が求める区分より粗くないか |
| 誰がいつ入力しているか | 提出の締めまでに埋まる運用か |

ここで抜けが見つかるのが普通です。抜けた項目は、記録画面に追加するか、別の様式で代替できないかを検討します。

つまずきやすいのは、粒度の不一致です。記録では「良好」と1つにまとめている状態を、様式では段階で区分している場合があります。この場合、入力欄を増やす改修が必要になります。

この突き合わせを外注先に任せると、事業所の運用を知らないまま設計が進みます。表を作るところまでは自事業所で行い、その表を要件として渡してください。外注先に渡す資料の作り方は後述します。

## LIFEのCSV連携仕様は何を定めていますか？

厚生労働省が公開するCSV連携仕様は、ファイルエンコード、改行コード、空値と半角空白の扱い、ファイル名の規則を具体的に定めています。確認できる最新は3.10版です。

文書名は「科学的介護情報システム (LIFE) CSV連携仕様について」です。3.10版は令和8年5月付で、発行は厚生労働省老健局と国民健康保険中央会です。

出典: 厚生労働省老健局・国民健康保険中央会「科学的介護情報システム (LIFE) CSV連携仕様について」【3.10版】（令和8年5月、https://www.mhlw.go.jp/content/12301000/001698660.pdf ）

つまり、CSVの中身は事業所や介護ソフトが自由に決められるものではありません。仕様書に合っていなければ、取込の段階で弾かれます。

### ファイルエンコードと改行コードの規定

仕様書は、文字の扱いを2点に限定しています。

| 項目 | 仕様書の規定 |
| --- | --- |
| ファイルエンコード | UTF-8 または Shift-JIS（MS932）のいずれか |
| UTF-8の場合のBOM | 有無は問わない |
| 改行コード | CR-LF または CR |

改行コードにLFのみは含まれていません。この点は見落とされやすい箇所です。開発環境によってはLFが既定になっているため、出力時の設定を確認する必要があります。

### 空値と半角空白の扱いは意味が違います

仕様書では、空の値と半角空白がまったく別の意味を持ちます。ここが最も注意を要する規定です。

1. 空値（CSVファイル内では連続したカンマ）は、新規登録ではNullとしてデータベースに格納します。更新時は更新しません。
2. 半角空白はNullに置き換えます。仕様書はこれを「データ削除目的の特殊処理」と説明しています。
3. 全角空白と、2つ連続した半角空白は、通常のデータとして扱われます。

つまり、入力していない項目と、いったん入れた値を消したい項目は、CSV上で書き分ける必要があります。記録画面で空欄にしただけのつもりが、半角空白として出力されると、前回の値を消す指示になります。

要件には「空欄と削除を区別して出力できること」と明記してください。この1行の有無で、後の手戻りが変わります。

### ファイル名の規則と推奨される付け方

ファイル名については「ファイル名に関する規則は設けない」とされています。ただし固定的な名称を要する場合の推奨が示されています。

推奨形式は、インターフェース名（日本語名またはローマ字を用いた略記）、アンダースコア、管理連番、独自記号、拡張子.csvを続ける形です。

仕様書に挙げられているインターフェースの例は次のとおりです。

1. IF 利用者情報
2. IF 科学的介護推進に関する評価情報
3. IF 科学的介護推進に関する評価情報（診断名）
4. IF ADL維持等加算（2024年度）

この例は、要件に書く対応範囲の単位としても使えます。どのインターフェースに対応するのかを列挙する形にすると、範囲が曖昧になりません。

## 記録システムの外注では何を要件に書きますか？

対応する様式の範囲、出力するCSVの仕様の版、取込に失敗したときの確認画面、この3点を要件に書きます。版を書かないと、後から仕様が変わったときの対応範囲が決まりません。

3点はいずれも、提案書の「LIFE連携に対応」という一文では判断できない内容です。項目ごとに書き分けてもらってください。

### 対応する様式の範囲を列挙します

範囲は、インターフェース単位で列挙するのが確実です。前述の仕様書には、IF 利用者情報、IF 科学的介護推進に関する評価情報、IF ADL維持等加算（2024年度）といった例が示されています。

要件には次の形で書きます。

1. 対応するインターフェースの名称をすべて列挙します
2. 今回は対応しないものも「対象外」として明記します
3. 将来の追加を想定する場合、追加時の費用の考え方を書きます

つまずきやすいのは2番目です。対象外を書かないと、できていない部分が漏れなのか仕様なのか、検収時に判断できません。

### 出力仕様の版と更新時の扱い

要件には仕様書の版を書きます。本記事の時点で確認できる最新は3.10版です。

| 要件に書くこと | 書き方の例 |
| --- | --- |
| 準拠する仕様の版 | CSV連携仕様3.10版に準拠して出力すること |
| 版が上がった場合の対応 | 改修の要否を判定し、見積もりを提示すること |
| 判定の期限 | 新しい版の公表から一定期間内に判定すること |

版が上がるたびに全面改修になるのか、項目の追加だけで済むのかは、上がった版の内容によって変わります。事前に金額を確定させることはできません。決められるのは、判定して見積もりを出すという手続きの部分です。

所要時間の目安として、この3点を文書にする作業は1日あれば終わります。

### 取込エラーを確認して直せる画面

最後に、取込に失敗したときの画面を要件に入れます。これが最も抜けやすい項目です。

必要なのは次の3つです。

1. どのデータが弾かれたかを一覧で見られること
2. 弾かれた理由が表示されること
3. 記録を直して再出力できること

この画面がないと、エラーが出たときに事業所側で原因を追えません。介護ソフトの提供元へ問い合わせるしかなくなり、提出の期限に間に合わなくなります。

あわせて、空欄と削除を区別して出力できることも要件に書いてください。前述のとおり、半角空白はデータ削除目的の特殊処理として扱われます。この区別は画面の設計に影響します。

## LIFEへの提出は加算とどう関係しますか？

LIFE関連加算では、LIFEを用いた厚生労働省へのデータ提出とフィードバックの活用が算定の前提とされています。提出頻度は加算ごとに異なるため、厚生労働省の通知で確認する必要があります。

混同しやすいのは、LIFE関連加算と生産性向上推進体制加算が別のものだという点です。前者は利用者の状態のデータ提出、後者はテクノロジーの導入と業務改善が軸です。

### LIFE関連加算の基本的な考え方を示す通知

厚生労働省は「科学的介護情報システム (LIFE) 関連加算に関する基本的考え方並びに事務処理手順及び様式例の提示について」という通知を出しています。

東京都福祉局の解説では、その趣旨を次のように説明しています。科学的に効果が裏付けられた自立支援・重度化防止に資する質の高いサービス提供の推進を目的とし、LIFEを用いた厚生労働省へのデータ提出とフィードバックの活用による、PDCAサイクル・ケアの質の向上を図る取組、というものです。

出典: 東京都福祉局「科学的介護情報システム (LIFE) の活用等について」（https://www.fukushi.metro.tokyo.lg.jp/kourei/hoken/kaigo_lib/life-kaigo ）

つまり、提出するだけでは趣旨を満たしません。返ってきたフィードバックを計画の見直しに使うところまでが求められます。

なお加算ごとの提出頻度については、厚生労働省の通知を確認するよう案内されています。頻度は加算によって異なるため、本記事では具体的な回数を示していません。御社が算定する加算の通知で確認してください。

### 生産性向上推進体制加算との関係

生産性向上推進体制加算は、LIFEへの提出とは別の枠組みです。単位数と要件は次のとおりです。

| 区分 | 単位数 | 主な要件 |
| --- | --- | --- |
| 加算 (II) | 月額10単位 | 委員会を設置し、見守り機器等のテクノロジーを1つ以上導入 |
| 加算 (I) | 月額100単位 | 加算 (II) の要件に加え、見守り機器・インカム等・介護記録ソフト等の3種類すべてを導入 |

加算 (I) では、見守り機器は全居室に設置し、インカム等は同一時間帯に勤務する全介護職員が使用することが求められます。あわせて1年以内ごとに1回、業務改善の取組による効果を示すデータをオンラインで提出する必要があります。

出典: 公益財団法人介護労働安定センター「生産性向上のための委員会と生産性向上推進体制加算 解説資料 Ver.3.0」

委員会の開催については、令和6年度の介護報酬改定で義務付けられました。対象は施設系・居住系・多機能系・短期入所系のサービスを提供する事業所です。3年間の経過措置があり、令和8年度末（2027年3月31日）までは努力義務として扱われます。開催頻度は少なくとも3か月に1回以上とされています。

### システムに任せられる範囲と人が行う範囲

記録システムに任せられるのは、データの作成と出力までです。判断と活用は人が行います。

1. システムが担う範囲は、記録の入力、様式に合わせたデータの生成、CSVの出力です
2. 人が担う範囲は、フィードバックの読み取り、計画の見直し、委員会での検討です
3. 議事録と効果を示すデータの保管は、運用で決める部分です

要件を書くときは、この線引きを先に共有してください。加算を取るために必要な作業のすべてがシステムで済むと考えると、提案の範囲がずれます。

## 個人情報と補助金の観点で決めておくことは？

個人データの取扱いを委託先とどう取り決めるか、補助金を使う場合に補助要件を満たす構成にするか、この2点を発注前に決めます。後から変えると構成のやり直しになります。

どちらも、決まっていないと見積もりの前提が変わる項目です。開発が始まってから判明すると、設計に戻ることになります。

### 個人データの取扱いと委託先の取り決め

介護記録は要配慮個人情報を含みます。要配慮個人情報とは、病歴や心身の状態のように、取扱いに特別の配慮を要する個人情報のことです。

この扱いについては、厚生労働省と個人情報保護委員会の「医療・介護関係事業者における個人情報の適切な取扱いのためのガイダンス」が定めています。平成29年4月14日の通知で、令和8年4月1日に最終改正されています。

出典: 個人情報保護委員会・厚生労働省「医療・介護関係事業者における個人情報の適切な取扱いのためのガイダンス」（https://www.ppc.go.jp/personalinfo/legal/iryoukaigo_guidance/ ）

ガイダンスが定めているのは、次の4点です。

1. 安全管理措置
2. 従業者の監督
3. 委託先の監督
4. 漏えい等の報告

要件に落とすときは、3番目が起点になります。開発会社とクラウド事業者のどちらも委託先にあたるためです。決めておくことは次のとおりです。

| 決める項目 | 具体的にみる点 |
| --- | --- |
| データの保管場所 | 国内か国外か、どの事業者の環境か |
| 開発時のデータ | 本番の記録を開発環境で使うのか、加工したものを使うのか |
| 端末の紛失時 | 遠隔でデータを消せるか、ログインを止められるか |
| 報告の経路 | 漏えいを把握したとき、誰が誰に何分以内に伝えるか |

つまずきやすいのは2番目です。動作確認のために実際の記録を渡すと、委託先の監督の範囲が広がります。加工したデータで足りるかを、要件の段階で決めてください。

### ICT導入支援事業の補助要件との関係

補助金を使う場合は、自治体が実施する介護サービス事業所ICT導入支援事業の要件を先に確認します。補助の対象となる介護ソフトに条件が付くためです。

公表されている条件には、次のものが含まれます。

1. ケアプラン連携標準仕様に準拠していること
2. サービス類型に応じて、居宅サービス計画書とサービス利用票のCSVファイルの出力と取込の機能を実装していること

出典: 千葉県「介護テクノロジー定着支援事業費補助金」、愛知県「介護事業所ICT導入支援事業」

また補助の対象は、厚生労働省と経済産業省が定める「介護テクノロジー利用の重点分野」に該当する介護ソフト等の導入経費とされています。

出典: 鹿児島県「令和7年度介護サービス事業所ICT導入支援事業」

つまり、LIFEへの提出だけを満たす構成では、補助の条件を満たさない場合があります。ケアプラン連携標準仕様への準拠が必要かどうかで、要件の範囲が変わります。補助金の利用を考えているなら、御社の自治体の要件を先に取り寄せてください。

なお補助率や上限額、締切は自治体と年度によって異なります。金額の判断は、必ず御社の自治体の公募要領で確認してください。

## 実装でつまずきやすいのはどこですか？

文字コードの取り違えによる文字化けと、空欄と削除の区別です。この2つは仕様書に明記されているにもかかわらず、要件から漏れやすい箇所です。

当社が業務システムを実装してきた経験では、外部の仕様に合わせる開発で手戻りが出るのは、機能の作り込みではなくこの種の形式の取り違えです。検収前の試験の設計で防げます。

### 文字化けは検収前の試験で見つけます

仕様書はファイルエンコードをUTF-8またはShift-JIS（MS932）のいずれかと定めています。改行コードはCR-LFまたはCRです。

問題は、開発環境の既定値がこれと違う場合です。多くの環境ではLFが既定になっています。出力の設定を明示しなければ、LFで出力されます。

検収前に次の試験を入れてください。

1. 実際の利用者名を含むデータで出力し、取込まで通します。所要時間の目安は半日です。
2. 氏名に旧字体や外字を含む利用者のデータを1件以上含めます。
3. 出力したファイルの改行コードを、テキストエディタの表示で確認します。

つまずきやすいのは2番目です。試験用に作った架空の氏名だけでは、文字化けが表に出ません。実際の記録を使う場合は、前述の委託先の監督の取り決めに沿って扱ってください。

### 空欄のまま送るのか、値を消すのか

仕様書では、空の値と半角空白の意味が異なります。前述のとおり、半角空白はデータ削除目的の特殊処理としてNullに置き換えられます。

実装で問題になるのは、記録画面の操作とCSVの出力が対応していない場合です。

| 事業所側の意図 | CSVで出すべき形 |
| --- | --- |
| まだ入力していない | 空値（連続したカンマ） |
| 入れた値を消したい | 半角空白 |
| 空白そのものが値 | 全角空白、または2つ連続した半角空白 |

記録画面で入力欄を空にしたとき、システムがどちらで出力するのかを確認してください。区別されていないと、未入力のつもりが前回の値の削除として送られます。

この不具合は、1回目の提出では気づきません。2回目以降の更新で、前に送った値が消えて初めてわかります。試験の設計では、同じ利用者について2回続けて出力する手順を入れてください。

### 様式の版が上がったときの改修範囲

CSV連携仕様は更新されます。本記事で確認できた最新は3.10版で、令和8年5月付です。それ以前には3.00版が公開されていました。

版が上がったときに必要な作業は、内容によって変わります。

1. 項目が追加された場合は、記録画面と出力の両方に手を入れます
2. 項目の桁数や区分だけが変わった場合は、出力側の修正で済むことがあります
3. 新しいインターフェースが追加された場合は、対応するかどうかの判断が先にあります

前述のとおり、要件には版が上がった場合に改修の要否を判定して見積もりを出す手続きを書いておきます。金額を先に決めることはできませんが、判定までの期限は決められます。

## 段階的に進めるとしたら、どの順番が現実的ですか？

算定する加算と様式の確定、記録項目の対応づけ、CSV出力の実装、取込の試験、この順に進めるのが現実的です。出力の実装から始めると、対応づけの抜けが後から出ます。

順番を守る理由は、前の段階の成果物が次の段階の入力になるからです。様式が決まらなければ対応づけができず、対応づけがなければ出力の仕様が書けません。

| 段階 | やること | 担い手 | 開発の必要性 |
| --- | --- | --- | --- |
| 第1段階 | 算定する加算と提出する様式を確定する | 事業所 | 不要 |
| 第2段階 | 様式の項目といまの記録項目を突き合わせる | 事業所 | 不要 |
| 第3段階 | 不足する記録項目を追加し、CSV出力を実装する | 外注先 | 必要 |
| 第4段階 | 取込の試験と、2回目の更新の試験を行う | 事業所と外注先 | 必要 |

第1段階と第2段階は、事業所側だけで進められます。ここまでを済ませてから発注すると、対応する様式とインターフェースが確定した状態で見積もりを取れます。

所要時間の目安として、第1段階と第2段階は合わせて数日から2週間です。第3段階以降は、対応する様式の数によって変わります。

つまずきやすいのは、第2段階を外注先に任せてしまうことです。記録の運用は事業所ごとに違います。誰がいつ何を入力しているかは、外部からは見えません。突き合わせの表は事業所で作ってください。

### 記録と提出で同じ内容を二度書いているなら、仕組みに移せます

同じ内容を、記録と申し送りと提出用の様式にそれぞれ書き写している事業所は少なくありません。書類作成に時間を取られ、その分だけ利用者に向き合う時間が減ります。

原因は、担当者の作業量ではありません。記録の項目と提出する様式の項目が対応づけられていない構造にあります。対応づけを先に決めれば、入力を1回にまとめられます。

当社は実装者が要件から関わります。厚生労働省のCSV連携仕様を読んだうえで、どの様式まで自動で出力できるかを先にお伝えできます。既存の介護ソフトを入れ替えずに、提出データを作る部分だけを作る構成も検討できます。

まず自事業所の状況を整理したい場合は、[無料診断](/diagnostic)をご利用ください。要件の書き方を先に知りたい場合は、[DXガイドブック](/guidebook)で外注前に決める項目を確認できます。補助金の利用を考えている場合は、[補助金の対象要件](/subsidy)もあわせてご覧ください。

## よくあるご質問

この記事に関して多い質問と回答をまとめます。

### 介護ソフトを入れ替えずに、LIFEへの提出データだけを別の仕組みで作れますか？

作れる場合があります。判断の分かれ目は、いま使っている介護ソフトから記録データを取り出せるかどうかです。

確認する順番は次のとおりです。まず介護ソフトの提供元に、記録データの出力機能があるかを問い合わせます。出力できる場合は、その形式を確認します。そのうえで、出力したデータからLIFE向けのCSVを作る部分だけを外注する構成が取れます。

出力機能がない場合は、記録の入力から作り直す構成になります。この違いで費用は大きく変わります。発注の前に必ず確認してください。

### LIFEのCSV連携仕様の版が上がったら、システムの改修は必要になりますか？

必要になる場合があります。ただし改修の範囲は、上がった版の内容によって変わります。

項目が追加された場合は、記録画面と出力の両方に手を入れます。桁数や区分だけが変わった場合は、出力側の修正で済むことがあります。前述のとおり、契約時には版が上がったときに改修の要否を判定し、見積もりを提示する手続きを決めておいてください。

### 記録を音声入力にすると、LIFEへの提出まで自動でつながりますか？

自動ではつながりません。音声入力は、記録を入力する手段のひとつです。入力した内容が様式の項目に対応づけられていなければ、提出用のデータにはなりません。

順番としては、様式の項目と記録項目の対応づけを先に決めます。そのうえで、対応づけた項目を音声で埋められるようにする、という設計になります。音声入力を先に導入しても、提出の作業は減りません。

### LIFEへのデータ提出は、どれくらいの頻度で行う必要がありますか？

頻度は加算ごとに異なります。本記事では具体的な回数を示していません。

東京都福祉局の解説では、加算ごとの提出頻度について厚生労働省の通知を確認するよう案内されています。御社が算定する加算の通知で確認してください。

出典: 東京都福祉局「科学的介護情報システム (LIFE) の活用等について」（https://www.fukushi.metro.tokyo.lg.jp/kourei/hoken/kaigo_lib/life-kaigo ）

### 提出したデータのフィードバックは、どう使えばよいですか？

計画の見直しに使います。厚生労働省の通知の趣旨は、データ提出とフィードバックの活用によってPDCAサイクルとケアの質の向上を図る取組と説明されています。

つまり、提出して終わりではありません。返ってきた内容を読み、必要に応じてサービス計画を見直すところまでが求められます。この読み取りと判断は人が行う部分です。システムに任せられるのは、データの作成と出力までです。
