# リニューアルの計測引き継ぎ｜発注で指定する項目

## リニューアルで計測が途切れるのは、どこで起きる？

途切れるのは、計測タグの再設置、コンバージョンの設定、Search Consoleの所有権とアドレス変更の3箇所です。いずれも発注時に指定しなければ引き継がれません。デザインや文章の確認に目が向くため、ここは抜けやすい箇所です。

### 計測が途切れる3つの箇所

| 箇所 | 何が起きるか | 誰の作業になりやすいか |
|---|---|---|
| 計測タグの設置 | 新しいページにタグが入らず、アクセスが記録されない | 制作会社。ただし指定がないと入れない |
| コンバージョンの設定 | 問い合わせ完了の判定が外れ、件数が0になる | 自社。URLやイベント名が変わると再設定が必要 |
| Search Consoleの所有権とアドレス変更 | 検索の数字が新しいサイトに引き継がれない | 自社。権限の付与と解除の判断も含む |

このうち2番目が最も見落とされます。問い合わせ完了ページのURLが変われば、以前の設定はそのURLを待ち続けます。画面上はエラーにならないため、件数が0のまま気づかれません。

### 途切れたことに後から気づく理由

計測の不備は、公開直後には目に見えません。アクセスが減ったのか、計測が止まったのかを見分けるには、両方のデータを並べる必要があります。気づくのは、月次の報告を作る段階か、社内から「問い合わせが来ているのに数字が0だ」と指摘が入ったときです。

さらに、気づいた時点で過去にさかのぼって記録することはできません。計測していなかった期間は、空白のまま残ります。だからこそ、公開前に指定と確認を終えておく必要があります。指定する項目は次のH2で整理します。

## 発注時に指定する項目は？

計測の引き継ぎは、タグの設置、コンバージョンの定義、権限、公開前後の確認の4つを仕様として書面に指定します。口頭で「計測はそのままで」と伝えるだけでは、どちらの作業かが決まりません。

### 指定する項目の一覧

1. **計測タグを入れるページの範囲**（所要時間の目安: 30分）。全ページか、一部を除くかを指定します。つまずきやすい点は、問い合わせ完了ページと採用ページのように後から追加される画面が範囲から漏れることです。
2. **既存の測定IDを使うかどうか**（同: 15分）。同じIDを使えば過去のデータと地続きになります。新しく作ると、以前のデータは別の場所に残ります。
3. **コンバージョンの定義**（同: 1時間）。問い合わせ完了を何で判定するか（完了ページの表示か、送信のイベントか）を決め、新しいサイトでのURLまたはイベント名を指定します。つまずきやすい点は、URLが変わったのに以前の条件が残り、件数が0になることです。
4. **権限の付与と解除**（同: 30分）。制作会社に渡す権限の範囲と、公開後に解除する時期を書いておきます。所有者の権限は自社に残します。
5. **公開前の確認**（同: 1時間）。テスト環境で計測が動くかを確認します。つまずきやすい点は、テスト環境のデータが本番の集計に混ざることです。混ざらない設定も同時に指定します。
6. **公開直後の確認**（同: 30分）。公開から数時間のうちに、アクセスとコンバージョンが記録されているかを確認する担当を決めます。
7. **確認結果の報告**（同: 15分）。検収の項目に含めるか、報告書で受け取るかを決めます。

### 自社で持つ作業と制作会社に任せる作業

| 作業 | 置き場所の目安 |
|---|---|
| タグの設置と設置範囲の実装 | 制作会社 |
| テスト環境での動作確認 | 制作会社（結果を報告してもらう） |
| コンバージョンの定義と設定 | 自社（URLやイベント名は制作会社から受け取る） |
| 権限の付与と解除 | 自社 |
| 公開直後の確認 | 自社と制作会社の双方 |

実装する側の感覚では、コンバージョンの設定を制作会社に任せきりにすると、公開後の検証で誰も中身を把握していない状態になります。設定は自社に置き、必要な情報（新しいURL、イベント名）を制作会社から受け取る形が、後の運用で困りません。

## 公開前に書き出しておくデータと、その期限は？

Search Consoleのデータは最大16か月で消えるため、比べたい期間がその内側に収まらない分は公開前に書き出します。Google Cloudの公式ブログは「Search Console stores up to sixteen months of data」と記載し、それより長く保存したい場合はBigQueryを使う方法を案内しています（出典: Google Cloud公式ブログ「Analyze Google Search data with BigQuery」）。

16か月より前の期間は、後から取り出せません。リニューアルの前年と比べたい場合は、公開前の書き出しが唯一の手段です。

### Search Consoleの保持期間と既定の表示期間

検索パフォーマンスレポートの既定の表示期間は過去3か月です。公式ヘルプには、過去3か月間のGoogle検索の検索結果におけるサイトのクリック数とインプレッション数のデータが表示されると書かれています（出典: Search Consoleヘルプ「検索パフォーマンスレポート」）。

| 項目 | 期間 |
|---|---|
| Search Consoleが保持するデータ | 最大16か月 |
| 検索パフォーマンスレポートの既定の表示期間 | 過去3か月 |

既定のままで見ている限り、保持されている16か月のうち3か月分しか確認していないことになります。書き出す前に、期間を広げて必要な範囲を確かめてください。

### GA4の保持期間の設定と、短い設定のまま公開した場合の影響

アクセス解析の側にも保持期間の設定があります。アナリティクスの公式ヘルプによると、ユーザ単位データ (キーイベントを含む) の保持期間は2か月または14か月、その他のイベントデータは2か月、14か月、26か月、38か月、50か月から選べ、26か月以上はアナリティクス360でのみ選べます（出典: アナリティクスヘルプ「データ保持期間」）。年齢、性別、インタレストカテゴリのデータには、設定に関係なく常に2か月の保持期間が適用されます。

2か月の設定のまま公開すると、公開前の数字は2か月後に消えます。保持期間を短縮した場合、影響するデータは次月の処理中に削除され、設定変更が反映されるまでに24時間かかります。設定を直すなら、公開の数日前ではなく、比べたい期間を決めた時点で確認しておく必要があります。

発注の仕様としては、書き出しの担当と期限を1行入れておくだけで足ります。「公開の2週間前までに、Search Consoleの検索パフォーマンスとアナリティクスの主要レポートを自社で書き出す」と決めておけば、公開作業と取り合いになりません。記録する指標の選び方そのものは別記事で扱っています。

## 一括エクスポートを設定すれば、過去分も残る？

残りません。BigQueryへの一括データエクスポートは設定した時点から先のデータを溜める仕組みで、過去分はさかのぼりません。公式ヘルプには過去データをエクスポートするという記述がなく、初期設定の前に過去データを確認する方法として、Search Console APIとレポートが挙げられています（出典: Search Consoleヘルプ「一括データエクスポート」）。

したがって、公開前の実績を残したい目的で一括エクスポートを設定しても、間に合いません。過去分はレポートまたはAPIからの書き出しで確保します。

### 設定から最初のエクスポートまでの時間と含まれる範囲

公式ヘルプによると、設定を正しく行うと最大48時間以内に最初のエクスポートが行われ、最初のエクスポートには当日のデータが含まれます（出典: Search Consoleヘルプ「一括データエクスポート」）。

| 確認したいこと | 公式ヘルプの記述 |
|---|---|
| 最初のエクスポートまでの時間 | 最大48時間以内 |
| 最初のエクスポートに含まれる範囲 | 当日のデータ |
| 過去分のさかのぼり | 記述なし（過去分はレポートまたはAPIで確認） |

### 設定に必要な準備と、長期保存を前提にする場合の着手時期

設定にはGoogle Cloud側の準備が必要です。公式ヘルプによると、BigQuery APIとBigQuery Storage APIを有効にし、サービスアカウントに「BigQuery ジョブユーザー」と「BigQuery データ編集者」の2つのロールを付与します。Cloudプロジェクトには、プロジェクト番号ではなくプロジェクトIDを入力します。

書き出したデータは、期限を設定しない限り蓄積され続けます。テーブル作成後にパーティションの有効期限を設定できますが、有効期限は14日以上にする必要があります（出典: Search Consoleヘルプ「一括データエクスポート」）。

16か月を超えて検索のデータを残す方針であれば、リニューアルとは切り離して早めに設定するのが筋です。実装する側の注意点として、設定の作業者と請求先が分かれる点があります。BigQueryの利用料は御社のGoogle Cloudのプロジェクトに発生するため、制作会社に設定を任せる場合も、プロジェクトの所有は自社に置いてください。

## ドメインを変える場合、追加で指定することは？

ドメインを変える場合は、Search Consoleのアドレス変更ツールとリダイレクトの保持期間が計測にも影響するため、期限を逆算して指定します。計測の引き継ぎは、アドレス変更の手続きと同じ日程の上に乗っています。

### アドレス変更ツールの有効期間とリダイレクトの保持期間

Search Consoleヘルプの「アドレス変更ツール」によると、移転をリクエストした後、Googleが旧サイトのシグナルを新サイトへ優先的に移す動作が続く期間は180日間です。同じヘルプは、少なくとも180日間はリダイレクトを維持し、Google検索からのトラフィックが残る間はさらに延長するよう案内しています（出典: Google Search Consoleヘルプ「アドレス変更ツール」）。

| 項目 | 期間 |
|---|---|
| 旧サイトのシグナルを優先的に移す動作が続く期間 | 180日 |
| リダイレクトを維持すべき最低期間 | 180日 |

このツールはドメインレベルのプロパティでのみ使用でき、旧プロパティと新プロパティの両方で所有者であることが前提です。つまり、制作会社に所有権を預けたままでは手続きが進みません。権限の指定を発注時に書いておく理由はここにもあります。

### 公開日から逆算する際に計測の作業を置く位置

JPドメイン名の管理指定事業者を変える場合、JPRSの案内によると、手続きに使う認証コード (AuthCode) の有効期限は発行日の翌日を1日目として35日後の23時59分59秒までです（出典: JPRS「ドメイン名の管理指定事業者の変更」）。期限が切れると最初からやり直しになります。

この35日と、公開後に続く180日を踏まえると、計測の作業は次の位置に入ります。

1. 公開の2週間前まで: データの書き出しと、コンバージョンの定義の確認
2. 公開の直前: Search Consoleで新しいプロパティの所有権を確認
3. 公開当日: 計測タグとコンバージョンの記録を確認
4. 公開後すみやかに: アドレス変更ツールの実行（旧新の両方で所有者である状態）
5. 公開後180日以上: リダイレクトの維持

実装する側で詰まりやすいのは、4番です。所有権の確認が済んでいないと、公開の勢いのまま進められず、数日空きます。その間の検索の数字は、旧サイトと新サイトに分かれて記録されます。ドメイン変更の手続き全体の段取りは別記事で扱っています。

## 公開後、どこまで比較できる？

前後の比較には仕様上の制約があり、保持できる期間比較の数や平均掲載順位の数え方を踏まえないと、数字の解釈を誤ります。比較できる範囲を先に把握しておけば、社内への報告でも説明に困りません。

### 期間比較の仕様と注意点

公式ヘルプによると、Search Consoleでは過去16か月間のデータが保持されます（出典: アナリティクスヘルプ「Search Console を Google アナリティクスに接続する」）。検索パフォーマンスレポートの既定の表示期間は過去3か月で、期間は日付フィルタで変更します（出典: Search Consoleヘルプ「検索パフォーマンス レポート (検索結果)」）。

比較の際に押さえておく点は4つあります。

1. **保持できる比較は1つだけ**。今週と先週のように異なる期間を比較できますが、一度に保持できる比較は1つのみで、新しい比較を追加すると既存の比較が置き換わります。
2. **平均掲載順位は母集団で動く**。表示のたびに最上位の順位を記録し、表示されたすべてのクエリにわたって平均した値です。期間によってクエリの顔ぶれが変わるため、平均掲載順位の増減だけで順位が上がったか下がったかは決められません。
3. **直近のデータは暫定値**。最新のデータはグラフ上に点線で表示され、その後数時間で変動することがあります。切り替えた直後の数日を比較に含めると、後から数字が動きます。
4. **集計の単位が項目で違う**。クエリ、国、デバイス、日付はプロパティごと、ページと検索での見え方はページごとの集計です。同じクエリで同一サイトの2件が出た場合も、表示回数は1回と数えられます。

### 計測が引き継がれたかを確認する手順

比較を始める前に、計測そのものが動いているかを確かめます。

1. 公開当日に、アクセスが記録されているかを確認します。
2. 問い合わせを1件テスト送信し、コンバージョンとして記録されるかを確認します。
3. Search Consoleで新しいプロパティのデータが入り始めたかを確認します。
4. 翌週、旧サイトのプロパティに数字が残っていないかを確認します。残っている場合はリダイレクトの漏れです。

このうち2番を飛ばすと、件数が0なのに気づきません。テスト送信の記録が本番の集計に混ざることを気にする場合は、記録を残したうえで報告に注記する形で足ります。期間比較そのものの読み方は別記事で扱っています。

## よくあるご質問

この記事に関して多い質問と回答をまとめます。

### GA4のタグは、リニューアルしても同じものを使い続けられますか？

同じ測定IDを使い続けられます。その場合、公開前と公開後のデータが同じ場所に入るため、期間をまたいで比べられます。新しく作ると以前のデータは別の場所に残り、並べて見る手間が増えます。どちらにするかを発注時に指定してください。

### 計測の設定は、どちらが用意するのが一般的ですか？

タグの設置は制作会社、コンバージョンの設定は自社という分け方が運用しやすいです。設定を制作会社に任せきりにすると、公開後に中身を把握している人が社内にいない状態になります。新しいURLやイベント名は制作会社から受け取り、設定は自社で行う形をおすすめします。

### 公開してから計測が止まっていたと気づいた場合、データは戻りますか？

戻りません。計測していなかった期間は空白のまま残ります。公開当日にアクセスとコンバージョンの記録を確認する担当を決めておくことが、唯一の対策です。

### Search Consoleの所有権は、制作会社に渡す必要がありますか？

作業のために権限を渡す場合でも、所有者の権限は自社に残してください。アドレス変更ツールは旧プロパティと新プロパティの両方で所有者であることが前提です（出典: Google Search Consoleヘルプ「アドレス変更ツール」）。所有権が制作会社側だけにあると、手続きが止まります。公開後に権限を解除する時期も、発注時に決めておきます。

### ドメインを変えると、過去の数字と比べられなくなりますか？

旧ドメインのプロパティに残っている範囲は参照できますが、同じ画面で連続した推移としては見られません。Search Consoleで保持されるのは16か月分です（出典: アナリティクスヘルプ「Search Console を Google アナリティクスに接続する」）。前後を1つの表で比べたい場合は、公開前に書き出して自社で突き合わせる形になります。

### テスト環境での計測は、本番の数字に混ざりませんか？

同じ測定IDをそのまま使うと混ざります。テスト環境を計測から除外する設定を、公開前の確認とあわせて指定してください。混ざった場合、該当期間の数字に注記を付ける以外の修正はできません。
