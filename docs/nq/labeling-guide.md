# 評価セットのラベリング基準書（2026-09-21 確定）

`eval/sessions.json` の正解（`expected`）を人が付けるときの基準。**この文書だけで正解を付けられる**ように、
軸ごとの判断基準と具体例、許容集合にしてよい条件、盲検の手順、記録の形式をまとめた。
`docs/nq/decisions-2026-09-21.md` 1章（オーナー決定）を正とし、`eval-label-review.md` 7章の判断基準の案を取り込んで確定したもの。
食い違いがあれば decisions が優先。

---

## 0. 前提

- 正解は **閲覧履歴から人が無理なく推測できること** だけ。推測できない軸は other／不明・その他／none／0 にする。
  「こういう人だろう」という想像で埋めない。根拠になるのは、流入元・見たページの題と種別・読み方・訪問回数だけ。
- 正解の使われ方（`eval/run.js`）。付け方に迷ったとき、何が評価に効くのかを知っておく。
  1. **決定一致率**（主指標）。人のラベルを確信度 1.0 としてルール表に通し、行2（営業→何も変えない）／行3（求職者→採用カード）／行4（同業者→関連記事）／行5以降（事業者・other→提案カード）の4分類がモデルの分類と同じか。
     つまり **visitor_type が最も効く**。
  2. **事業者への誤り件数**。人が 事業者 と付けたのに、決定が求職者向けか同業者向けになった件数（2件以下が完了条件）。
  3. 補助: 軸別の一致、カードの適合率、不安、cta_ok、stage の分布（人が 2 以上と付けた件数と、そのスコアの分布からしきい値を決める）。
- **モデルの回答に合わせて正解を直すことはしない。** 根拠は閲覧だけ。これは盲検（1章）で担保する。「モデルがそう答えたから」の修正は 0 件で、記録（5章）にそう書く。
- 1人が全件を同じ基準で通す。途中で基準を変えたくなったら、この文書を直してから最初のセッションに戻る。

## 1. 盲検の手順

### 1.1 開いてはいけないもの（ラベルを確定して記録するまで）
| 場所 | 理由 |
|---|---|
| `eval/results/` 以下の全ファイル、`eval/baseline.json` | モデルの回答そのもの |
| `docs/nq/eval-2026-09-21.md` | 回答の要約と数字 |
| `docs/nq/eval-label-review.md` | 3〜6章に回答の列がある。7章の案は本書に取り込み済みなので、開く必要がない |
| `docs/nq/open-decisions.md` の E7・D10・D11 | 回答の数字を含む |
| `node eval/run.js --provider jev` と `--provider stub` の出力 | 回答と選ばれたカードが出る。`--check`（形の検査だけ。モデルを呼ばない）は使ってよい |

### 1.2 開いてよいもの
| 場所 | 使い方 |
|---|---|
| `eval/sessions.json` の `id` `note` `request` | セッションの中身。旧 `expected` と旧 `alt` は、作業表を作るまで見ない（1.4） |
| `data/catalog-pages.json` | 記事以外のページの `title` と `type` |
| `build.js` の `const BLOG = [ ... ]` | 記事の `title` `desc` `category`。**読むだけ**（1行も編集しない） |
| `data/blocks.json` の `block_id` `target_url` `audience` | カードの行き先と対象（3.5 の手がかりの判断に使う） |
| `data/nq-labels.json` | ラベルの正式な文字列（付録 A に写してある） |
| 本書 | |

### 1.3 根拠にしないもの
- `data/catalog-articles.json` の `need` `industry` `audience` のタグ。自動付与の値で、判定の入力側にあるもの。正解の根拠にすると評価が循環する。記事の中身は題と `desc` から自分で読む。
- `sessions.json` の旧 `expected` と旧 `alt`（LLM の下書き）。作業表を付け終えたあとに、差分の記録のためだけに見る。
- `note` の解釈の部分。`note` はページ列の要約で、「発注の準備をしている」「気になっている」のような解釈が混ざっている。事実（どのページをどう読んだか）の部分だけを読む補助にする。
- モデルの癖・過去の結果・「たぶんこう答える」という予想。

### 1.4 作業の順番
1. **作業表を作る。** セッションごとに `id` `trigger` `ref` `visit` `device`、ページ列（着地 → 履歴 → 現在。それぞれ title・種別・読み方／到達）、`passed` を書き出す。
   `expected` は写さない。手で作っても、使い捨てのスクリプト（scratch に置き、コミットしない）で作ってもよい。
2. **id 順に全件を付ける。** 本書 2〜3章の順（読み方 → visitor_type → industry → need → stage → cards → concerns → cta_ok）で付け、集合にした行は理由を書く。
3. **揃えを確かめる。** 6章の型ごとに並べ、同じ型のセッションが同じ付き方になっているかを見る。違うなら、どちらが基準に沿っているかを本書で確かめて直す。
4. **旧 expected と突き合わせる。** 変えた行を 5.3 の形式で記録する。「下書きがそうだったから」は残す理由にならないし、「モデルがそう答えたから」は（見ていないので）起こりえない。
5. **v2 の形式（5.1）で `sessions.json` に書く。** `version` を 2 にし、旧フィールド（`relevant_cards` `best_card` `alt`）は使わない。
6. **高検討度の 10 件を足す（7章）。** 足した件も同じ手順で付ける。
7. `node eval/run.js --check` を通し、警告を潰す。
8. ここで正解を凍結し、評価担当に渡す。以後の変更は、5.3 の記録に行を足してからにする（結果を見ながら直さない）。

## 2. セッションの読み方

### 2.1 `request` のフィールド
| フィールド | 意味 | 根拠としての使い方 |
|---|---|---|
| `trigger` | T1 = 記事本文の 25% に達した時点。着地直後なら `history` は空／T2 = 2ページ目以降のページ表示直後／T3 = 現在のページを最後まで読んで滞在 | T1 の現在のページは「読み始めたところ」。T3 の現在のページは じっくり と同じ重み |
| `state.ref` | `google` `yahoo` `ai` = 検索／`sns`／`direct` = 直接／`other` = 外部リンクなど | 検索は「課題があって探している」寄り、SNS・直接・外部は「中身に引かれて来た」寄り（3.1） |
| `state.landing` | 着地ページ | 検索・直接で着いたページは「目的を持って来た」根拠 |
| `state.history[]` | 現在より前に見たページ。`read` は `deep`（じっくり）／`skim`（流し見）／`bounce`（途中離脱） | 2.4 の重み |
| `state.current` | いまのページ。`reach` は `top`（冒頭）／`half`（半分）／`end`（最後まで） | T1・T2 では実際にはほぼ `top`。「そのページに来た」ことが根拠 |
| `state.visit` | `first`（初回）／`return`（再訪） | 再訪は stage の根拠（3.4） |
| `state.device` | `sp`／`pc` | ラベルの根拠にしない |
| `state.passed` | 見送ったカード（表示されたが押されなかった） | そのカードは候補から外れる（3.5）。訪問者タイプの根拠にはしない |

### 2.3 記事の題の3分類
記事は、題（と `desc`）を読んで次の3つに分ける。**カテゴリ名（Web制作／技術／AI活用／DX 観察記／SEO／マーケティング／業種別）は目安にすぎない**。
カテゴリ「技術」に発注側向けの記事が多数あり、「AI活用」に作る側向けの記事がある。

| 分類 | こういう題 | 例（BLOG の実際の題） |
|---|---|---|
| **発注側向け** | 自社の意思決定のために読むもの: 費用・相場・見積・予算、進め方・手順・チェックリスト、業者の選び方・外注先の見極め、補助金、導入判断・活用ガイド、法規制や制度への自社サイトでの対応、業種別のやり方 | ホームページリニューアル費用｜見積もり内訳と補助金／ホームページ見積書の見方／Web制作のRFP作り方／制作会社を変えるリニューアル、引き継ぐもの一覧／小規模事業者持続化補助金でホームページ制作／ホームページリニューアル｜社内担当者がいない場合の進め方／Excel管理からの脱却｜業務システム化で解決できる課題と進め方／基幹システムの刷新・再構築／AIチャットボット業種別活用ガイド｜中小企業の導入判断／AI開発の外注先、設計レビュー体制の見極め方／受発注の電話・FAX脱却｜外注前に決める手順／女性活躍推進法の情報公表を自社サイトに載せる手順／クリニックのWeb集客 2026年版 完全ガイド |
| **作る側向け** | 実装する人のためのもの: 実装手順、コード・設定ファイル、API・ライブラリ・フレームワークの使い方、エラーの原因と解決、評価指標の測り方、モデルの学習、開発の裏側 | LLM安全対策の3層ガードレール｜NeMo・OWASPに基づく実装手順／LLMガードレール評価の精度測定｜4つの指標と実装手順／LLM攻撃検出の機械学習モデル、過学習を防ぐ3つのステップ／iOS NFC FeliCa読み取りが遅い原因と解決法｜Info.plist設定ガイド／AI画像データの構造化抽出、モデル選定方法 |
| **読み物・統計・時事** | 誰が読んでもおかしくないもの: 統計の解説、業界の観察・随想、ツールや技術の比較そのもの、時事 | 中小企業の生成AI活用率｜大企業との差を統計で解説／中小企業のサイバー攻撃被害割合｜警察庁・IPA統計／なぜ日本のDXはアメリカに2〜3年遅れているのか／AIO・LLMO対策に踊らされる前に／PoCで終わるAI案件と、本実装まで進むAI案件の違い／Web集客はまだまだ熱い |

**どちらにも読める題**がある（発注側にも作る側にも当てはまる）。例: ホームページ制作でCore Web Vitals対応、中小企業向け5ステップ／WordPress と Next.js（静的生成）を比較／URL移行で検索順位を下げない301リダイレクト完全ガイド／AI検索に引用される会社サイトの作り方｜LLMO対策の実装手順／中小企業向けLLMガードレール導入コスト／要件定義書のAIレビューで精度を上げる方法。
これらは 3.1 で集合にする。「どちらにも読める」と「読み物」は違う: 前者は目的のある2種類の読者が想定でき、後者は目的が読めない。

### 2.4 読み方の重み
| 読み方 | 重み | 使い方 |
|---|---|---|
| じっくり（deep）、最後まで（T3 の `reach: end`） | 根拠になる | すべての軸の根拠にしてよい |
| 検索・直接で着地したページ（途中離脱を除く） | 根拠になる | 目的を持って来たページ。着地直後の T1（履歴なし）は、着地記事の題と流入元だけで判断する |
| 現在のページ（`reach: top` / `half`） | 弱い根拠 | 「そのページに来た」ことは根拠になる（stage では流し見と同じ扱い）。ページの中身をどう読んだかは分からない |
| 流し見（skim） | 弱い根拠 | 流し見 1 回だけを根拠に、業種・不安・カードを **確定しない**。付けるなら集合にする（4章） |
| 途中離脱（bounce） | 根拠にしない | 例外: 採用情報・ゴールのように目的がはっきりしたページに検索・直接で着地した場合は、「そこに来た」ことだけ残す |
| SNS・直接・外部リンクからの着地 | 流入の性質だけ | 目的がある、とは言わない。記事1本のセッションでは other 側に傾ける（3.1） |

セッション全体では、**じっくり読んだページと現在のページが主題**を決める。流し見のページは主題にしない。
後半のページ（サービス・料金・実績・ゴール・採用情報）は、着地記事より訪問者タイプを強く決める（記事から入っても、料金や実績をじっくり読んだ人は事業者）。

## 3. 軸ごとの基準

### 3.1 visitor_type（5ラベル）

| ラベル（正式な文字列） | 定義 |
|---|---|
| `事業者` | 自社のサイト制作、AI導入、システム開発について、外部への依頼、進め方、費用の相場を調べている事業者。旧「情報収集中の事業者」と「発注検討中の事業者」は、どちらもこれ。検討の進み具合は stage で表す |
| `同業者・学習者` | Web制作、開発、マーケティングを仕事や学習として行っており、実装方法や技術の仕組みを学ぶために記事を読んでいる人 |
| `求職者・学生` | Nortiq Labs で働くこと、インターン、社内の様子に関心がある人 |
| `営業・売り込み` | 自社の商品やサービスを Nortiq Labs に売り込む目的で会社情報や連絡先を探している人。**閲覧だけでは確定しない**（下記） |
| `other` | 訪問の目的が閲覧から読めない人 |

#### 確定してよい条件
| ラベル | こう見えたら確定 |
|---|---|
| 事業者 | (a) 発注側向けの記事（2.3）に **検索** から着地して読んでいる。記事1本でよい。(b) サービス内容（S）・料金（P）・実績・声（W）・ゴール（G）のいずれかを じっくり 読んだ、または再訪で見ている。(c) 業種ソリューション・業種特化LP に検索・直接で着地した、または じっくり 読んだ。(d) 作る側向け以外の記事（発注側向け・どちらにも読める・読み物）から入って、S・P・W・G のページへ進んだ（現在のページでよい）。作る側向けの記事から入った場合は下の集合の表 |
| 同業者・学習者 | 作る側向けの記事（2.3）を読んでいて、S・P・W・G のページを見ていない。流入元は問わない（技術記事は SNS から読まれることが多い） |
| 求職者・学生 | 採用情報（`/recruit`）を じっくり 読んだ、または検索・直接で採用情報に着地した（途中離脱でもよい） |
| other | (a) 読み物・統計・時事の記事1本だけで、SNS・直接・外部リンクから来ている。(b) 記事を途中離脱しただけで、ほかに根拠になるページが無い。(c) トップ・お知らせ・自社プロダクト・規約類だけ。(d) 会社情報だけ（この場合は集合にする。下記） |

#### 集合にする条件（4章の一般則に加えて）
| 状況 | 付け方 |
|---|---|
| 発注側向けの記事1本だが、SNS・直接・外部リンクから来た | `["事業者", "other"]`。目的があるとも、中身に引かれただけとも言える |
| 読み物・統計・時事の記事1本だが、検索から来た | `["other", "事業者"]`。統計を検索する人は事業者にも学生・書き手にもいる |
| どちらにも読める題（2.3）の記事1本 | `["事業者", "同業者・学習者"]`。流入元は問わない |
| 作る側向けの記事 → 自社プロダクト（`/product-*`）へ進んだ | `["同業者・学習者", "事業者"]`。プロダクトの導入を調べる事業者とも読める |
| 作る側向けの記事 → S・P・W を **流し見**、または S・P・W が現在のページ | `["同業者・学習者", "事業者"]`。じっくり なら 事業者 で確定 |
| 採用情報を **流し見** しただけ | 残りのページから決めたラベルに `"求職者・学生"` を足す。例: 発注側向けの記事を じっくり → 採用情報 流し見 → `["事業者", "求職者・学生"]`、記事を途中離脱 → 採用情報 流し見 → `["other", "求職者・学生"]` |
| 採用情報を じっくり、かつ S・P を じっくり | `["事業者", "求職者・学生"]`。両方に根拠がある |
| 会社概要・お知らせ・サイトマップ・トップ だけ | `["other", "営業・売り込み"]` |
| 上に加えてスタッフ紹介を見ている | `["other", "営業・売り込み", "求職者・学生"]`。社内の人に関心がある動きは求職者にも見える |
| 会社情報だけでなく実績も見ている（サービス・料金は無し） | 実績が じっくり なら `["事業者", "other"]`（実績を読み込む動きは売り込みの手がかりではない）、流し見・途中離脱なら会社情報だけの場合と同じ |

**営業・売り込みを確定しない理由。** 会社概要やスタッフ紹介を見る動きは、求職者・取引先・知人・同業者でも同じで、売り込み目的と分かる手がかりが状態に無い。
問い合わせフォームの種別のような閲覧以外の手がかりが状態に入るまで、営業・売り込み は集合の中にだけ現れる。

**事業者 と other の線引き（記事1本のセッション）。** 次の2つで決める。
1. 題が「自社の意思決定のために読む」ものか（2.3 の発注側向け）→ 事業者 側。読み物・統計・時事 → other 側。
2. 流入元。検索 → 目的がある → 事業者 側。SNS・直接・外部リンク → 中身に引かれて来た → other 側。

2つが同じ側なら確定、割れたら集合。記事1本で 事業者 を確定できるのは「発注側向けの題を検索で引いた」場合だけ。

**後半のページが決める例。** 作る側向けの記事 → 料金 じっくり → 事業者（確定）。発注側向けの記事 → 採用情報 じっくり → `["事業者", "求職者・学生"]`。発注側向けの記事を途中離脱 → トップ → other（確定。途中離脱は根拠にならず、トップは何も言わない）。

### 3.2 industry（業種）
| 付け方 | 条件 |

| 確定 | 業種のページ（下の表）を じっくり 読んだ／検索・直接で着地した。または業種名が題に入る記事を じっくり 読んだ／検索で着地した |
| 集合 `["<業種>", "不明・その他"]` | 業種のページを 流し見 1回しただけ、または現在のページ（`reach: top` / `half`）としてあるだけ。業種名入りの記事を 流し見 しただけ |
| `不明・その他` | 業種のページを途中離脱しただけ。業種のページも業種名入りの記事も無い。2つの業種が同じ重みで出てくる（じっくり と 流し見 なら じっくり のほうを採る） |

| ページ・題 | 業種 |
|---|---|
| `/solution-clinic` `/works-clinic`、題に クリニック・医療・歯科 | `クリニック・医療` |
| `/solution-realty` `/works-realty`、題に 不動産・売却査定 | `不動産` |
| `/solution-build` `/works-build`、題に 建設・工務店・建築・リフォーム | `建設・工務店` |
| `/solution-hr` `/works-hr`、題に 人材紹介・派遣・求人サービス | `人材` |
| `/solution-retail` `/works-retail`、題に 小売・EC・ネットショップ | `小売・EC` |
| `/works-infra`、題に 製造・インフラ | `製造・インフラ` |
| `/service/kanri-dantai`、題に 監理団体・登録支援機関・協同組合・技能実習・特定技能・外国人材 | `外国人材（監理団体・登録支援機関・協同組合）` |
| 題に 介護・福祉・障害福祉 | `介護・福祉` |

| `/works-ai` `/works-lp-*` `/works-video` `/works` | 業種は分からない |

- 事業者 を含まないラベル（同業者・求職者・other の確定）のセッションは `不明・その他`。訪問者の「事業の業種」を聞く軸なので、作る側や求職者には当てはまる業種が無い。
- 業種の記事を読んだのが「同業者・学習者」（例: クリニック向けの制作手法を学ぶ制作者）と読める場合も、visitor_type が 事業者 を含むなら業種は付ける。

### 3.3 need（解決したいこと）
事業者 を含むラベルのセッションだけ付ける。**着地記事のタグではなく、セッションの主題（2.4）から読む。**

| 主題（題・ページ） | need |
|---|---|
| サイトを新しく作る、制作費用、ローンチ、RFP、ホームページが無い会社 | `新規サイト制作` |
| リニューアル、作り直し、リニューアルの失敗・費用・検収・引き継ぎ、無料診断（`/diagnostic`。今あるサイトの診断） | `サイトリニューアル` |
| 「ホームページ制作」「Web制作」「制作会社の選び方」「見積書の見方」「格安制作」など、新規かリニューアルか分からない | `["新規サイト制作", "サイトリニューアル"]` |
| 採用サイト、求人、応募、`/feature-recruit`、`/service/recruit-site` | `採用強化` |
| SEO、検索流入、AI検索・LLMO、記事更新、CMS、Googleビジネスプロフィール、`/feature-cms` | `集客・SEO` |
| LP、広告、CPC、費用対効果、問い合わせ率、`/feature-lpo` | `LP制作・改善` |
| チャットボット、問い合わせ対応のAI、AIでの記事作成、生成AI活用の導入判断、`/chatbot` | `AI導入・チャットボット` |
| 業務システム、基幹システム、Excel脱却、受発注のデジタル化、自動化、データ活用、CRM、予約システム、システム外注、`/dx` | `業務システム・DX` |
| 保守、運用、更新費用、公開後、`/support` | `保守・運用` |
| 補助金、`/subsidy` | `補助金活用` |
| 業種ソリューション（`/solution-*`）だけが根拠 | `["新規サイト制作", "サイトリニューアル"]`（パッケージは集客・予約・管理を含むサイト構築なので） |
| 業種特化LP `/service/kanri-dantai` | `["新規サイト制作", "サイトリニューアル"]` |
| 料金・実績・資料・会社情報だけで主題のページが無い | `other`（何を頼みたいかが読めない） |

- 主題が2つあり、どちらを頼みたいか分けられないときだけ集合（最大2）。例: 「持続化補助金でホームページ制作」→ `["補助金活用", "新規サイト制作"]`。「予約システムの開発費用」→ `業務システム・DX`（費用は主題ではなく不安。3.6）。
- 流し見のページの主題は need にしない。じっくり読んだページと現在のページで決める。
- visitor_type が `["事業者", ...]` の集合なら、need は上の表で決めた値に `"other"` を足した集合にする（事業者でなければ other だから。この場合だけ3つになりうる）。例: 統計の読み物を検索で引いた `["other", "事業者"]` → need `["other", "AI導入・チャットボット"]`。「ホームページ制作でCore Web Vitals対応」の `["事業者", "同業者・学習者"]` → `["新規サイト制作", "サイトリニューアル", "other"]`。
- 事業者 を含まないラベル（同業者・求職者・営業＋other・other の確定）は `other`（確定）。作る側向けの記事の主題は、その人の「自社の課題」ではない。

### 3.4 stage（検討度 0〜3）
定義（decisions 2章）: 0「記事だけ読んでいる」／1「サービス概要か料金を流し見した」／2「料金・実績・サービス内容をじっくり読んだ、または再訪して料金を見た」／3「無料診断か資料請求に到達した」。
これを、2.2 の群（S・P・W・G）で機械的に決める。**整数1つ。集合にしない。**

| stage | 条件（上から順に見て、最初に当てはまるもの） |
|---|---|
| 3 | G（`/diagnostic` `/guidebook` `/subsidy`）が履歴か現在のページにある（読み方は問わない。「到達」が条件） |
| 2 | S・P・W のどれかを じっくり 読んだ（履歴の deep、または T3 の現在のページ）。または `visit` が 再訪 で、P が履歴（途中離脱を除く）か現在のページにある |
| 1 | S・P・W のどれかが履歴（流し見）か現在のページ（`reach: top` / `half`）にある |
| 0 | 上のどれにも当てはまらない（記事だけ。会社情報・採用情報・お知らせ・トップ・プロダクトは数えない） |

- 群に入れる判断で迷いやすいもの: `/voice`（声）は W。`/support` は S。`/subsidy` は G（相談ページ。到達は資料請求と同じ重み）。`/quick-diagnosis` は「その他」で数えない。
- 記事の内容は stage に効かない。RFP や見積書の記事を じっくり 読んでも、サービスのページを見ていなければ 0。発注の準備をしている人でも、当社のページでの行動がまだ無い、という定義。
- **事業者 を含まないラベルは 0**（約束事）。同業者・求職者・営業＋other・other の確定には当てはまる段階が無い。visitor_type が `["事業者", ...]` の集合なら上の表で決める。
- S・P・W を途中離脱しただけなら、そのページは無かったものとして数える（0 か、ほかのページで決まる値）。

### 3.5 cards（正解のカード）
`cards.relevant` と `cards.best` の2つを分けて付ける。定義が違う。

| フィールド | 定義 | 形 |
|---|---|---|
| `relevant` | **閲覧の手がかりから当てはまると言えるカード**（状態にそのカードの対象だと言える手がかりがあるカード）の全部 | 配列。無ければ `[]` |
| `best` | `relevant` の中で、**その閲覧の次に読むと最も役に立つカード** | 1つの ID、同点なら ID の集合（最大2）、`relevant` が空なら `"none"` |

`best` は必ず `relevant` の中から選ぶ。「手がかりは無いが次に見せたい」カードは、どちらにも入れない（手がかりが無ければ、当てはまるとも役に立つとも言えない）。

#### 候補（この中からだけ選ぶ）
`selectable` な提案カード 13 枚（付録 B）から、次を除いたものが候補。
- 現在のページを指すカード（例: `/pricing` に居るなら `sg-pricing`）。
- 見たページ（履歴。読み方は問わない）を指すカード。`sg-works` は `/works` か、その訪問者の業種の `/works-<業種>` を見ていれば外す。`sg-solution` は業種の `/solution-<業種>` を見ていれば外す。
- `passed` にあるカード。
- `sg-solution`: 業種が確定（集合ではない）で、その業種のパッケージがある（クリニック・医療／不動産／建設・工務店／人材／小売・EC）ときだけ候補。
- `sg-recruit`: 求職者・学生 だけが対象。求職者と分かるのは採用情報を見たあとなので、そのカードは「見たページ」として外れる。実際には正解に入らない。
- `sg-guidebook` `rs-*` `ct-*` `rl-related` は関連度を聞かないカード。正解に書かない。

#### 手がかりの表（このカードが「当てはまる」と言える閲覧）
「題に」は、じっくり 読んだ記事・検索で着地した記事・現在の記事の題。流し見・途中離脱の題は手がかりにしない。

| カード | 行き先 | 手がかり |
|---|---|---|
| `sg-web` | `/web` | need が 新規サイト制作／サイトリニューアル（集合を含む）。または need が 採用強化 で採用サイトの制作を調べている。または need が other で stage 2 以上（主題は読めないが制作の外注を検討している） |
| `sg-pricing` | `/pricing` | 題に 費用・相場・見積・料金・予算・価格・格安・実質負担。または 事業者 で stage 2 以上（料金をまだ見ていない） |
| `sg-works` | `/works`（業種版あり） | 事業者 で stage 2 以上（実績をまだ見ていない）。または題に 事例・実績・制作会社の選び方・外注先の見極め方 |
| `sg-subsidy` | `/subsidy` | 題に 補助金 |
| `sg-support` | `/support` | 題に 保守・運用・更新費用・公開後。または need が 保守・運用 |
| `sg-solution` | `/solution-<業種>` | 業種が確定していて、その業種のパッケージがあり、まだ見ていない |
| `sg-cms` | `/feature-cms` | need が 集客・SEO。または題に SEO・検索流入・AI検索・LLMO・記事更新・CMS・WordPress |
| `sg-lpo` | `/feature-lpo` | need が LP制作・改善。または題に LP・広告・CPC・問い合わせ率 |
| `sg-chatbot` | `/chatbot` | need が AI導入・チャットボット。または発注側向けの題に チャットボット・問い合わせ対応AI・AIでの記事作成。作る側向けの LLM の記事は手がかりにしない |
| `sg-dx` | `/dx` | need が 業務システム・DX。または発注側向けの題に 業務システム・基幹・Excel脱却・自動化・システム外注・機械学習の導入。作る側向けの記事は手がかりにしない |
| `sg-recruit-site` | `/service/recruit-site` | 業種が 建設・工務店／運送・物流／介護・福祉 で、採用サイト・求人・応募が主題 |
| `sg-kanri-dantai` | `/service/kanri-dantai` | 業種が 外国人材（監理団体・登録支援機関・協同組合） |
| `sg-recruit` | `/recruit` | （実際には正解に入らない。上記） |

#### `best` の選び方（上から順）
1. 読んでいる題の問いに直接答えるページ。費用の記事 → `sg-pricing`、補助金の記事 → `sg-subsidy`、保守の記事 → `sg-support`、業種の記事・業種の実績 → `sg-solution`。
2. 業種が確定していて業種パッケージが未閲覧なら `sg-solution`（汎用のサービスより業種のほうが役に立つ）。
3. 主題のサービス（`sg-web` `sg-chatbot` `sg-dx` `sg-cms` `sg-lpo` `sg-recruit-site` `sg-kanri-dantai`）。
4. 主題のサービスをもう見ていれば、料金 → 実績 の順で、まだ見ていないもの。
5. どちらが上とも言えなければ集合（最大2）。

#### 訪問者タイプとの関係
- 同業者・学習者／求職者・学生／`["other", "営業・売り込み", ...]`／other の確定: `relevant: []`、`best: "none"`。手がかりの表は 事業者 の需要を前提にしているので、当てはまるカードが無い。
- `["事業者", "other"]` の集合: 事業者 として表を当てる（目的が読めない人にも、手がかりのあるカードなら見せてよい）。
- `["事業者", "同業者・学習者"]` や `["事業者", "求職者・学生"]` の集合: `relevant` は表のとおり、`best` は `["<カード>", "none"]` の集合にする（事業者でなければ何も出さないのが正しいため）。

#### 迷いやすいもの
- `best` が `"none"` なのに `relevant` が空でない、`best` が `relevant` に無い、は形の誤り（`--check` が警告する）。
- 同じ問いに答えるカードが2枚（費用の記事で `sg-pricing` と `sg-subsidy` の両方が題にある）→ `relevant` に両方、`best` は題の主のほう。主が決まらなければ集合。
- 記事1本の T1 でも、題に手がかりがあればカードは付く（費用の記事に着地 → `sg-pricing`）。
- 見送ったカード（`passed`）は候補から外れるが、その事実を「もう興味が無い」とは読まない。ほかのカードの選び方は変えない。

### 3.6 concerns（不安）
事業者 を含むラベルのセッションだけ。当てはまるものを全部（順不同）。**流し見だけ・途中離脱だけの根拠では付けない。** 集合にしない（迷ったら付けない）。

| キー | 付ける条件 |
|---|---|
| `cost` | 費用・相場・見積・予算・価格・格安・実質負担・補助金 を題にする記事を じっくり 読んだ／検索で着地した／いま読んでいる。または料金プランを じっくり 読んだ／現在のページ／再訪で見ている |
| `trust` | 実績・声・会社概要のどれかを じっくり 読んだ／現在のページ。または 制作会社の選び方・外注先の見極め方・格安制作の注意点・口コミ のような依頼先選びの題の記事を じっくり 読んだ／検索で着地した |
| `scope` | 進め方・要件定義・RFP・仕様確認・引き継ぎ・社内担当者がいない・外注前に決めること を題にする記事を じっくり 読んだ／検索で着地した。「選び方」は trust 側 |
| `schedule` | 納期・期間・最短○か月・ローンチ・遅延 を題にする記事を じっくり 読んだ／検索で着地した／いま読んでいる |
| `ai_quality` | AI生成記事の品質・AIレビューの精度・AI開発の品質・ガードレール導入コストなど、AI を使うことの品質を発注側の立場で扱う題を じっくり 読んだ／検索で着地した。作る側向けの LLM の記事は付けない |

- 事業者 を含まないラベルは `[]`。
- 実績を 流し見 しただけでは trust を付けない。料金が現在のページなら cost は付く（「そのページに来た」根拠で足りる。3.4 と同じ扱い）。

### 3.7 cta_ok（強い CTA を今見せて役に立つか）
`true` は次の全部を満たすときだけ。それ以外は `false`。
1. visitor_type が `"事業者"` の確定（集合は false）。
2. stage が 2 以上。
3. `trigger` が T2 か T3（着地直後の T1 は false。当社のページをまだ何も見ていない）。

## 4. 許容集合にしてよい条件

- 集合にできる軸: **visitor_type、industry、need、cards.best** だけ。stage は整数、concerns は当てはまるものの列挙、cta_ok は真偽。
- 集合にしてよいのは、**状態の中に、2つ以上のラベルそれぞれを支える手がかりがあり、どちらかに決める手がかりが無い**とき。
  「念のため」「どちらでもよさそう」「外れにしたくない」で足さない。手がかりの無いラベルは入れない。
- **集合は最小に。** ふつう2つ、最大3つ。3つ目を入れるのは、3.1 の表に書いた場合と、3.3 で need に `"other"` を足す場合だけ。
- 集合にした行は `label_note` に理由を書く（どの手がかりがどのラベルを支えるか）。
- 集合を使うほど評価は甘くなる。確定できるものは確定する。特に visitor_type に `"事業者"` を含む集合は、「事業者への誤り」の数え上げで確定と同じには扱えない。
- 集合の順番に意味は無い（v2 では第1ラベルという概念が無い）。ただし読みやすさのため、より支持の強いラベルを先に書く。

## 5. 記録の形式

### 5.1 `eval/sessions.json` の `expected`（v2）
```jsonc
{ "visitor_type": "事業者" | ["事業者", "other"],        // 文字列＝確定、配列＝許容集合
  "industry": "不明・その他" | ["人材", "不明・その他"],
  "need": "サイトリニューアル" | ["新規サイト制作", "サイトリニューアル"],
  "stage": 0 | 1 | 2 | 3,                                  // 整数
  "cards": { "best": "sg-pricing" | ["sg-pricing", "sg-web"] | "none",
             "relevant": ["sg-pricing", "sg-web"] },        // best は relevant の中から。空なら best は "none"
  "concerns": ["cost"],                                     // 順不同。無ければ []
  "cta_ok": true | false,
  "note": "ページ列の要約（事実だけ）",
  "label_note": "集合にした理由、迷った点、揃えのために採った判断（無ければ省略）" }
```
- 文字列は `data/nq-labels.json` の語と一字一句同じにする（付録 A）。全角・半角・中黒・括弧の違いで `--check` が落ちる。
- `version` は 2。旧フィールド（`relevant_cards` `best_card` `alt`）は書かない。
- `cards.best` に `"none"` を含む集合（`["sg-web", "none"]`）は、3.5 の「事業者 と 同業者／求職者 の集合」のときだけ。
- `request` は変えない（変えると別のセッションになる）。`request` に不備があれば直さずに 5.3 に記録し、評価担当に渡す。
- `note` は事実の要約に直してよい（解釈語を消す）。

### 5.2 `label_note` に書くこと
- 集合にした理由（必須）。例: 「統計の読み物を検索で引いた。事業者とも学生とも読める」。
- 揃えのために採った判断。例: 「同型の sNN と同じ付け方」。

## 6. 揃えの確認（型の一覧）
2 の手順のあと、次の型ごとにセッションを並べ、同じ型で同じ付き方になっているかを見る。違いがあるなら、その違いを生む手がかりが状態にあるかを確かめる。無ければ揃える。

|---|---|
| 発注側向けの記事に検索で着地（T1・履歴なし） | 事業者 確定／stage 0／題の問いに答えるカードが best／題の不安 |

## 7. 高検討度セッション 10 件の作り方（s61〜s70）
目的は、人が stage 2 以上と付けるセッションを増やし、検討度の分布としきい値を評価できるようにすること（decisions 1章・2章）。

- 形の条件（`sessions.json` の `_comment` と同じ）: URL は `data/catalog-pages.json` か BLOG に実在するものだけ。`history` に現在のページを入れない。`current.reach` は T1・T2 では `top`、T3 では `end`。静的LP（`/service/*`）は履歴の途中にだけ置く。`session_id` は `r_eval0061` 〜 `r_eval0070`。`passed` に入れるのは `data/blocks.json` に在る ID だけ。
- 実在しそうな動きにする。既存の 60 件とページ列を丸ごと重ねない。`ref` `visit` `device` `trigger` をばらす（T2 が中心、T3 を 2 件以上）。
- 入れる動きの目安（合計 10 件）:
  | 動き | 件数 | 狙い |
  |---|---|---|
  | 料金 じっくり → 実績 → 無料診断（現在） | 2 | stage 3、cta_ok true |
  | サービス じっくり → 料金 → サービス紹介資料（現在） | 1 | stage 3 |
  | 補助金の記事 じっくり → 補助金活用相談（現在） | 1 | stage 3、sg-subsidy が候補から外れる型 |
  | 再訪で料金に着地 → 実績 → サービス（現在） | 2 | 「再訪して料金」で stage 2 |
  | 業種パッケージ じっくり → 業種の実績 → 料金（現在） | 2 | industry 確定、sg-solution/sg-works が外れたあとの best |
  | 見積書・RFP・選び方の記事 じっくり → 料金 じっくり → 実績 → 会社概要（現在） | 2 | stage 2、trust と scope、`passed` を 1 件に入れる |
- できれば、`--check` が「best/relevant に一度も出ないカード」と警告するカードを、この中で自然に正解にする（例: 保守運用費の記事 じっくり → 料金 じっくり → 実績（現在）なら `sg-support` が best になる）。無理に入れない。
- 作ってから、ほかの 60 件と同じ手順で盲検でラベルを付ける（作った人がそのまま付けてよいが、作るときに正解を決め打ちしない。ページ列を先に決め、本書で付ける）。
