### 共通の理由（表の中で「共通◯」と書いたもの）
- **共通E（営業）**: 売り込み目的は閲覧履歴だけでは言えない。下書きの `_comment` も「閲覧だけでは言い切れないので other を許容」と書いている。第1を other にし、営業・売り込み（と、スタッフ紹介を見ている行は 求職者・学生）を alt に回す。s57・s58 と同じ形になる。
- **共通N（事業者でない訪問者の need）**: 第1は other のまま。着地記事を じっくり 読んだか、いまその記事に居る（T1・T3）なら、その記事の need タグを alt に入れる。流し見・途中離脱の記事のタグは alt に入れない。理由: タグは状態にそのまま入っていて Jev はそれを読む。need の質問文は「外部に頼みたいか」を聞いておらず、開発者が読む技術記事でも文字どおりには当てはまる。need がルールに効くのは行5のカードの順位づけだけ。
- **共通S（事業者でない訪問者の stage）**: stage の 4 段階は発注の検討度で、同業者・求職者・営業・other には当てはまる段階が無い。正解 0 は約束事。直さず、stage は `eval/run.js` が別に出している「事業者だけ」の数字（±0 65.6%、±1 90.6%）で見る。Jev が 2 付近を返す行は【B3】で、タイプを確信できなかったとき（s48〜s52、s57、s58）に行6の対象に残る点だけ注意。
- **共通K（relevant_cards の定義）**: 案は「状態の中に、その audience に当てはまる直接の手がかり（題・ページ種別・読み方）があるカードだけを relevant_cards に入れる。『次の一歩として見せたい』だけのカードは alt.best_card に回す」。
  下書きの `_comment`「閲覧履歴から人が無理なく推測できる正解だけ」に沿う。**ただしこれは Jev の答えに正解を寄せる方向の直しなので、採るかどうかは人が決める。** 採らないなら、sg-pricing と sg-works の audience に状況の語を足して Jev が拾えるようにするのが筋（`data/blocks.json` の担当）。

### 7-2. 読み方の重み
- 途中離脱した記事は根拠にしない（s55）。例外は、検索や直接で「採用情報」のような目的のはっきりしたページに着地した場合（s47 は 求職者 のままでよい）。

### 7-3. need
- 事業者: 着地記事の need タグではなく、セッション全体から読む。新規かリニューアルかが分からないときは片方を第1、もう片方を alt（下書きのとおり）。何を作りたいか読めなければ other（s26）。
- 事業者でない訪問者: 共通N（第1は other、じっくり読んだ着地記事のタグを alt）。全件で揃える。

### 7-4. stage
- 0: 課題や用語の記事だけ。1: 費用・導入・進め方の記事、または料金を 1 回見ただけ。2: 7-1 の 発注検討中 の条件を満たす。3: 再訪で、料金・実績・声・会社概要を一通り見たうえで、相見積の記事かゴールのページ（資料・無料診断・補助金相談）も見ている（s23）。迷ったら 2。
- 事業者でない訪問者は 0（約束事）。採点は「事業者だけ」の数字で見る。

### 7-5. カード（best_card / relevant_cards）
- relevant_cards は、状態に直接の手がかりがあるカードだけ（共通K）。sg-pricing は題に「費用・相場・見積」、sg-subsidy は「補助金」、sg-works は業種が分かっていて実績をまだ見ていない、sg-support は保守・運用・担当者不在、sg-solution は業種が分かっている、sg-web はサイト制作・リニューアル（採用サイトを含む）。
- 「次の一歩として見せたい」だけのカードは alt.best_card へ。手がかりのあるカードが候補に残っていなければ best_card は none。
- 関連度が 0.02 以内の同点は、どちらが 1位でも外れと見なさない（s01、s06、s25）。どちらも relevant_cards に入れておく。
- 第1が 同業者・求職者・営業・other のセッションは none。other の読み物1本は、記事のテーマのカードを alt に入れてよい（s53、s59）。

### 7-6. concerns
- cost: 費用・相場・見積・補助金・格安の記事を じっくり、または料金を じっくり／現在のページ。
- trust: 発注検討中 で、実績・お客様の声・会社概要のどれかを じっくり 読んだか、いまそこに居る。
- scope: 進め方・要件定義・RFP・「社内に担当者がいない」の記事を じっくり。「制作会社の選び方」は trust 側。
- schedule / ai_quality: それを題にした記事を じっくり、またはいま読んでいる。
- 事業者でない訪問者は空。

### 7-7. cta_ok
- 「事業者で stage 2 以上」に加えて、**T2 か T3 で、当社のサービス・料金・実績・声のどれかを少なくとも 1 ページ見ている**こと。着地直後の T1（s29）は false。

### 7-8. 完了条件をどの数字で見るか
- 案: **許容込み（alt も正解）を主の数字**にし、完全一致は参考にとどめる。other を第1にして alt を付けたセッションが、直したあとは 11 件になり、完全一致は第1と alt の順番だけで約 7 ポイント動くため。
- あわせて「確信あり（0.6 以上）での正答」（いま 97.4%。外れは s46 だけ）と、1章の「ルールの分かれ目」を見る。実際に画面を変えるのはこの 2 つ。
- 許容込みで見るなら、alt の付け方を 7-1〜7-3 で揃えることが前提（揃っていない alt で点が動くのを防ぐ）。

### 7-9. この基準を当てはめると、いま食い違っていない行でも変わるもの
試算には入れていない。採るなら一緒に直す。
- s36: s38 と同じく自社プロダクトのページへ進んでいる → `alt.visitor_type: ["情報収集中の事業者", "other"]`。Jev は 同業者 0.51（確信度 0.41）なので、しきい値適用後の外れが 1 件減る。
- s24: 小売の実績を じっくり → 7-6 なら concerns に trust。Jev は 0.50 なので見逃しが 1 件増える。
- s10: 発注検討中・stage 2 に直すなら、cta_ok は true（Jev 0.42 → 見逃し +1）、実績が現在のページなので concerns に trust（Jev 0.46 → 見逃し +1）。

## 8. 担当外で気づいたこと（直していない）
- `api/_lib/state.js`: need タグ（と topic・industry）を着地ページにだけ入れている。【B1】の原因。履歴のページには付かないので、着地がトップや料金だと need が other に落ちる（s21）。タグを渡すのをやめるか、履歴にも付けるかは設計の判断。
- `data/nq-labels.json` の `page_type_labels`: 会社概要・スタッフ紹介が「信頼・条件」。【B3】の原因。会社情報を別の種別名にすると、求職者・営業の stage と trust が下がる見込み。
- `data/nq-labels.json` の stage の基準 1「解決方法や費用の相場を比較している段階」: 料金プランの閲覧と文字どおりに結びつく（【B4】）。「記事で一般的な相場を調べている」と「特定の会社の料金・実績を見て依頼先を比べている」を書き分けると 2 に上がりやすい。
- `data/nq-rules.json`: `stage_cta: 2` は Jev の score（確率の重みつき平均）ではほぼ届かない（60 件中 1 件）。`cta_ok: 0.7` は Jev の値の範囲の外。
- `eval/run.js`: 「none の一致」が `alt.best_card` を見ていない（s26、s35、s40）。
